## 9 七条口径演进主线

第 2 至第 8 节按代陈列细节，本节只陈列跨代方向与断点：每条主线给序列、失效点与这一改带来的可核对后果，凡能从盘上或提交面数出来的都给锚。

主线一，用户入口与启动件的更替。序列自 v1.0 的 00_START_HERE.md 加 agent/AUTONOMOUS_MASTER_AGENT_PROMPT.md（P-G01 §二）起，v1.1 至 v1.3 换 AUTONOMOUS_ENTRY.md 加 START_PROMPT.txt 双件、提示词 61 至 66 字符并被 v1.2 的 tools/validate_pack.py 列为 REQUIRED 前两项（P-G01 §四）；v2.0 再加 README_INSTALLATION.md 的八步首执且规定冲突以 README 为准（P-G02 §四-1）；Stage1 分两套，Agent 包用 00_AGENT_START.txt 加 START_HERE.md、交付包用 00_README.md（P-G03 §二）；ACR 五包用 00_AGENT_START_PROMPT.txt，其首段自述包名固定（P-G04 §一）；V3 起定标为 00_READ_FIRST.md 加 START_PROMPT.txt，V4 反而缺提示词、V5 恢复（P-G07 §六 6.1），V6 起提示词须含 main、ACR、32R 等 token（P-G09 §四-1），V8.1 首把一到一百字符写成机器断言（validate_control.py:255）；对齐包 V1 取消提示词只留入口件（P-G13 §二 2.1），救援包又配回五十四字符提示词（P-G14 §二），包规范件的槽位清单则不含 START_PROMPT（P-G15 §六），现行 RQS 退回 00_README.md 导航件（建区锚 C1859｜43c5c488）。断裂有三处：C237｜a78f5430 把 v1.x 载体整件删入历史，V3 定标改写了此后四代的名字，宪章期改由槽位清单裁定谁算入口。可核对的后果是同一身份在不同形态下可能一份有一份无——V4 的 zip 缺提示词而解包件齐全，判「缺件」必须先声明比的是哪个形态；提示词一旦带机器断言，长度本身就成了可失败项。这条主线的方向是入口件从给人读的叙述件变成被清单钉死的契约件、再退回单件叙述，往返两次。这条主线的可核对性还有一层：入口件名本身就是断代依据——按 00_START_HERE、AUTONOMOUS_ENTRY、00_AGENT_START、00_READ_FIRST、00_README 五种字面量给七十四实例分类，得到的分布与按提交日期分类几乎重合，只在 V4 与救援包两处错开，而那两处恰是本线自己制造的断档与回潮。可见入口制式不是收敛性设计，也不能当作稳定性证据：它是随派发动机临时改写的附属件，同一份文件在七代里承担过说明书、契约与导航三种角色。另有一处后果可直接复算：入口件缺位在 pack_inventory.csv 与 digest 里都表现为文件数差一，判「zip 与解包件是否同构」时它是第一个要核对的路径。

主线二，架构分层与规格骨架。序列：v1.0 根十八份编号规格加六子目录（P-G01 §二）→ v1.1 迁 docs 十九份并新立 contracts 与 reference、v1.2 把 contracts 全数 schema 化（P-G01 §二）→ v2.0 收敛到七十四文件（P-G02 §六 6.1）→ V3 至 V5 走顶层规格加 templates 与 scripts，V5 新增独立 schemas 两件且 SHA256SUMS 从无到有（P-G07 §六 6.1）→ V6 全换代四十六文件并引入 fixtures（P-G08 §六）→ V7 推到九十九文件二十四规格加 validators 十八件、另立 ACTIVE_DOC_INDEX 的 L0 至 L3 分层（P-G10 §二）→ V8.1 删八项规格改建 baseline 与 ci、五十六文件十六规格、并把 baseline 的 zip 哈希写进机器门（P-G12 §四 4.2）→ 对齐包转成 control-pack.json 加 tasks 五十七件的图（首入库 C1796｜e9547c02、末触 C1849｜f5f944a5）→ 宪章期改由 工程控制/包规范.md 的七槽位定形、架构权威移入宪章 §1.1。断裂在 V8.1 与宪章期两处：schemas 目录被取消、完整性担保被 git 与登记面接走。可核对的后果是必需文件清单与目录实体两次脱钩——V7 的清单列十三项而包内实存十八件校验器，V8.1 的四件校验器又列三十八项 REQUIRED；于是同包三形态跑自家校验可能两败一成（V6.1 与 V8.1 均有此例），「包是否自洽」不再是包内单一真值，必须按形态分列。骨架规模从九十九文件升到一百九十九再跌回五十六与七十四，说明分层深度与文件数在代五见顶后反向。本线的方向可概括为三层递进：先由人写目录，再由校验器把目录写成清单，最后由仓库工具与宪章接管清单之外的东西。判别式是目录名的首现与消失次序——templates、schemas、fixtures、validators、baseline 五类目录的出入次序本身就给出代次顺序，无需读台账；其中 schemas 两次易手（V5 独立成目录、V8.1 并入 ci）与 validators 一次冲高（V7 十八件）是本线最大的振幅。本线的失效还解释了一个现象：同一代三个形态的文件数可相差一到三，差额几乎总在目录层的规格件而非载荷代码，故规模统计须按形态分列。

主线三，资源与真机门禁。序列：V3 采绝对值，05 号规格第 19 至 24 行写计算窗口平均 CPU 不低于 150%、单线程对双线程加速比不低于 1.50（P-G05 §四）→ V4 与 V5 改相对带宽式，阈值 0.80×min(workers,可用核数)，V5 再加前十秒快速失败与退出码十（P-G06 §六、P-G07 §四）→ V6 与 V6.1 改统计式，p50 不低于 90、mean 不低于 85、worker p50 不低于二，并把 Fatduck 等待写成 WAITING_WINDOWS（P-G08 §四、P-G09 §四）→ V7 回到均值 80% 加连续十秒低于 50% 即禁止、加速比 1.60，另立 resource_class 三值（P-G10 §六）→ V8.1 包内只留定性条款，85% 与 60% 在全形态含两千一百五十三份留痕零命中，真机口径落在 09 号第 18 至 28 行的九步（P-G12 §四 4.6）→ 宪章期数值实体在 §10.5 与 §18.2 以及 run_monitored.py:453/455、resource_gate.h:108/111，两枚代码锚分别引入于 C1745｜1a590f63 与 C1809｜91440c16。断裂有三段：绝对值死于 V4，包内数值死于 V8.1，等待状态死于 V7 却在 V8.1 留痕里以枚举外字面量 FATDUCK_PENDING 复活（P-G10 缺口 12）。可核对的后果是「包写了什么阈值」自此不能用来判定运行是否合格，必须去 grep 代码常量与宪章条款；而救援期只设禁止项不设 waiver，把这条主线收束在门禁不再随包发布这一点上；等待语义的最后一处残迹，是留痕面那个越枚举的 FATDUCK_PENDING。可核对性因此双向变化。一边上升：数值锚现在可以在 run_monitored.py 与 resource_gate.h 的行号上直接读到，两枚引入提交 C1745｜1a590f63 与 C1809｜91440c16 都晚于提出该口径的包，链条可双向验证。另一边下降：V3 至 V7 的阈值随包而异，若沿用现行的 0.85 与 0.60 去回看前四代，会把它们全部判成不合格——这正是第 10 节所说命中与完成不可互推的由来。本线的实质是把阈值从叙述搬进代码：数值不再随包发布，而成为仓库常驻实现的一部分，包只负责指向它。同时资源口径与真机口径在本线里合成一条：包内既不再写数值，也不再写 Fatduck 的等待状态，两者一并交由登记面与代码接管。

主线四，版本与包命名口径。序列：v1.1 的 PACKAGE_VERSION.txt 记日期加特性长串，v1.2 两行，v1.3 收敛为语义化 1.3.0、文件本身从六十六字节缩到六字节（P-G01 §六）→ v2.0 改名目式（P-G02 §2.1）→ V5 的 13 号规格第一章定 MAJOR.MINOR.PATCH-alpha.N 并把 alpha 正则写进终包校验器（该号第一章第 97 行）→ V6 与 V6.1 改由 MANIFEST.json 的 target_version 承载，0.10.0-alpha.1 递增到 -2、用 prior_control_sha256 链代（P-G08 §二、P-G09 §二）→ V7 让包根 VERSION 与 product_version 同值为 0.11.0-alpha.1、链代改指源码提交（P-G10 §六）→ V8.1 的包根 VERSION 写 8.1 并被 validate_control.py:150 断言，语义从产品版本改成包版本，与宪章 §16.1「根 VERSION 为唯一版本输入」构成口径冲突 → 宪章期包内再无版本件、救援包版本字样零处（P-G14 §五），根 VERSION 停在 0.11.0-alpha.2。审核包命名同线演变：V3 每 Gate 一包、V4 与 V5 任务号加提交十二位胶囊、V6 与 V6.1 单一审核包带 UTC 时间戳与十二位哈希、宪章期改 hash 式、救援期取 sha256 前十二位（P-G05 §四、P-G07 §四、P-G10 §四、P-G14 §四）。断裂在 V6 的清单绑定取代包内规格、与宪章期包内版本件消失两处。可核对的后果是版本字样散落四个位置且可四值并存——V7 的抬头、MANIFEST、zip 文件名与解包目录名各写一处，ALPHA 可只在 zip 名而不在包内（P-G07 §一 1.2）；凡按包名里的版本对齐提交窗口的做法都会错窗，AUDIT_PACKAGE_587fe0e341a7.zip 之名内嵌的其实是提交哈希，其锚为 C1259｜587fe0e3。本线的实质是版本号从叙述退成索引：早期版本串承载语义（日期、特性、阶段），后期只剩机器可断言的短码，真正的版本权威移到根 VERSION 与宪章 §16.1。判别式必须四路并读——包内版本件、清单字段、文件名内嵌串、根 VERSION——任何一路单独使用都会错代。命名与哈希的混淆是本线的副产品：十二位串既可指提交也可指包体，故引用包名时必须写全来源形态与所指对象。命名口径还有第三处后果：ALPHA 只在文件名出现时，包内条文与清单并不含该字样，按包内文本检索版本阶段会整代漏判。

主线五，台账与状态机字面量。序列：v1.1 的 MASTER_TASK_REGISTER.csv 三值 TODO/DONE/BLOCKED，v1.2 增 DEFERRED、v1.3 增 IN_PROGRESS（tools/migrate_from_v12.py 第 40 至 46 行的映射）→ v2.0 换 READY/CONDITIONAL/PENDING_USER_DECISION 并出现任务卡、台账、Gate 清单三载体，卡与账漂移廿四对三十（P-G02 §六 6.1）→ ACR 五包改用 coverage 状态机加结论词 SKIPPED/PASS/ABORT（P-G04 §四）→ V3 起五值、V4 七值、V5 六值且 DEFERRED 被明文禁用而 REVIEW_PENDING 存一行（P-G05 §三、P-G06 §三、P-G07 §三）→ V6 的 validate_task_graph.py:19 立 WAITING_WINDOWS、删 BLOCKED，V6.1 把七值推给仓库工具（04 号第 47 行）→ V7 删 status 列、状态外置 TASK_STATE.json 十一值并新增 WAITING_RESOURCE → V8.1 status 列回归且三十六行全 NOT_STARTED → 对齐包首用 PASSED 并把 REVIEW_PENDING 判死 → 救援包不建台账、RQS 改以 fix_state 与 verified_state 承载（账本/FIX_LEDGER.csv 的二十四列内）。断裂有三：V6 判 REVIEW_PENDING 非法而 V5 表里仍存一行；V7 删列使状态在包内消失一代；宪章期三本历史台账全被现行 tools/quality/validate_task_ledger.py 判列不匹配（P-G13 §四 4.3）。可核对的后果最硬：以今日校验器复核历史包必然报错，不能据此倒推历史包失格；且跨代统计完成度必须先声明用哪一代枚举，否则同一行在 V4 是 DEFERRED、在 V5 是禁用词、在 V6 是非法值。这条主线的方向是状态语义从包内列移到包外文件、再移到仓库工具与登记面，字面量的可数性随之下降：V5 之前可按列统计，V7 之后必须按包、留痕、工具三处分别统计，代七起还要加登记面一处。后果最直观的是完成度：同一次执行在 V4 记 PASS、在 V5 可记 REVIEW_PENDING、在 V6 起该写法被判非法、在 V8.1 必须写成 PASSED 才能通过对齐校验、在 RQS 则拆成 fix_state 与 verified_state 两列。因此本报告在第 2 至第 8 节逐代照录字面量原值、不做归一，凡遇同义改写只在句中标注而不改数——这是本线给出的最重要口径纪律，也是代与代之间不能直接相加的唯一解释。另登记一处反向证据：V5 的 DEFERRED 在入口件第三章被明文禁用，却在同一张台账里留有一行，说明声明面与数据面在本线中长期两条轨迹。

主线六，审核包与提交协议。序列：V3 定十步提交与七条禁止（06 号规格）、每 Gate 停工、审核包压缩后不超 25MiB 且单文件不超 5MiB（07 号规格）→ V4 在 01 号的取消节改连续执行、只留最终一次原子提交、结论词限 AWAITING_EXTERNAL_RELEASE_REVIEW、审核件封装换成十二号胶囊规格 → V5 的十号第二章把胶囊索引铺到八十八行且实测每行有胶囊、十五号定 C0 至 C9 出口校验 → V6 的十二号规格要求四类提交相等并支持 --baseline-sha256 冻结台账，V6.1 以 validate_return_audit.py 取代旧校验器、把 READY 与 alpha 批准分离 → V7 的十八号第一与第六章定 verdict 四值与五步提交门 → V8.1 的十一号规格加 08 号第 26 至 30 行立 known_failures 只减不增，唯一一次变更 C1944｜ccc7a933 是删除 → 宪章期完成顺序改由 §14.5 第 567 行六步冻结、审核包自产不超 10MB、修复面转为常驻账本（账本/README.md 第四章）。断裂有三：胶囊体系死于 V6 的单一审核包；V6 交付的审核实物是 .tar.gz、违反自家十二号规格第一章；审核包实物在 C1785｜789c5b6c 出库后包内只剩名字指向。可核对的后果是协议越严密越依赖包外实物：V6.1 的 MANIFEST v2 四个绑定字段里 reviewed_audit_sha256（137e3ed14ef85142 起）在现存文件与十一份 zip 中零命中，归档回写又使 V5 台账哈希进入四个不同状态（基线快照 C1232｜ef0858c5 与归档复原件 C1251｜3ca7f974 之间），凡引用该哈希的字段随之失效。本线还留下一条方法性后果：审核实物的存在性与包内条文的可执行性并不等价。V6 之后审核包不再随控制包入库，包内条文只描述其结构，于是同一句四条提交相等的要求在 V6.1 有两种执行结果——密封版判 FAIL、改版判 PASS，两条记录都真实存在，取舍待裁（见第 13 节丙类）。判别顺序因此要反过来：先看有无实物，再看有无条文，最后看有无留痕。本线的提交锚也最密集：从 C1039｜b12305ed 的删一归一到 C1785｜789c5b6c 的审核包出库，协议变更几乎都是单提交落地，可逐枚复核。

主线七，派发协议。序列：v1.0 单代理总提示词加控制器六子命令 → v1.1 一句话提示词 → v2.0 的 install_and_migrate.py 把派发做成安装器、硬编码目标目录 → V3 至 V6.1 回归上传 zip 加启动动作，解包、跑校验、取三枚 SHA、写 evidence 四步定型，台账出厂密封全 NOT_STARTED → V7 换 cprun 队列，配 05 号绑定表与 DISPATCH.json，实测队列 tasks=140、mutex_lock 92、owner 三十三名 → V8.1 弃队列改用负责人直令加前台手册（04 号第 37 至 39 行十要素、WRITE_LEASE.json 单写租约、next_tasks.py 算可派集），包内 cprun 字样零命中 → 宪章期由 cprun-v4-pack-template 与 工程控制/包规范.md 定八字段派发（模板入库锚 C1784｜4d3feaf4），救援包 00 号第三章明文不依赖队列插件 → RQS 收成负责人直接指令加自建工作区加三级流水线（首锚 C1859｜43c5c488）。断裂有三：安装器派发随 C237｜a78f5430 删副本而终；队列派发终止于 42/140 的解除武装登记（ACTIVITY_STATE.md 第 24 行，随 C1850｜5a250999 入库）与 R-18 停用门框架；zip 密封让位于工作区原地接管，而 RQS 一代七百四十二文件全量入库，方向恰与 zip 不入库成常态相反。可核对的后果是任务被谁标成 IN_PROGRESS 在七代里有四种答案——安装器、启动动作、cprun 队列、负责人直令，故台账状态列的时间戳不可跨代比较；且派发动机与包体解绑后，包内不再留派发的机器痕迹，只能由登记面与框架证据域佐证。本线可核对的最后一层后果是登记面的兴起：派发协议在包内消失后，谁在派发只能由状态件的 §2 表与框架证据域的运行记录反推，而该表九行里唯一标 ACTIVE 的是救援包、RQS 甚至不在表内。这意味着到代七，包不再是派发协议的唯一载体，口径演进的终点是包与派发解绑：包给规格与门禁，登记面给状态，框架给队列，三者互不覆盖也互不复算。若把这条线画到底，可核对的端点是两份文件：代五的 DISPATCH.json 是队列实存，代七的 工程控制/ACTIVITY_STATE.md 是登记实存，中间再无第三种派发动机留下的包内文件。
