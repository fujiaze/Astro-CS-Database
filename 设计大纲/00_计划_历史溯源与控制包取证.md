## 0. 本计划的边界与硬约束

1. **只做客观取证，不做设计判断。** 报告只写"发生了什么、包内写了什么、证据指针在哪"，不写"应该怎么设计"。后续的设计大纲由负责人基于这些报告自行分析。
2. **不写大段代码。** 报告中禁止粘贴 diff / 源码块。允许的形式是"文件级 + 函数级 + 行为级"的自然语言描述，以及 SHA / 文件路径 / 台账行号等证据指针；单条引用的标识符不超过必要限度。
3. **每条断言带证据指针**：commit SHA（短 8 位）、文件相对路径、控制包内的文件名与条款号。无法从证据直接支撑的话，写"未证实/证据不足"，不做推断性补全。
4. **区分三类陈述**：`事实`（证据可直接核对）、`归纳`（由多条事实聚合，附聚合依据与覆盖范围）、`缺口`（应存在但找不到的证据）。归纳不得写成事实。
5. **仓库纪律**（AGENTS.md / 宪章）：SubAgent 不 commit、不建分支、不碰 `BASS DR3/`、`GaiaDR3*/`、`AstroCS.wiki/` 等用户/资料区；所有分析脚本放 `设计大纲/_tools/`。

## 2. 任务一：项目历史溯源

### 2.1 三层流水线（先代码固定证据 → 再子子代理逐条详析 → 再子代理归纳阶段）

```
层 1（脚本，非模型）  git plumbing → 设计大纲/_evidence/commits/*   ← 固定、可复核、可重跑
层 2（子子代理 ×N）   每片按权重领 30–60 条提交 → 设计大纲/reports/history/slices/H-Sxx.md
层 3（子代理 ×1）     合并分片 + 重叠区冲突核对 → STAGE-0x.md + 00_OVERVIEW.md
```

**层 1 产出（用代码固定证据，不含解释）**
- `index.jsonl`：每提交一行 —— seq（拓扑序号，1=最早）、SHA 全/短、author、ISO 日期、是否 merge、类型前缀、**任务编号抽取**（正则 `P\d+(-\d+)?`、`V\d+(\.\d+)?`、`[A-Z]{2,6}-\d{3}`、`RQS`、`GOV-\d+`、`M\d+`）、subject、body 全文、文件数、增/删行、重命名数、顶层目录直方图、根谱系归属。
- 单提交**证据卡** `cards/H-Sxx/<seq>-<sha8>.md`，固定五段：
  1. `元信息`：SHA、日期、作者、抽取到的任务编号、**消息全文**（消息本身是一手证据，原样保留）
  2. `变更面`：按目录聚类的影响面 + 新增/修改/删除/改名清单（改名保留旧路径→新路径对）
  3. `内容要点`：脚本抽取的结构性摘要 —— 被改的函数/类/结构体签名、新增或删除的测试用例名、`CMakeLists.txt` 目标与选项变化、`TASK_LEDGER.csv` 账本行的增删改、schema/contract 字段变化、`ci/checks.json` 检查项变化、`module.yaml`/`README` 声明变化（**只列标识符与签名，不列函数体**）
  4. `自述 vs 变更面`：消息声称的目标与文件级证据是否同域（客观比对，不下结论）
  5. `限长标记`：卡片是否触顶被截断、截断段
- `cross.csv` 三张透视表：目录×月份提交数与净行数、任务编号族×月份、包文件×提交事件（供层 3 划阶段）。
- 大提交（191 条"大" + 36 条 >10k 行）走**结构模式**：只出文件集合、改名映射、目录直方图与"搬家/导入/整理"型标记，不出逐文件要点。阶段统计里把"净开发行"与"搬家行"分列。
- 硬编码排除区：`run/`、`build/`、`out/`、`worktrees/`、`third_party/`、`GaiaDR3*`、`BASS DR3/`、testdata 二进制。

**层 2 分片规则（对应"每个子子代理负责一定条数，之间要有重叠"）**
- 排序：拓扑序（时间序的可靠近似），1981 条全覆盖。
- 权重：小提交 1 / 中 2 / 大或搬家 4；每片权重预算 ≈ 75，落片时提交数随之在 **30–65 条**之间浮动；预计 **33±3 片**。
- **重叠**：相邻两片共享 **10 条**（≈15%）。两片各自独立对这 10 条出正文；片尾 `重叠区核对` 段必须写明与上一片结论的一致/不一致。
- 每份 `H-Sxx.md`：逐条（同任务编号的连续提交可合并成组，但组内列出全部 SHA）给出 `做了什么 / 改动落在哪些模块与契约 / 与前后提交的关系 / 证据指针`；片尾三段：`本片主题归纳（标注为归纳）`、`重叠区一致与不一致`、`本片遗留与缺口`。
- 并发：后台 subagent，每批 ≤6 个，约 6 批收口；每批落盘即完成，不重跑。
- 派发拓扑：前台 → 2 个顶层子代理（历史、控制包）→ 各自再派发子子代理领分片。若子子代理不可得，退化为前台直接分批派发，**分片与重叠参数不变**。

**层 3 归纳（1 个子代理 + 前台复核）**
- 阶段划分判据（只用可核对信号）：控制包版本切换点（zip 上传/解包/归档提交）、目录谱系重构提交（`engineering_v1.2 → v1.3 → archive → 工程控制 → engineering/control`）、CI 门禁体系变化（`ci/checks.json` 条目增减）、任务编号族更替（`P0x` → `P3-00x` → `WIN/SYN/SCI/ISA/BENCH/ALG/ARCH/API/CLI/PAR/REV/ABI/ISO` → `V8-CI-0xx` → `RQS V4/V6/P8-P15`）、13 条根谱系边界、明显时间断档（如 06 月仅 4 条）。
- 输出：`STAGE-01…0N.md`（每份一个大阶段）+ `00_OVERVIEW.md`（跨阶段总览、阶段划分依据表、覆盖率声明、指针索引）。
- 每份阶段报告固定结构：`时间窗与提交数 / 该阶段要解决的问题（引自包与提交消息） / 具体工作内容（按模块分述） / 交付与验证留痕 / 结构与规范变化 / 遗留与下一阶段衔接 / 证据缺口`。

### 2.2 验收标准（任务一）
- **覆盖率**：1981/1981 提交在分片清单中登记，且至少一片有正文条目（搬家型提交以文件集合条目计）；未覆盖者列显式缺口及原因。
- **抽查**：随机 30 条由前台回读原始 `git show` 核对分片条目，误读率写进 `spotcheck.md`。
- **冲突**：所有重叠区不一致逐条列表 + 裁定依据，保留两方原文。
- **可复核**：报告里每个数字都能指向 `_evidence/` 的一个文件或一条可复制命令。

## 3. 任务二：历代控制包详析

### 3.1 流水线
```
层 1（脚本）  包身份归一 + 影子树去重 + 历史复原 → 设计大纲/_evidence/packs/*
层 2（子子代理）  每包一份详析（含与上游包的差异）→ 设计大纲/reports/packs/P-*.md
层 3（子代理）    包谱系与代际归纳 → STAGE-0x.md + 00_OVERVIEW.md
```

**层 1**
- `pack_inventory.csv`：`包标识（名称+版本+日期戳）| 存形态（zip / 解包 / 归档 / 影子树副本 / 仅历史）| 路径 | 文件数 | sha256(zip 或 MANIFEST) | 首次出现提交 | 最后修改提交 | 当前状态（活动 / superseded / 已删）| 改名链`。
- 11 个 zip 原件**只读登记**（`unzip -l` 清单 + 抽样 `unzip -p` 读关键文件），不解压进仓库目录；同名包"zip vs 解包件"做文件级比对，多/少/改名差异逐条登记。
- 历史仅存包（`REAUDIT_V4/v4_reaudit`、`_new_pack_v1.1/AstroCS_CLI_Core_Development_Pack`、`Authoritative_v2.0`、`Stage1_HISS_Agent_Package`、`_agent_package`、`engineering_v1.2 / v1.3 / archive_v1.0 / authoritative`、3 个旧 zip）→ `git ls-tree`/`git cat-file` 导出到 `设计大纲/_evidence/packs/history/<路径>`，每份附**来源提交 SHA + 删除提交 SHA**双指针。
- 每包固定导出：`00_READ_FIRST.md`、任务台账 CSV（表头、行数、状态字面量分布、任务号集合）、`control-pack.json`/`MANIFEST.json`、`START_PROMPT.txt`、schemas 清单、scripts 清单（名称+行数+一句作用，取自文件自身说明）、`SHA256SUMS` 核对结果、`tasks/*.md` 任务号与规模。
- `run/**` 影子树只登记为副本，不参与内容分析；若与主副本有字节差异则登记差异。

**层 2（每包一份；体量小的相邻包由同一子子代理领 2–3 包，但逐包各出一份）**
`P-<包名>.md` 固定结构：
1. `包的身份与来源`：命名、版本、日期戳、zip sha256、引入提交、现存路径谱系与改名链
2. `包内文件地图`：各规格文件的职责（引包内自述，不改写为评价）
3. `任务结构`：任务数、任务号族（如 V5 的 98 任务；`WIN/SYN/SCI/ISA/BENCH/ALG/ARCH/API/CLI/PAR/P3/REV/ABI/ISO` 前缀按包内定义引用）、依赖图（若包内声明）、台账状态字面量与迁移
4. `门禁与验收要求`：机器门列表、状态机口径、控制包完成顺序、waiver/豁免机制（引包内条款号）
5. `设计意图（转述 + 标出处）`：包自述目标与禁止项；与前代的继承/废止声明（如 `11_V3_INHERITANCE_AND_INVALIDATION.md`、`12_V3_V4_MIGRATION.md`）
6. `代际差异`：与前一版本包的逐项差异表（新增/删除规格文件、新增或收紧的门禁、任务数变化、口径变化），不写优劣
7. `执行留痕三方核对`：包内台账 vs `evidence/<包短名>/tasks/<任务号>/` 实际留痕 vs `git log` 中带该任务编号的提交 —— 一致 / 有账无据 / 有据无账，报清单与数量
8. `缺口`：读不到、被删、无法归一化的部分

**层 3**：包谱系表（先后与继承声明的对照）、代际阶段报告（数个大阶段）、`00_OVERVIEW.md`（跨代口径演进序列：用户入口 / 架构分层 / 资源门禁 / 版本命名 / 审核流程 / 状态机字面量 / 派发与回报协议）。

### 3.2 验收标准（任务二）
- 清单完整性：19 个现存解包目录 + 11 个 zip + `cprun-v4-pack-template` + 历史仅存包（≥5 个）逐个有条目，且与 `git log --diff-filter=ADR` 的路径事件一致。
- 至少一条跨任务一致性验证：包声明的任务号族能否在任务一分片报告里找到对应提交（两任务报告互相索引）。

## 5. 规模、并发与风险

| 风险 | 处置 |
|---|---|
| 提交消息高度"自述化"，直接采信会失真 | 卡片把`消息自述`与`文件级证据`强制分列；层 3 不得把自述当事实 |
| 1981 条 × 摘要 ≈ 语料过大，子子代理上下文吃紧 | 卡片限长（小 ≤3KB / 中 ≤8KB / 大仅结构模式 ≤6KB），单片证据预算上限 220KB |
| `run/` 影子树被当成工作内容、包副本被重复计数 | 排除区在脚本里硬编码 + 副本登记；所有计数标"主副本" |
| 历史仅存包复原张冠李戴（同一包在历史里被改名多次） | 复原件绑定"来源提交 + 删除提交"双指针，改名链单独成表 |
| 36 条 >10k 行搬家型提交淹没真实工作量 | 结构模式 + 阶段报告分列`净开发行`与`搬家行` |
| 子子代理结论互相冲突 | 重叠区（10 条/边界）专设冲突登记，层 3 逐条裁定并保留双方原文 |
| 长跑中断 | 层 2 全部后台派发、按批收口，每片独立落盘，续跑只补缺片 |

预计工作量：层 1 一次跑完（分钟级）；层 2 约 33 个提交片 + 约 20 个包报告，分 6–8 批并发；层 3 共 2 个汇总代理 + 前台复核与抽查。
