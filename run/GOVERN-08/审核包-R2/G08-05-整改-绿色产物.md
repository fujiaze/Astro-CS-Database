## 2. 改法说明 + 改前改后逐字

### 2.1 选法与理由

**选法：让 `check()` 成为「打印 + 记账」的唯一通道（单通道收敛），并加一条独立于记账路径
的漏计守卫。**

不选「在调用点逐个补 append」的理由：前台在 `G08-05-整改-自证式判据-生产面.md:683` 建议的
正是「每个 else/continue 分支 append 一条 `pass: False`」（约 6 行）。**本单复核后不采用它**，
因为那是**逐点补丁**：它把这一次的 7 个洞补上，却把「下一个调用点再忘了」的风险原样留下 ——
本缺陷的成因正是「记账是可选的额外动作」。单通道把「打印」与「记账」在语法上焊死，
使「打印但不计入」这一状态**不可表示**。

三项具体设计：

1. **`Ledger.record()`（改后 `:99-120`）**：`print` 与 `self.sink.append(entry)` 在同一个
   函数体内相邻，任何 `check()` 调用都必然两条都做。
2. **`check()` 强制 `scope`/`tag`**（改后 `:125-132`）：25 个调用点逐个带 section 与场景
   tag（AST 复核见 §6.2），使摘要可按段追溯；账本未建立即调用时 `raise RuntimeError` 而非静默忽略。
3. **所有代码出口必经 `finalize()`**（改后 `:265-292`）：原 `main()` 的两个 `return 1`
   移入新的 `_run_checks()`（改后 `:294`），它**不返回退出码**，因此没有任何一条路径能绕过
   汇总落盘 —— B 组的「残留上一轮绿色摘要」随之根除。

**未改变任何判据/阈值**（逐条核对见 §6.3）：`GATES` 字典一字未动；D 段那个与
`GATES["closure_fp64"]` 不同的字面量 `1e-6`（改前 `:259`）**原样保留**，只是加了注释说明
它与 GATES 不同 —— 统一它会把门收紧，属于改判据，不在本单。H 段负例谓词一字未动。

class Ledger(object):
    """判定账本: 打印与记账的唯一通道。

    record() 打印一条判定, 同时把同一条判定写进 results["checks"]。判定不可能

    def __init__(self, sink):
        self.sink = sink          # results["checks"]

    def record(self, name, cond, detail="", scope="-", tag=None, **metrics):
        cond = bool(cond)
        print(VERDICT_FMT % ("PASS" if cond else "FAIL", name,
                             (" (%s)" % one_line(detail)) if detail else ""))
        entry = {"scope": scope, "tag": tag if tag is not None else name,
                 "name": name, "pass": cond}
        if detail:
            entry["detail"] = one_line(detail)
        entry.update(metrics)
        self.sink.append(entry)
        return cond


_LEDGER = None

        raise RuntimeError("判定账本未建立: check() 只能在 main() 内调用")

## 4. 新守卫：让「有失败但 `failed` 仍为 0」本身可被检出

### 4.1 实现

守卫在 `finalize()`（改后 `:225-262`）。**关键在于它走一条与记账无关的路**：`_Tee`
（改后 `:63-87`）在 `main()` 里把真实 stdout 复制一份留底，守卫数的是 `tee.text` —— **本次
实际打印出去的字节**，而不是 `Ledger` 自己攒的列表。

```python
def finalize(results, ledger, tee, out_dir):
    """唯一的出口: 从账本算汇总 -> 漏计守卫 -> 落盘 -> 返回退出码。 …"""
    checks = results["checks"]
    printed_fail = len(VERDICT_RE_FAIL.findall(tee.text))          # :237
    printed_total = len(VERDICT_RE_PASS.findall(tee.text)) + printed_fail   # :238
    recorded_fail = sum(1 for c in checks if not c["pass"])        # :239
    guard_ok = (printed_total == len(checks)) and (printed_fail == recorded_fail)  # :240
    results["guard"] = {"printed_verdicts": printed_total,
                        "printed_fail": printed_fail,
                        "recorded_verdicts": len(checks),
                        "recorded_fail": recorded_fail,
                        "consistent": bool(guard_ok)}               # :241-246

    ledger.record("判定账本自洽 (打印条数/失败数与记账一致)", guard_ok,
                  "打印 %d 条(FAIL %d) / 记账 %d 条(fail %d)"
                  % (printed_total, printed_fail, len(checks), recorded_fail),
                  scope="GUARD", tag="ledger_consistency")          # :247-251

    passed = sum(1 for c in checks if c["pass"])                   # :253
    failed = len(checks) - passed
    results["pass"] = passed
    results["fail"] = failed
    … json.dump …                                                  # :255-258
    return 0 if failed == 0 else 1                                 # :262
```

三处设计细节：

- **判定行格式单源**（改后 `:57-60`）：`VERDICT_HEAD = "  [%s] "` 同时供给 `print` 与守卫的
  两个正则，改格式必须同步改守卫，不会各自漂移。
- **守卫自己的判定也走 `record()`**（`:247`）。守卫在**记入自身之前**的窗口上计算
  `guard_ok`；记入后打印数与记账数**同增同减**，不变式按构造成立，守卫不会因自己而产生新的不等。
  守卫红 ⇒ `checks` 里多一条 `pass=false` ⇒ `failed ≥ 1` ⇒ `:262` 必然返回非 0。
- **`one_line()`（改后 `:89-96`）把 detail 压成单行**，这是必须的：真实的
  `drizzle_acceptance_test.cpp:39/:91` 自己也用 `  [FAIL] ` 开头打印失败行，而 exe 的输出会
  作为 `detail` 内嵌进本脚本的一行判定里。不压平则内嵌的 exe 失败行会被守卫误认成脚本的判定行。

### 4.2 它怎么被证伪 —— 三条，全部实测

「证伪」在此取两个方向：一是**证明它非空转**（能真的变红），二是**划出它会被打穿的边界**。

#### 证伪一：注入原缺陷形态 ⇒ 守卫必须变红（实测通过）

在改后副本 `/tmp/g08-05/negctl/` 里把 A 段 5 条 `FP64 闭合` 判定改成
`print(VERDICT_FMT % ("FAIL", …))` 的裸打印（**打印 FAIL 却不记账**，即原缺陷形态），
其余保持正确。跑「全通过」输入：

```
exit=1
  [FAIL] [north_pole] FP64 通量闭合
  [FAIL] [south_pole] FP64 通量闭合
  [FAIL] [equator_ra0] FP64 通量闭合
  [FAIL] [ra_cross0] FP64 通量闭合
  [FAIL] [nominal] FP64 通量闭合
  [FAIL] 判定账本自洽 (打印条数/失败数与记账一致) (打印 65 条(FAIL 5) / 记账 60 条(fail 0))
== 验收汇总: 60 通过, 1 失败 ==
summary: pass=60 fail=1 guard={'printed_verdicts':65,'printed_fail':5,
                               'recorded_verdicts':60,'recorded_fail':0,'consistent':False}
```

**这正是「有失败但 `failed` 仍为 0」的情形**：5 行 `[FAIL]` 已打印，而容器里 `recorded_fail=0`。
改前在这一状态下会给出 `fail=0` + 退出码 0（绿色）；改后守卫判红、退出码 1、摘要 `fail=1`。
⇒ **守卫非空转，它有牙齿。**

#### 证伪二：伪红检查 —— C++ exe 自身的 `[FAIL]` 行不得让守卫误判（实测通过）

用一个复刻 `drizzle_acceptance_test.cpp:39/:91` 格式、打印 3 行 `  [FAIL] ` 后 `exit 1` 的
exe，跑改后脚本：

```
  [FAIL] C++ 验收 exe 运行成功 (  [PASS] north_pole 闭合 ⏎   [FAIL] south_pole 闭合 rel=3.1e-02 >= 1e-07 ⏎   [FAIL] os1_pf0.50 FP32 相对差 4.4e-04 >= 1e-05 ⏎   [FAIL] another ⏎ )
  [PASS] 判定账本自洽 (打印条数/失败数与记账一致) (打印 3 条(FAIL 1) / 记账 3 条(fail 1))
== 验收汇总: 3 通过, 1 失败 ==
guard= {'printed_verdicts':3, 'printed_fail':1, 'recorded_verdicts':3, 'recorded_fail':1, 'consistent':True}
```

内嵌的 exe 失败行被 `⏎` 压平在同一行内，守卫数到的 3 条判定全是脚本自己的，**无误红**。
（若没有 `one_line()`，这里 `printed_fail` 会是 4 而 `recorded_fail` 是 1，守卫假红。）

#### 证伪三：守卫会被什么打穿（已知边界，如实登记）

1. **改到 stderr 的判定不被守卫看见**。守卫只镜像 stdout。若将来有人把某条失败写成
   `print(..., file=sys.stderr)`，它既不进容器也不进 `tee.text` ⇒ 守卫**漏**。
   缓解：该文件当前无任何 `file=sys.stderr`（已 grep 复核）；且这条与 §2.1 的单通道正交 ——
   只要走 `check()`，无论最终被谁读到都必然记账。
2. **守卫只核对「条数」与「FAIL 条数」，不核对内容**。若将来有人把两条 PASS 记成一条 FAIL
   而总数不变，条数相等 ⇒ 守卫不响。防这类需要语义比对，非本单范围。
3. **账本被外部等长改写**。`finalize()` 读的是 `results["checks"]`；若 `results` 在记账后被
   外部覆盖且长度不变，守卫不响（同上第 2 点）。

**结论**：守卫覆盖的正是本缺陷的形态（打印侧多于记账侧 ⇒ 条数/FAIL 数不等），并已在两个方向
上实测。边界是**换一条通道打印**，而不是「记账」本身 —— 后者已被单通道从语法上消除。
