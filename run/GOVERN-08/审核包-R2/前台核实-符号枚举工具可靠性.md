# 前台核实 · 「符号级枚举」的工具可靠性

## 起因
批次 3 车道提出一条方法论告警：**「`git grep` 在本仓会漏」**（它给的数字是跟踪集
1817 / 工作树 4009），并据此警告 AGENTS.md §2.3 要求的「符号级枚举」若建在
`git grep` 上，**方法本身就有洞**。前台实测复核。

## 复核结论：**告警的结论对，但它给的证据不成立，且适用范围被它说过头了**

### 一、它给的数字不成立
前台第一次复算时**忘了加 `-c core.quotepath=false`** ⇒ 中文路径被八进制转义，
与磁盘路径对不上，于是得出「3308 份生产源文件未跟踪」的**假结论**，
其中包括一批**其实已被跟踪**的实验审计脚本。

⚠️ **前台自己违反了本项目反复强调的那条纪律**（中文路径必须加 `core.quotepath=false`），
并且在管道写失败（`sort: write error`）的情况下**没有察觉就继续解读了那个数**。
⇒ 记一条：**测量出现管道错误时，得到的数一律不采信，先把测量做对再解读。**

### 二、加对参数后的真实情况
```
跟踪集                        2,851
磁盘（排除 run/ 与 build/）    5,110
磁盘有而跟踪集无              2,569   ← 绝大多数是 __pycache__ 字节码、
                                        testdata、CI 产物等**被忽略规则刻意排除**的
```
逐条 `check-ignore` 核过：漏掉的是 `__pycache__/*.pyc` 之类。

### 三、所以正确的结论是
- **「调用者是否在仓内」这个问题，`git grep` 对生产代码是够用的** ——
  被排除的是构建产物与测试数据，**不是生产调用者**；
- 车道用它自己两次踩坑（空捕获假阴性、行号读到脏工作树）来支撑这条告警，
  **那两次踩坑的真实原因不是工具漏文件，而是检索形态不对** ——
  前者是自己写的脚本抓不到同行收尾形态，后者是读了有并发改动的脏工作树。
  **归因错了。**

## 纪律修订
AGENTS.md §2.3 的「不得用文本检索」**仍然成立且必须保留**（路径以变量拼接出现，
文本检索必然漏）—— 但**理由不是「工具漏文件」**，而是「**文本形态匹配不到调用形态**」。

⇒ **一条工具的可靠性主张，也要先验证再采纳。** 本项目这一轮里，
「恒真门」「恒红门」「无工具链」「零调用者」都出现过同类误判，
**工具的可靠性是被判定的对象，不是默认前提。**
