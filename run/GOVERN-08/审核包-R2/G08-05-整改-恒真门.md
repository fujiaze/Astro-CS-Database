### 2.1 `audit/route2/exp10_truncation_window.py` 循环变量泄漏 —— **已修**

**根因（逐位复现）**：`:68` 在 `for name, fwhm, terms in cases` 循环内写
`_, s2_all, _ = terms(fwhm, BIG)`；循环结束后 `s2_all` **泄漏**为最后一个算例
`moffat2p5_260`（Moffat β=2.5、FWHM=260）的值 `3.3850693062739133e-06`。
`:86` 的 V-7 块直接用这个泄漏值当分母，而分子是 FWHM=3 的高斯 ⇒ **高斯分子除以 Moffat 分母**。

**实测（修复前）**：四个窗口逐位同为 `14484.233240478441`，
与 `code/audit/results/route2/exp10_truncation_window.json` 里落盘的四个值**逐位一致**。

**注入验证**（`/tmp` 副本 + `inspect.getsource` 打活体源码）：

```
[注入A] 泄漏分母下 V-7 读数: {'half36': 14484.23324, 'half60': 14484.23324,
                             'half180': 14484.23324, 'half720': 14484.23324}
[注入A] 与存档 14484.233240 逐位一致: True
[inspect.getsource] 活体源码含自行计算参照量: True
```

**修复**：`:89` 新增 `_, s2_all_ref, _ = gauss_terms(3.0, BIG)`，V-7 用本检查自算的参照量。
修复后读数 **1.0**（四窗口全 1.0），符合 V-7 声称的「half 12→60 FWHM 内 ΣP² 稳定到第 5 位」。

**顺带发现并处置（真判据体检的第二面）**：修好泄漏后 V-7 正例在代数上**必然**为 1.0——
half = 12·FWHM = 28.3σ，尾部比例 `exp(-h²/σ²) = exp(-800)` 在 IEEE-754 双精度下**下溢为 0**。
也就是说**正例永远绿，不构成判据**（规范 08 §4）。故补了一条**负例**：
`v7_negative_control_half0p5fwhm`，窗口缩到 0.5 FWHM = 1.18σ ⇒
实测 `0.7499999999999999`，`deviates_from_unity = True`。
**注入验证**：正例偏差 `0.0` → 绿；负例偏差 `2.500e-01` → 红。判据两侧都能出。

### 2.2 `reverse_verify/frame_snr/run_redlines*.py` fail-open —— **已修（两处）**

**根因**：`run_redlines.py:253-259` 与 `run_redlines_physical.py:431-437` 的
`_out_of_range_negative` 把 JSON 解析失败吞成 `{"ok": False, "parse_error": True}`，
随后 `rejected = (not prod.get("ok"))` 为 **真** ⇒ **一个跑不起来的探针被记成「生产正确拒绝」，
门照样绿**。这就是「吞异常转绿」。

**修复**：只有拿到**可解析且含 `ok` 键的生产判决**才允许记 `rejected`；
探针崩溃／超时／stdout 空／非 JSON ⇒ 该用例记 `rejected=False` +
`probe_inconclusive=True` + 探针退出码 + stderr 尾段，整体 `pass=False`，
并给出可诊断的 `status` 串。**失败即报，不吞。**

**注入验证**（两个文件各跑 4 个场景）：

| 场景 | 旧实现 | 新实现（实测） |
|---|---|---|
| 探针崩溃（`exit 3`，stdout 空） | **pass=True（绿）** | `pass=False`，`probe_inconclusive=[两条]` |
| 探针打印非 JSON（`Segmentation fault`） | **pass=True（绿）** | `pass=False` |
| 生产明确拒绝 `{"ok":false,"rc":1}` | pass=True | `pass=True` ✅ |
| 生产错误接受越界输入 `{"ok":true,…}` | pass=False | `pass=False` ✅ |

新实现既能绿也能红，且**探针死掉时判红**。

⚠ **一处需要前台知悉的更正**：本单派单假设这两处是待修的既有 fail-open。实测**修复前的
代码确实是 fail-open**（`git diff` 可证，见 §8），但一名只读扫描子代理在扫描期间读到了我

### 7.5 扫描过程中发现、需前台知晓的「更正」与「反证」

**(a) 一条扫描结论经本单实测证伪——不要照单修。**
扫描报告称 `reverse_verify/f_instr/f_instr_lib.py:360` 的
`est_psf_optimal` 因 `/var*var` 代数相消而「**根本不是** Naylor/Horne 最优提取」，
并被 4 个实验用于横向排名。**本单实测证伪该结论**：

```
代码写法 num/den/var*var = -0.7872441639860114
docstring Horne 式      = -0.7872441639860089
朴素 num/den            = -0.7872441639860114
```

在方差**空间均匀**的前提下，`(Σ p·d/var)/(Σ p²/var) = (Σ p·d)/(Σ p²)` **数学上就是同一个量**，
差别仅 ~3e-15 的浮点运算序（float 舍入），不是模型错误。
⇒ **该函数确实是 Horne 最优提取，不存在需要修的算法缺陷。**
可提的只有**代码表述**问题：`/var*var` 暗示存在方差加权而实际被约掉，读者易被误导
（`f_instr_lib.py:344` 的 docstring 写的是 `F = sum(p(d-b)/var)/sum(p^2/var)`）。
建议改写成 `num/den` 并注明「var 在分子分母中相消（方差均匀）」，**不要**改成别的算法。
