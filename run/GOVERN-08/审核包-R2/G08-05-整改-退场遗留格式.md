### 1.3 判定：重复产物，不是设计外死路径，也不是设计内依赖

- **不是设计外死路径**：它有活的编解码实现、有被注册的构建目标、有默认关闭但可开启的校验开关。
- **不是设计内依赖**：最高设计与一级正本都已把阶段交换媒介钉死为 HiPS；生产末端实测直写 HiPS。
- **是「可删的重复产物」**：同一产品的 HiPS 面在产、legacy 面同挂但不产。

⚠️ **但要修正一个容易踩的定性：它不是「未编入构建的死代码」。** 子代理复核（我已回查确认）：

- 根 `CMakeLists.txt` 的 `acsd_hips`(STATIC) 目标**无条件**编译这 7 个 `hiss_*.cpp` 与 `aio_healpix_io.cpp`；
- `lib/algorithms/drizzle/CMakeLists.txt:50-56` 又把这 7 个源**二次编入** `acsd_p1_drizzle`(SHARED)；
- 唯一 `add_executable`（`acsd`）链接 `acsd_hips`；`AIO_ENABLE_HEALPIX` 是**无条件编译定义、不是 `option()`**，没有开关可关。

⇒ 准确表述是：**「编进生产链接图、但运行期零引用」**。这决定了退场必须动构建登记，不是纯删文件。

**另有一条干净接缝（利好）**：`lib/infrastructure/aio/src/healpix/aio_healpix_io.cpp`(2201 行) 与 `include/aio_healpix_io.h`(262 行) **全部 24 个导出都是 `aio_hiss_*`/`aio_hcsd_*`，无一个 HiPS 符号**；反之 `aio_hips_reader.cpp` / `aio_hips_writer.cpp` / `aio_upm.cpp` / `aio_hips.h` **零 HISS 引用**。⇒ `.hiss`/`.hcsd` 的 C ABI 面与 HiPS 面**完全分离**，切起来边界是清楚的。

**所以我敢进入第 2 步的依据就是上面三条链的一致结论 + `docs/` 全量分类 C 类（设计内必需）命中数为 0。**
