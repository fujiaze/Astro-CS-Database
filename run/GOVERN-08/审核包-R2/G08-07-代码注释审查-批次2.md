### L1 · P0 · `artifact_abi_v1.c:515-557` · `input_digests` 元素计数恒为 0 → 类恒真门④ + 往返自证

- **原状**（`:515-526` 改前）：
  ```c
  int depth = 0;
  while (r < ae) {
      if (*r == '[') ++depth;
      else if (*r == ']') { if (depth == 0) break; --depth; }
      else if (*r == '{' && depth == 1) ++cnt;
      ++r;
  }
  ```
  元素是**对象** `{...}`，而 `depth` 只由 `[`/`]` 驱动 ⇒ 顶层 `{` 落在 `depth==0` 上，
  `}` 完全未被考虑 ⇒ **`depth == 1` 恒不成立 ⇒ `cnt` 恒为 0**。
- **新状**（`:515-557`）：改为数数组**顶层**元素对象；遇顶层 `{` 计一并整段跳过其内部；遇 `]` 停。
- **依据**：手工逐分支推演（不是猜测）：对任何由「对象元素数组」构成的 `input_digests`，
  `[`/`]` 只可能出现在**元素内部**才会改变 `depth`，而元素内部无嵌套数组 ⇒ `depth ≡ 0`。
- **恢复了什么捕获**：`if (cnt > 0)` 整块（元素解析 + **`artifact_id` 重复拒绝**）永不可达
  ⇒ 血缘（`input_digests`）被**静默丢弃**，且 `lib/include/acsd/contracts/artifact_abi_v1.h:46`
  明写的契约「`input_digests` 内 `artifact_id` 唯一(重复输入拒绝)」在 C 侧**零实现**。
  查询面 `acsd_artifact_query_input_count_v1`（`:612`）恒返回 0。
- **顺带（必须同改，否则等于激活一个潜伏缺陷）**：`:562-585` 的元素边界扫描原本不认识
  JSON 字符串字面量 —— 含 `{` 的 `artifact_id` 会让配平错位、含 `]` 的会让计数提前截断
  （`cnt` 偏小 ⇒ 后面的元素被静默丢弃 = 假绿）。三处扫描已统一为「跳过字符串字面量」，
  复用文件内既有的 `parse_json_string(p, end, NULL)`（`:48`，`out==NULL` 时自行释放）。
- ⚠️ **可达性如实登记**：`acsd_artifact_manifest_parse_v1` 全仓**零调用者**，仅编译进
  `CMakeLists.txt:259` 的 `acsd_runtime` 共享库并按 `SA-IO-07/DATA-06` 全导出。
  ⇒ 这是**已发布 C ABI 合同面**缺陷，不是当前产品主链缺陷。

### L3 · P0 · `fits_verify.py:405-433` · CHECKSUM 三处 fail-open → 类 fail-open（非恒真）

- **原状**：`if len(cval) == 16 and cval != "0" * 16:` 把整个校验块挂在这个条件之下；
  且 `ok = (computed_std == decoded_std or computed_std == 0xFFFFFFFF or computed_std == 0 or computed_fio == decoded_std)`。
- **三处 fail-open**：
  1. 卡值长度 ≠ 16 ⇒ **整块跳过**，函数照常返回成功；
  2. 卡值为全零占位串 ⇒ 跳过；
  3. `computed_std == 0` ⇒ **无条件旁路**，与卡解码值是否一致无关。
- **新状**：三条坏卡口径一律 `raise FitsVerifyError`（`:411-419`）；删掉 `computed_std == 0` 旁路。
- **依据（仓内 C 侧为准，不引外部文献）**：同仓 `fits_core.c:1645-1663` 的
  `acsd_fio_verify_file_v1` 对同三种情形分别是：空卡 → `ACS_FIO_ERR_BAD_HEADER`；
  `>=15 个 '0'`（引号除外）→ `ACS_FIO_ERR_CHECKSUM`，注释逐字写「**全零 CHECKSUM 串是"预留槽未复算"的基准态, 不是交付校验值。verify 必须 fail-closed 拒绝它**」；
  且 `:1690` 明写「M2b-B-09: 不再豁免 `sum==0` —— 全零串已在上方显式拒绝」。
  写侧 `fits_core.c:1474-1478` 在 `write_checksum=0` 时把该卡**抹空**而不是留全零 ⇒ 不存在「合法产物带全零卡」的情形。
  Python 侧与 C 侧**同仓、同一判据族**，此前方向相反。
- **恢复了什么捕获**：更要紧的是它**把记录也弄假** —— `hips_output_store.py:750-751`
  按 `bool(self.verify_checksum and hdr.checksum is not None)` 记账，
  于是「坏卡被静默跳过」会被**如实记成「已做 CHECKSUM 校验」**，进入完成 manifest。
- **纪律**：只收窄不放宽 —— `ok` 的三条通过分支里**没有新增任何一条**。
- ⚠️ **改变可观测行为**：见 §3。

### L4 · P0 · `fits_core.c:690-717` + `:1480-1499` · seek/读失败被压成合法校验和 → 类静默降级

- **原状**：`static unsigned long fio_hdu_checksum_stream(...)`，`if (fio_file_seek(...) != 0) return 0;`，
  循环内 `if (got == 0) break;`（返回**部分**累计值）。调用处 `:1483` 直接
  `unsigned long sum = fio_hdu_checksum_stream(...)` 后 `fio_encode_checksum(sum, 1, cstr)` 落盘。
- **缺陷本质**：**失败与合法值共用一个返回通道**。0 同时是合法的 1 补码和值，
  「半个 HDU 的和」与「和恰为 0」对调用方完全不可分辨。
- **新状**：改签名加 `unsigned long* out_sum, char* err, size_t cap`，返回 1/0；
  seek 失败与读不满都置错误串并返回 0；调用处 `:1489` 改为
  `if (!fio_hdu_checksum_stream(..., &sum, err, cap)) { st = ACS_FIO_ERR_IO; goto fail; }`
  —— **读不到就不写 CHECKSUM 卡**。
- **依据**：同文件姊妹函数 `fio_file_read_datasum`（`:601-608`）早已用 `(size_t)-1` 表示 seek 失败
  并由调用方检查 ⇒ 本次是**把同文件既有约定统一到漏掉的那一个函数上**，不是新发明。
- **恢复了什么捕获**：原状下 seek 失败 ⇒ `sum=0` ⇒ `encode(0, complm)` 编出 `0xFFFFFFFF` 的合法 ASCII 串
  ⇒ 交付物带着**一个从未被计算过的校验值**落盘，且 `verify_before_rename` 若关闭则一路发布成功。

### L9 · 判据类 · `atomic_publish.h:113-134` + `atomic_publish.cpp:456/495/622/650` · `publish_result_consistent()` 是恒等式却被 8 个生产点当红灯门 → 类恒真门③（往返自证）

- **原状**：

  ```cpp
    const bool published = r.durability != PublishDurability::kNotPublished;
    return r.renamed == published;

  ```
  头文件 `:27` 与 `:109-110` 自己就写着「**恒等式**：`renamed == (durability != kNotPublished)`」——
  **命名即承认它是恒等式**。

- **判别依据**：被检验量 = 文件系统上目标是否存在；期望量 = 「rename 返回 0 ⇒ 目标必然在盘上」
  ⇒ **期望量不追回到被检验量自身的输出字段，谓词可假**（这是本批唯一一处把「往返自证」真正修掉的）。
- **为什么不会造出恒红门**：观测点**只放在 rename 已生效之后**。
  早退路径上「目标存在」可能来自**上一次发布**，拿它当判据必然恒红 —— 这是双向体检里必须防的那一类。
  逐一核对四种终态：① fsync 真失败 → `kNotDurable` + 目标在盘 ⇒ `true==true` 绿；
  ② 撤销成功 → `kNotPublished` + 目标不在 ⇒ `false==false` 绿；
  ③ 撤销失败（目标仍在）→ 保持「已发布」+ 目标在 ⇒ 绿（且这正是原代码的意图）；
  ④ rename 失败等早退 → `target_checked=false`，只判内部不变量 ⇒ 绿。
- **恢复了什么捕获**：8 个生产点（`phase1_product.cpp:598/988`、`phase2_integrate.cpp:524/809`、
  `p3_export.cpp:601/622/792/817`，全在 normalize/mosaic/export 三命令的写出主链）
  原先的**红灯永不触发**；现在「rename 报成功但目标不在盘上」「撤销声称成功但目标还在」两类不一致能被看见。

### L10 · 判据类 · `atomic_publish.cpp:135-152` · `fsync_dir` 把 `EINVAL`/`ENOTSUP` 当成功 → 类 fail-open
