# 前台裁决 · Windows 警告处置与生成器口径

## 一、生成器口径 —— 已在 `前台裁决-Windows工具链口径.md` 裁定，不重复
**按 preset 走 VS 17 2022 生成器；不用 Ninja、不用 VS18。**
若该主机只有 VS18 ⇒ 记「工具链漂移」，可跑一次只为暴露警告，
**但不得把 VS18 产物当「双平台全量编译通过」交付**，不得为迁就本机改 preset 或合同。

## 二、`_CRT_SECURE_NO_WARNINGS` 那 332 处 —— **裁定：不逐点整改，收紧作用域**

车道报：该宏用**目录级无条件定义**，等同全项目关掉一类警告，第一方受影响调用点
**332 处**（仓内注释自称 206 处，数字对不上）。项目立场是「该类是平台口径差、
同码在 GCC 侧零告警」。

**裁定**：
- **逐点整改 332 处 —— 否决。** 该类警告在 Windows 上是真实的 API 使用惯例差异，
  逐点整改会产生大量纯形式改写，**行为风险不为零而收益为零**，且与「优化不影响
  数学精度」的要求无关。
- **但「目录级无条件」这个作用域 —— 必须收紧。** 问题的实质不是「关了这类警告」，
  而是**关得没有边界**：它同时覆盖了第一方与第三方、以及目标级门控机制之外的
  全部代码。仓内已有**目标属性级**的门控机制，应复用它，而不是另开一条无边界通道。
- 处置口径：**把该定义从目录级无条件改为按目标受控**，第三方代码保留、第一方
  默认不被该定义覆盖。**具体改法由执行车道按现有门控机制的模式实现。**

⚠️ 一并要求：**修正仓内那处与实测对不上的数字注释**（自称 206，实测 332）。
**注释里的数字与事实不符，本身就是一处需要修的缺陷** —— 本轮治理反复出现
「文档数字与实测不符」，不得因为它在注释里就放过。

## 三、`/W3` 把第一方目标降级 —— **裁定：必须修**
第一方模块动态库在全局 `/W4` 之上又加了 `/W3`，而全局那道 `/W4` 仍在
⇒ 编译器会额外报一条「**用 `/W3` 覆盖 `/W4`**」的警告。
这条警告本身就是**「降级手段本身」的告警**，恰是仓内自己论证要避免的形态。
⇒ **删掉该目标的 `/W3`**，与全局口径对齐。

## 四、目标级整体关闭警告 —— **裁定：降级为「记录并逐目标收窄」**
五个目标带整体关闭开关，其中三个**同时编译大量第一方源文件**（合计约 65 个），
⇒ 这些源文件实际以「零告警」而非严格档编译。
**裁定**：不要求本单全量整改，但要求**逐目标列出「关了哪些、为什么、影响多少第一方源文件」**，
并对**编译第一方源文件却整体关警告**的目标给出收窄方案。**关的理由必须逐目标写清**，
不接受「沿用既有设置」。

## 五、「执行器缺位」不是缺陷 —— 采纳车道的推翻
车道推翻了自己子代理的指控：工作包规范**明文要求治理开始时先物理删除旧门禁与 CI**，
且**规定在双平台编译之后才重建**。⇒ **执行器缺位是计划内时序，不是遗漏。**
（与前台此前的判断相反，车道的推翻成立。）

## 六、车道拒绝盲改 —— 认可
车道在拿到真实 Windows 告警清单前**不动代码**，理由是「改代码＝盲改」。
这与本轮固化的纪律一致：**核实先于断言、取证先于修改**。**认可，不催它先改。**
