# 前台裁决 · acr/ 是否进零告警门

## 事实（前台已核）
`acr/CMakeLists.txt` 是**独立构建项目**：自带 `project()`，**不在根项目的警告接线里**。
其 `:92` 把严格档**追加**到已含构建器默认较松档的旗标串上 ⇒ 会触发
「用较严档覆盖较松档」的覆盖告警 —— **正是根构建文件自己论证要避免的形状**。
另有两处**硬编译错**（非告警）：裸内联汇编、GNU 独有的目标属性语法。

## 裁定：**纳入**

理由：
1. 它在 `lib/` 下，属**生产源码树**。把生产源码排除在「零告警」之外，
   等于留一块**永远不被检查的面积** —— 本轮已经因为「整目标静音」
   造成约 48 个第一方源文件两平台都不被检查，**不能再开第二个这样的洞**。
2. 它自己**已经声明**要用严格档 ⇒ 排除它等于**排除它自己的承诺**。
3. 它的两处硬编译错是**真实缺陷**，不是「若纳入才有」的问题 —— 排除范围**不会让它们消失**。

**但处置时机在编译阶段**，理由：
- 把它拉回根警告口径属**构建体系整改**，需要真实构建做回归；
- 而编译阶段的**前置尚未完成**（规范 08 §1 时序）。

⇒ **本轮只做登记，不动代码。** 登记内容：
- 独立项目、警告档不接入根接线（附行号）；
- 覆盖告警的具体成因；
- 两处硬编译错的位置；
- 处置方向：**把独立项目的警告档改为显式声明而非追加**，并补 Windows 分支。

⚠️ 另记一条纪律：**排除范围不能用来消除真实缺陷。** 「若不纳入则不阻塞」
是把范围问题当成了缺陷不存在。
