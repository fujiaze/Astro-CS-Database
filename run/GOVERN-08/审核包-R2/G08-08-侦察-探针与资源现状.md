## 1. 结论先行：负责人的探针印象是否成立

### 判定：**成立**（且成立程度高于「有个开关」的最低预期）

负责人的原话是「性能优化什么的我印象里程序里埋了可开关的探针，根据探针提高CPU利用率，设计尽可能高效占满CPU和内存的调度器等等」。拆成三段分别核实：

| 负责人的断言 | 判定 | 依据 |
|---|---|---|
| 程序里埋了**可开关**的探针 | **成立，且是双层开关** | 编译期 CMake option + 运行期环境变量，见 §2 清单 A/B/C/E/F/I |
| 根据探针提高 CPU 利用率 | **部分成立** | 探针能测，但**测完不回灌**：负责资源选型的 `worker_advisor` 只有测试调用方，生产无调用点（§6 事实错误 F-01） |
| 设计尽可能高效**占满 CPU 和内存**的调度器 | **部分成立** | CPU 侧有预算源、内存侧有回压与滞回治理且推导带实测；但「占满」的调优闭环缺失，编排参数是**配置驱动**而非**探针驱动**（§3） |

### 为什么说「成立」而不是「部分成立」

本仓的探针不是设计文档里的设想，而是**已接线、已埋点、已接产物**的三层体系：

1. **观测层**（in-process，毫秒级）：`acsd::probe` 框架，编译期关掉时链接产物中不存在任何 `acsd::probe::*` 符号（`probe.h:13-14`），且生产代码已真实埋点约 50 处、落在逐帧/逐块热循环内。
2. **画像层**（离线，`acsd benchmark` 子命令）：kernel 级测量数值误差、吞吐、线程扩展、内存带宽四类量，产出 `cpu_profile.json`，落安装目录、运行期自动读取。
3. **伴随层**（Python sidecar）：与 run 同 ID 每秒采集系统利用率，原始 CSV 带指纹链防伪造。

这三层合起来，正好对应负责人「埋了可开关的探针 → 据此提高利用率」的前半句。

### 但「据此」这一环断了

规范 07 §3 写「调度器据画像选取指令集库**与编排参数**」，规范 07 §4 写「编排参数（窗口大小、预取深度、帧并发、工作窃取）由性能探针实测迭代，不使用固定经验值」。

实测：ISA 选取这一半**已闭环**（`cli_select_backend` 在生产三命令共同路径上被调用）；编排参数这一半**未闭环**——画像里逐 kernel×workers×block 的实测行（`acsd.cpu-profile/v2`）确实存在，但把它翻译成调度参数的 `worker_advisor` 全仓只有 `eng/tests/unit/cpu008_worker_advisor_test.cpp` 一个调用方。

> 一句话给负责人：**探针埋得很好、也确实在用；缺的是「探针结果 → 编排参数」这一段接线，而这恰好是您说的「占满 CPU 和内存」最值钱的部分。** 该做的不是造新探针，而是把已经写好的 `worker_advisor` 接进生产（见 §7 施工单 A-1）。

## 3. 编排参数现状表

唯一数值源：`eng/packaging/config/runtime_resources.json`，经 CMake `configure_file` 生成头 `runtime_resources_generated.h`，实现侧零字面量。

| `frame_memory_gate.bytes_per_pixel` | `116.0` | 配置键 | **是**——authority 标注 PERF-P1 标定，来源 `run/P1-CONCURRENCY-CALIB-01` |

### 关键判定：编排参数是「配置驱动 + 推导留痕」，**不是「探针驱动」**

- 好的一面：几乎每个键都带 `*_constraint` 或 `*_derivation` 字段，写明取值依据与适用域；`memory_pressure_derivation_scope` 甚至显式声明「帧几何、精度模式、nside 或 scratch 池上限变更 ⇒ 边际 1.6724 GB 失效 ⇒ high/low 必须重测重推」。这是本仓文档纪律的正面样板。
- 缺的一面：`p1_max_frames_in_flight` 的 constraint 引 `docs/ACSD_DESIGN.md §8.3:652`「编排参数…基于探针实测数据迭代，不靠静态猜测」，但**当前取值是 `0` = 交给 lease 与内存闸门**，并没有任何「探针实测迭代」的回路把 `cpu_profile` 里的 workers/block 喂进来。`worker_advisor` 就是为这件事写的，但没接线（§6 F-01）。
- 「工作窃取」三项在三处一致声明未实现，且**是诚实的 gap 登记而非隐藏**：
  - `eng/packaging/config/runtime_resources.json:65` → `"work_steal_policy": "gap:未落地（…生产无实现，不落死键）"`
  - `eng/packaging/config/config_registry.json:2702-2707` → reason：「全仓 grep：生产侧零 work-steal 实现（唯一命中 = `lib/infrastructure/acr/**`，而 ACR 生产不可达）；P1 帧轴现用原子认领（`p1_parallel_for`），无窃取路径」
  - `docs/engineering/execution_options_contract.md:152` → 「生产不实现工作窃取；相关键位在实现前不进入配置面」

## 4. 资源自适应现状

### 4.1 CPU 预算：三层来源，无写死

| 层 | 机制 | 位置 |

### 4.3 内存上限：按比例，且真的读 cgroup

- 口径：`预算 = 当前可用内存 × memory_budget_percent/100`，默认 95（`runtime_resources.json`）
- 可用内存探测：Linux = `/proc/meminfo` 的 **MemAvailable**（含可回收 page cache，不是 MemFree）∩ cgroup 内存余量（v2 `memory.max - memory.current`；v1 `memory.limit_in_bytes - memory.usage_in_bytes`）；Windows = `GlobalMemoryStatusEx.ullAvailPhys`；返回 0 = 不可判定 ⇒ fail-closed（`runtime_resources.json` `available_memory_probe` 字段）
- profile 覆盖：运行期可由 `acsd.cpu-profile/v2` 的 `host.memory_budget_percent` 覆盖，非法值回落默认（`commands.cpp:132-155`）
- 定位澄清：内存**不设门**（资源门只管磁盘，`docs/ACSD_DESIGN.md §4.5`），预算只作调度准入输入，不产生退出码（`runtime_resources.json` `enforcement.not_a_gate = true`）
- 治理：压力高时「可中断排队」→ 持续高压才「可丢弃重跑」，滞回带 [75, 90)，且有 run 级 JSONL 台账（只增不改，不参与判据）

⇒ 规范 07 §4「不写死…内存上限」「内存上限可用百分比表达」**均成立**。

### 4.4 并行轴分配：帧轴 × 帧内轴，预算唯一

- 不变式：两轴之积 ≤ 预算（`cpu_budget.h:4-5`）

### F-02 【阻断】Windows Job Object 恒为 null —— 规范 07 §4 的四个来源少一个

- **文档说**：规范 07 §4「worker 数与并行宽度由运行环境自动获取（可用核、亲和性、cgroup、**Job Object**）结合 config 决定」

- **文档说**：规范 07 §4「一个资源预算源统一调度，模块不私建线程池」；`AGENTS.md` §6「模块不读全局配置、不私建线程池」；`docs/engineering/CONCURRENCY_STANDARD.md:32`「科学计算路径…只用显式并行区（OpenMP / 线程池）；**不用 `async` / `future` / promise 链，不嵌套并行**」

- **注意嵌套并行风险**：`module_adapters.cpp:2099` 的帧轴 `std::thread` 池内部，`omp_set_num_threads(inner_omp)`（:2104）注入帧内宽度——这正是文档说的「并行轴分配」正确形态（有显式收窄，非裸嵌套），故此处**不判为嵌套并行违规**，只判为「私建池」
