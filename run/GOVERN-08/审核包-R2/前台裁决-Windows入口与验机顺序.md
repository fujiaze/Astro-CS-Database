# 前台裁决 · Windows 入口缺陷与验机顺序

## 一、入口缺陷：**成立，且它比所有告警都更早决定成败**

前台**独立复核属实**：
- 入口源文件在 `_WIN32` 分支下**只定义宽字符入口**，窄字符入口在 `#else` 里；
- 受跟踪的构建文件与源码中，**宽字符宏定义命中数为 0**；
- 该可执行目标**未按窗口子系统构建** ⇒ MSVC 取默认启动例程去找**窄字符入口**，
  而 Windows 侧**没有**窄字符入口 ⇒ **链接期失败**。

⇒ **这不是「一条告警」，是「Windows 侧连链接都过不去」。** 任何以「零告警」为
验收口径的讨论在它面前都是空的。

**裁定**：
1. 该缺陷**在拿到真实构建证据前不得盲改**（改错会让 Linux 侧入口回归）；
   机器恢复后**第一件事就是单独构建该可执行目标验证它**。
2. **验收顺序据此调整**（见第三节）—— 入口先于告警。
3. 车道先前把入口判为「通过」，**自行发现并公开更正**。**这个更正动作是对的**，
   且应作为本轮纪律的正面例证记下：**已经写进交付件的结论，发现错了要公开推翻，
   不要让它留在文件里等人踩。**

## 二、头号结构问题：约 48 个第一方源文件在两个平台上都没有被告警检查
静音开关设在**整目标**档位，而三个目标把第一方源与内嵌第三方混在同一个构建单元里
⇒ 第一方源既被静音、又不在 Linux 侧严格旗标列表内。
⚠️ **这直接违反仓内自己的标准**（该标准逐字禁止用整目标或全局降级掩盖本项目源码告警）。
⇒ 即使严格档全绿，**也证明不了这批源文件干净**。

**裁定**（补车道建议）：
- 本轮**只做静态取证与方案**（把内嵌第三方抽成独立编译单元，一步同时修好隔离与
  重复编译），**不做大改** —— 大改需要真实构建做回归。
- **但**「第一方源文件不得处于整目标静音档」这条要写进交付件与后续门禁设计，
  否则修完没人再查。

## 三、验机顺序（**车道建议，前台采纳**）
1. 先查本机装了哪些生成器/工具集 —— 前台探测时该目录下**「18」与「2022」两个条目
   同时存在** ⇒ 若旧版在，四项版本差自然消失，可直接走合同路径，无需记为漂移。
2. **单独构建主可执行目标，验入口**（比任何告警都更早决定成败）。
3. 喂压缩库根路径变量 —— preset 不含它，且某模块的依赖查找**无平台分支保护**、
   注册更早 ⇒ 缺它会先死在别的模块。
4. 才进入告警面。

## 四、车道查出一条「零告警反而掩盖问题」的典型，写入本轮检查项
一处兼容层把上游索要的「**递归**互斥」**静默降级成非递归自旋锁** —— 直接丢弃参数、
而设置类型的调用**仍返回成功**。
⇒ **重入即自死锁烧满一核，而它不产生任何严格档告警。**

⚠️ 这证明**只靠告警收敛不可能达到「编译干净」** —— 告警只覆盖编译器看得见的。
**本轮固化一条新检查项：静默降级与自降级，即使零告警也必须显式排查。**

## 五、两处实操陷阱（车道查出，前台采纳）
- 忽略规则里的 `build/` **未锚定**，连带屏蔽了别处的同名目录 ⇒ 默认检索
  **会静默跳过整个 Windows 构建入口**。复核本轮结论必须用「不尊重忽略」的检索。
- 一个仍指向**已不存在目录**的 Linux 构建脚本 ⇒ 任何「照该脚本复现」的建议都会失败。
  **不影响 Windows 结论**（Windows 走 preset，不经此脚本），但该脚本本身是死指针。
