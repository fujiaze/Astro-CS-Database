### 1.3 最简正确顺序，以及它为什么能防住中途失败

**最简正确顺序（就这四步，不可再简）**：

1. 词法预检 + 存在性判定（只读，不改盘面）；
2. **全部暂存成功**（写 → fsync → fitsverify → sha256）——所有会失败的昂贵动作都在这里；
3. **一次性原子让位**：成功对象用一次 rename 挪到 `.replaced-*`，残渣直接删（残渣本就不可消费，删它不丢正产物）；
4. 换入 + 落 COMPLETE manifest；失败则把让位副本搬回；成功才回收让位副本。

**为什么这个顺序防得住中途失败**：

- 第 2 步失败 ⇒ **第 3 步根本没执行**，目标目录一个字节都没动过。这是修复的核心：把"会失败的东西"全部放在"动旧东西"之前。
- 第 3 步失败 ⇒ rename 是原子的，要么整体搬走要么没搬；`_retire_success_target` 额外校验 `backup.exists() and not target.exists()`，不成立就搬回去并抛错。目标要么是完整的旧产品、要么是完整的让位副本，**不存在"半旧"**。
- 第 4 步失败 ⇒ 目标区被半写，但**没有 COMPLETE manifest**，消费者（`has_complete_manifest`）一律拒绝；随后 `_restore_retired` 先撤掉半写目标区再把让位副本搬回 ⇒ 旧产品原样恢复。
- 回滚本身失败（唯一真正丢数据的极端）⇒ 不删让位副本，抛出的 `PublishError` 里**逐字给出副本路径**供人工恢复。按负责人"不得静默丢数据"，这是唯一诚实的出口。

### 1.6 一个必须登记的遗留风险（不自行扩大写面）

`_discard_retired` 在回滚成功后回收让位副本时用的是 `remove_tree`；若此刻进程被杀，
`products/` 下会留一个 `.replaced-*`。它不会被索引（点前缀），但会占盘。

**这不影响数据正确性**（旧产物已在目标位，新产物已带 COMPLETE manifest），仅是占盘残留，
登记为后续可清项，本单不扩写面去动 `cleanup()` 语义。

## 2.【转述过头；部分成立】读回校验读的也是同一页缓存

### 2.0 先说对抗性复核的结果（这一条改变了我的结论）

我先按转述去找"被注释成落盘证明的读回"，没找到；随后派了一轮**独立对抗扫描**
专门找这个形态，写明三要素：①写入后从同一路径读回；②注释/自述声称落盘；
③该数据路径无 fsync。四路独立扫描（含 aio 树、algorithms 树、
scheduler/phase/pipeline/observability/acr/benchmark 树，以及自写结构化脚本）
**一致结论：这个形态在本仓不存在**。

这个"不存在"是**结构性的**，不是抽样没撞上：主产品路径
`lib/infrastructure/aio/product_io/src/atomic_publish.cpp` 的次序是
`::fsync(fd)` `:400` → `rename` `:434` → **`confirm_dir_durability()` `:447` 决定
kDurable/kNotDurable** → `verify(target)` `:465`
—— **落盘由一个不同的机制、在读回之前就判定了**，所以那条路径按构造就容不下这个缺陷。
`atomic_publish.cpp:146-147` 的注释逐字就是这么写的："返回 true 仅当『目录 fsync 已执行且成功』
—— 这是 kDurable 的**唯一证据**"。

所以转述里"某个实现把读回校验当成落盘证明"这句**不成立**。我把自己的初判也一并降级：
初稿写的是"读回校验读的也是同一页缓存（成立）"，那是**我自己从转述推出来的、而不是我核实出来的**，
按负责人口径"判据不可信、不必核实为通过"，我把它记为误判。

### 2.1 实际成立的、较窄的两件事（我核实过，逐字）

**(a) 一处措辞过宽的自述。** `hips_output_store.py` 的 `verify_tree_hash` 改前逐字：

```python
        """tree hash 可重算验收：按磁盘当前文件重算 == manifest.tree_hash。"""
```

"按**磁盘**当前文件重算"里的"磁盘"经不起推敲 —— 它读的是文件系统视图，命中的是写方
自己刚写进页缓存的同一份数据。这不是"假落盘证明"，是**一个函数自述把话说满了**。
本单把这句收紧（§2.5），并补上"能证明 / 不能证明"两段。

**(b) 一个真实但更窄的缺口：这个模块没有持久化三态，且目录 fsync 失败不留痕。**
`hips_output_store.py` 的 `_fsync_dir`（`:190-198`）对任何 `OSError` 一律 `pass`。
所以**目录项**的 fsync 真失败时，模块内没有任何状态/返回码/日志能反映它。
注意模块对**文件数据**是真 fsync 的（`StoreIO.write_bytes` 内 `os.fsync(fd)`），
所以准确说法不是"缺少落盘同步"，而是"**目录项**的落盘同步缺失且失败不可观测"。
按"不得静默降级"，这本身就该登记。

### 2.2 那个验证到底能证明什么、不能证明什么

对象：`hips_output_store.py` 的 `verify_tree_hash`（`:823`）与 `read_product_file`（`:793`）。
它对每个 manifest 登记项 `sha256_file(p)` 重算再比 `tree_hash`（或逐项比对登记的 sha256）。

**能证明**：

- 该产品当前**有** COMPLETE manifest（在"可消费"意义上是成功对象）；
- 此刻按路径读到的字节，其 sha256 与 manifest 登记值一致 ⇒ **事后篡改可检出**，
  且树内容与清单自洽（没有文件缺失）。

**不能证明**：

- **不能证明数据或目录项已落盘。** 读回命中的是写方自己刚写进页缓存的同一份数据。
  缺失的文件 fsync（在本模块里不存在）或目录 fsync，在这个函数里**结构上无法被发现** ——
  不是"没测"，是"原理上测不到"。
- **不能证明 rename 之后目录项已持久化。** 这是本模块的真实缺口：`_fsync_dir` 静默吞错。
- 通过 ⇒ 只能说"文件系统视图里内容对得上"，**推不出**"掉电后还在"。

再强调一次边界：这两条讲的是**这个 Python 模块**，不是全仓。
按 §2.0，`atomic_publish` 那条产品路径有独立的、由 `confirm_dir_durability` 判定的落盘证据，
不存在这个问题。

### 2.3 复用仓内已有的真正落盘口径（不自造）——并附一个我核实到的口径自身缺口

仓内**已有**权威口径，我没有另造：

- `lib/infrastructure/aio/product_io/include/astro/aio/atomic_publish.h:19-31` ——
  `PublishDurability` 三态（`kDurable` / `kNotDurable` / `kNotPublished`），
  判据 = **rename 已生效 + 目录 fsync 成功**；并明写"不得回滚删除、不得静默当成功、须显式可见"。
  消费面接线见 `lib/phase3_session/p3_export.cpp:424-461`（`note_publish_durability`）。
- `atomic_publish.cpp:146-147` —— "返回 true 仅当『目录 fsync 已执行且成功』——这是 kDurable
  的**唯一证据**"。
- 次序参照：`fsync(fd)` `:400` → `rename` `:434` → `confirm_dir_durability()` `:447`
  → `verify(target)` `:465`。**先定落盘，再读回** —— 这正是本模块缺的那一层的正确次序。

**⚠️ 我核实到的口径自身缺口（我亲自逐字读过，见 §7.3 第 6 条）**：
`atomic_publish.cpp:138` 逐字是

```cpp
  if (rc != 0 && saved != EINVAL && saved != ENOTSUP) {
    if (err) *err = std::string("fsync dir failed: ") + std::strerror(saved);
    return false;
  }
  return true;
```

即：`fsync(dirfd)` 返回非 0 且 errno 为 `EINVAL`/`ENOTSUP` 时，**落到 `return true`**。
在目录 fsync 真的不支持（返回 EINVAL/ENOTSUP）的 POSIX 文件系统上，
`confirm_dir_durability` 会返回 true ⇒ 上报 `kDurable`，**而没有任何持久化证据**。
这与同一文件 `:159` 明写的原则（"不得把『无失败证据』当成『已确认落盘』"）**自相矛盾**。
Windows 那一侧 `:160` 是正确处理（恒返回 false）。
所以我写进注释的"复用该口径"这句，必须带上这个尾巴 —— **该口径自己在 POSIX 侧有一个洞**。
我没有去改它（不在本单点名的写入面内，且属另一车道）。

### 2.4 如实登记的缺口（不冒充、不自造"更强的验证"）

`hips_output_store.py` **未接入**上述持久化三态：它没有 `kDurable/kNotDurable`，
`publish_directory` 返回的 manifest 里没有任何 durability 字段，
`_fsync_dir` 的静默吞错使得目录 fsync 失败在模块内完全不可见。

**本单的处理**：只把边界写进注释/自述（模块 docstring 新增第 8 条"落盘口径（本条是边界声明，
