# 前台记录 · 工程结构现状对「重新梳理」这一决策的含义

负责人裁定「三重新梳理工程结构」。现状调查车道中期报出若干条**与本决策直接相关**
的事实，前台已逐条独立复核。**此件不是建议，是把「要梳理什么」落成可议的清单。**

## 一、仓库存在**三处自相矛盾的自订契约**

根构建文件第 3–4 行**逐字自称**：「本文件是仓库**唯一 project()** 与唯一产品事实源」。
而实测：

| 自订契约 | 实测 | 性质 |
|---|---|---|
| 唯一 `project()` | **另有两处**（界面模块、覆盖图模块）各声明一个，其中一个还声明了可执行目标 | **违反自订契约** |
| 目录为空（某模块 `PENDING.md` 逐字写「本目录为空，未含任何实现」） | 该目录**38 个受控文件、28 个源文件、近万行**（一个完整图形界面） | **文档与事实相反** |
| 注释里的行锚 | 三处漂移（自指位置错一位、引用的子构建文件**在当前树不存在**） | AGENTS §2.3 点名的失效形态 |

⚠️ 第一条的含义：**「根是唯一事实源」这条契约本身已经不成立**。
后续任何「以根构建为准」的判断都建立在一条假前提上 —— **这必须在梳理的第一步解决**，
否则后面每一步都在错误的地基上。

## 二、「目录存在但不在构建图」不止一处
全仓的子目录引入**只出现在根构建文件的 16 处**。实测有**五个目录自带构建文件却不在图里**，
其中两个是**生产源码所在**（覆盖图、噪声信噪比）。两个界面/工具模块亦不在图内。

⚠️ 含义：**「有没有被构建」与「目录里有没有代码」是两个独立事实。**
本项目已多次把两者混为一谈（那批「测试目录」里其实有正向代码）。
梳理时**必须逐目录给出这两个事实的组合**，不能只报一个。

## 三、**三个模块目录只有合同、零源码** —— 而这是**既定安排**，不是意外
三个模块目录只有说明与合同文件，**源码文件数为零**；真实源码在另一个目录里、
编进同一个库。合同文件**自己写明了原因与迁移目标**，且目标库尚不存在。

⚠️ 含义：**这是模块化前夜的正常状态，不能当缺陷「修掉」。**
梳理时须把它列为**已登记的迁移计划**，并核对那个目标库是否该建。

## 四、设计顶点点名的一个目录**在磁盘上不存在**
设计文档里点名的一个基础设施目录，实测**不存在**；而构建目录里那个同名路径
**只是陈旧的构建产物**（本项目已多次把陈旧产物当证据）。

⚠️ 含义：**陈旧构建产物会伪造出「某目录存在」的假象。**
判「某目录是否存在」必须以**受跟踪文件集**为准，不看构建目录。

## 五、命名违反设计顶点的明文约束
设计顶点**明文写**某类命名不得出现在命令与算法目录中；实测**算法目录下有两个**
该类命名的目录，另有若干同前缀包装层。

⚠️ 含义：这是**设计与实现的正面冲突**，按权威链应以设计为准 ——
但**改命名是破坏性动作**（涉及构建、注册、文档三面），须与「模块化迁移计划」一起排序。

## 六、口径（受跟踪文件为准）
```
lib     915 文件 / 601 源 / 401,960 行   ← 其中内嵌第三方 193,294 行，占 48%
eng     304 / 4 / 291
实验     724 / 29 / 5,712
docs    187 / 0 / 0
```
⚠️ **`lib/` 的一半行数是内嵌第三方**，任何按行数做的结构判断都严重失真。

## 前台的处置立场
- **一～三**是**仓库与自身契约的矛盾**，属本项目内部债务，**不需负责人裁决**，
  按文档纪律「代码与文档冲突时以文档为准」逐条订正即可；
- **四**是设计顶点点名了不存在的东西 —— **要改设计顶点**，须负责人点头；
- **五**是命名冲突 —— 属设计层面的决定，**须负责人裁决**（改不改、何时改）；
- **六**是既定迁移计划 —— 登记并核对，**不擅自推进**。
