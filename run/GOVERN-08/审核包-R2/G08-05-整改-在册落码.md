### 2.1 `tools-003-B1` · `eng/tools/arch/cmake_graph.py` — 一行换一片捕获

| | |
|---|---|
| **台账原判据** | `:104` `gc` 未 import，6 处守卫全抛 `NameError`，「判据从未运行过」 |
| **新处置** | 本模块自持 `class GateError(Exception)`（`:20`），6 处 `raise gc.GateError(...)` → `raise GateError(...)` |
| **落码位置** | `cmake_graph.py:20-30`（定义）、`:118`、`:303`、`:314`、`:333`、`:337`、`:429`；`gen_build_graph_doc.py:101-111`（调用方接线） |

**为什么台账判定要纠正一半（重要，直接影响修法）**

台账隐含的修法是「补 `import gc`」。**那是错的**：`gc` 是 Python 标准库垃圾回收器，**不含 `GateError`**；
全仓 `grep "class GateError"` **零命中**，`GateError` 从未被定义过。补 `import gc` 后仍是 `AttributeError`。

**我回仓实测出的真实缺陷形态**（比台账窄，但不轻）：

`raise gc.GateError(...)` 会先求值 `gc.GateError` → `NameError`。`NameError` **也是异常，照抛不误**
⇒ 这 6 处守卫**不是**恒真门，也**没有** fail-open。真正的损失是两条：

1. **稳定错误码全部丢失**：`ANCHOR_MISSING` / `ANCHOR_STALE`（×2） / `ANCHOR_EMPTY` /
   `ENTRY_REGISTRY_EMPTY` / `ENTRY_REGISTRY_AMBIGUOUS` 一个都到不了调用方，只剩
   `NameError: name 'gc' is not defined`；
2. **异常类型不可甄别**：调用方无法区分「构建图确实不合格（合法拒绝）」与「这个工具有 bug」。

**恢复的捕获**：稳定错误码 + 可按类型捕获的异常身份。调用方 `gen_build_graph_doc.py:110`
以 `except mod.GateError → raise SystemExit(str(exc))` 把错误码送到退出面 —— 该文件其余 5 处
拒绝（`:112/:120/:132/:139`）本来就是 `SystemExit("ANCHOR_*")`，此前这 6 处是**唯一一组到不了退出面**的，
口径现已统一。

**判别依据（非同源）**：错误码是 `GateError` 的**载荷**，由守卫点按真实状态构造，
不经过「把产生该量的定义式重写一遍再与它自己比较」。

### 2.5 `BL-N02` · `lib/infrastructure/aio/io/hips_output_store.py` — 甲类生产缺陷（主因判定有误，残留已落码）

| | |
|---|---|
| **台账原判据** | `:589` 写死 `"performed": True, "checksum": "datasum"`，而 `:372 verify_checksum` 默认关闭 ⇒ 恒定谎报 |
| **判定纠正** | 台账把 **DATASUM 与 CHECKSUM 混为一谈**，`"checksum": "datasum"` 是**准确的** |
| **落码位置** | `:537-543`（记录真实校验事实）、`:600-623`（manifest 由事实导出）、`:727-751`（`_verify_fits` 返回事实） |

**台账主因错在哪（实测）**：`fits_verify.py:371-382` 的 DATASUM 校验
**完全不受 `verify_checksum` 开关约束** —— `if h.datasum is not None:` 无条件执行，
双通道（标准 32-bit 折叠 / IO-001 writer 16-bit 折叠）任一匹配即通过。
`verify_checksum` 只在 `:384` 门控 **CHECKSUM 卡**（整 HDU 1 补码），与 DATASUM 是两件事
（`fits_verify.py:16` 的步骤表逐字区分）。故「默认关闭 ⇒ 谎报 datasum」**不成立**。

**但残留缺陷是真的，且台账没说到**：完成 manifest 的 `tile_count`
用 `sum(1 for r in staged if r["fits"])`，而 `r["fits"]` 的判据是 `fn.endswith(".fits")`（`:542`）——
**`Moc.fits` 也是 `.fits` 后缀，却被 `:538` 的分支显式排除、从未校验**（BINTABLE，IO-001 支持域外）。
⇒ **未校验的 `Moc.fits` 被计成「已校验 tile 数」。** 这才是甲类生产缺陷（标识失败产出貌似正常值）。

**落码**：`_verify_fits` 改为返回**实际做了什么**的事实
（`{"datasum": 该文件带 DATASUM 卡且已过该卡校验, "checksum": 这次真的做了 CHECKSUM 校验}`），
`staged` 每项带 `fitsverify`（`None` = 没验），manifest 三项全部由这些记录导出：

- `performed` ← `bool(已验 tile 存在)`（不再写死 `True`）
- `tile_count` ← `len(已验 tile)`（**`Moc.fits` 不再被计入**）
- `checksum` ← 仅当每个已验 tile 都带并通过 DATASUM 卡才记 `"datasum"`，否则如实记 `"none"`

**判别依据（非同源）**：期望量取自 `_verify_fits` 返回的**校验器自身输出字段**
（`verify_fits_bytes` 返回的 `_Header.datasum`），不是把 manifest 的定义式重写一遍与它自己比较。
`_Header.datasum` 是校验器的输出，不是 manifest 的输出。

**未越界**：manifest schema 三字段**未增未删**，与 `docs/engineering/io/IO_003_ATOMIC_OUTPUT_PUBLISH.md:188`
的登记形态完全一致；全仓 `grep "performed"` / `"tile_count"` **无任何代码读者**（仅文档引用），改动面封闭。
