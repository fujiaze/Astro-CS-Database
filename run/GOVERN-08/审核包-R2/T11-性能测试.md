### 3.2 「真的并行了」逐段验证（不只看总时长变短）

⚠️ 派单点名：**本项目历史上有「在飞帧数上限被写成编译期常量导致该段代码永不执行」**。
本单正面核这一条，结论与字面印象**不同**，必须分三层：

**第 1 层：租约层 —— 真并行。** 15 个节点全部
`[lease] … host_workers=16 acquired=1 cap=16 budget_available=0`（normalize 8 + mosaic 7）。
**无一节点降级到单线程**，并行预算确实发到了。

**第 2 层：帧级层 —— 真并行。** `[p1cap] frame_workers` 观测
`lease=16 memory_cap=77..87 frame_workers=16` ⇒ `min(16, 87) = 16`，帧轴未被内存闸门压低。

**第 3 层：帧内轴 —— 满宽（这里纠正了一个被误读的量）。**
`[p1cap] parallel_for` 六行**全部**为
`lease=16 memory_cap=0 frame_workers=16 **n_units=4 inner_omp=4**`。

按实现公式逐项复算（`lib/infrastructure/scheduler/src/module_adapters.cpp:1990-1995`、`:2365`）：
```
in_flight = min(n, frame_w) = min(4, 16) = 4
inner_u   = max(1, budget / in_flight) = max(1, 16/4) = 4
K         = min(num_threads, kScratchPoolCap) = 4   (drizzle_engine.cpp:1663，缺省 cap = num_threads)
W_eff     = in_flight × min(inner_u, K) = 4 × min(4, 4) = 16 = lease   ← 满宽
```
⚠️ **必须写明纠错**：第一版测量报告把 `inner_omp=4` 读成「帧内宽度被钉在 4 的上限」。
**错**。它是**分配的结果**，不是约束；总并行度 **4 × 4 = 16 = lease**，**已满宽**。
判满宽的充要条件是 `in_flight × inner_omp = lease`，这里 16 = 16。
**「`in_flight` 只有 4」的真正成因是 `n = 4`（帧数），不是任何上限。**

**并行轴旋钮可控性已被独立证实（方法有效性）**：同一二进制、同一数据，只设
`ACSD_P1_AXIS_FRAME_WORKERS=8` + `_INNER_OMP=2`（8×2=16，未越 lease），六个
`parallel_for` 观测点全部从 `frame_workers=16 inner_omp=4` 变为 `frame_workers=8 inner_omp=2`
⇒ **「逐段验证并行」这个方法本身在不触碰产品代码的前提下有效**。
⚠️ 该 A/B 的墙钟差异**不可归因**（同时 `memory_cap` 从 ~85 掉到 ~50，分批大小混杂），如实登记。

### 3.3 那段「永不执行」的代码：本单的当代形态

`module_adapters.cpp:1965-1984` 的帧并发度上限块：

```cpp
std::uint32_t frame_cap = acsd::runtime_resources::kP1MaxFramesInFlight;   // :1975
const std::uint32_t cap_env = p1_axis_env_u32("ACSD_P1_MAX_FRAMES_IN_FLIGHT"); // :1976
if (cap_env > 0u) frame_cap = cap_env;                                    // :1977
if (frame_cap > 0u && frame_cap < frame_w) { frame_w = frame_cap; }      // :1978-1983
```
`kP1MaxFramesInFlight` 是 configure 期固化的 inline constexpr（值 **0**）⇒ 不设 env 时
`frame_cap ≡ 0` ⇒ **收紧分支不生效**（实测三轮 `[p1axis]` 行数均为 **0**）。

⚠️ **两处表述必须分清**（本单实测裁定）：
1. **它在 HEAD 上不是「不可达」**：`1ef0849c` 起 `:1976-1977` 已有运行期通路。
   准确表述是「**默认部署下不生效**」，不是「不可达」。
2. **它不是宽度来源，是收紧机制**：`frame_w` 真正来自 `:1959` `frame_w = workers`，
   而 `workers = p1_frame_workers(doc) = min(lease, mem_cap)`（`:2365`）；
   `:1978` 只在 `cap < frame_w` 时收紧，**结构上不可能放大**。
   ⇒ **cap = 0 不会让并行塌成 1**；本轮 `in_flight = 4` 的成因是 **n = 4**。
   实测反证：`memory_cap = 87 ≫ lease = 16 ⇒ frame_workers = 16`，四帧全在飞。

⇒ **真正「写好但默认不生效」的是"收紧旋钮"（帧并发度上限），不是"并行代码"本身。**
6 个带池节点全部实测走到了 `p1_parallel_for`，没有任何并行代码不可达。

|---|---|---|---|---|
| normalize | **0** | 21.0% | **4** | **96.8%** |
| mosaic | **0** | 14.9% | **1** | 87.8% |

⇒ **不是 CPU 饥饿**（`runnable_p50 = 0`，就绪线程为 0，没有线程在排队等 CPU），

**（c）决定性一刀：drizzle 节点内部时间构成**

⚠️ 这**推翻了「热点在 drizzle 算法」的直觉**：热点在**写路径**。

**（d）per-file 往返是机制之一，但不是唯一**

| 阶段 | `syscr`（读系统调用） | `syscw`（写系统调用） | `read_bytes` | `write_bytes` |
|---|---|---|---|---|
| normalize | 198,149 | 28,318 | 185.8 MiB | 216.6 MiB |
| mosaic | **287,019** | 35,690 | 1185.6 MiB | 1081.6 MiB |
| export | 186,368 | 46,948 | 40.2 MiB | 27.4 MiB |

`[aio_sparse] trim=punched` 事件 **normalize 812 次 / mosaic 272 次**
（⚠️ 纠错：第一版报告写 612 次，是**转写错误**；本人已直接核 A 轮原始日志
`grep -c "trim=punched"` = **812 / 272**，与轮 D HEAD 实测逐位相同）。

per-file 不是唯一机制。

**（e）可证伪表述 H（供后续单验证）**：「drizzle 节点墙钟由 per-file I/O 往返决定，与并行宽度无关」。

### 5.3 ⚠️ 一个指标恒为常数（任务书点名的历史坑，本单命中）

`PERFORMANCE_MODEL.md` 的 worker_balance 指标**正确算法**要求
`utilization_pct = 100 × mean_over_windows(busy_workers/n_workers)`，
并**明文**：「『0.5 × 100』式常量与『(min+max)/2』式恒值算法**一律判红**」。

**实测该指标恒为 50.00**：
- 实现 `lib/infrastructure/cli/resource_recorder.h:368-369`：`denom = active + runnable`；`util = active×100/denom`。
- 两列同源：`lib/infrastructure/cli/commands.cpp:950` `set_workers(planned_start, planned_start)`、`:969` `set_workers(eff, eff)`。
- 代入 `active == runnable == w > 0` ⇒ `util = 50.00`，**与负载无关、与 `w` 无关**。

- 已被单元测试**锁死**：`eng/tests/unit/test_resource_judgement.py:457,458,477,479`

### 6.2 其余不可外推的读数

| 读数 | 不可外推的理由 |
|---|---|
| **单轮墙钟** | **同机同场景同产物的 drizzle 节点墙钟在三轮之间变化 3.3×**（308.078 s / 148.035 s / 94.242 s）。normalize 总墙钟 337.97 s → 164.90 s，而**总 CPU 消费量一致**（253.8 vs 220.5 核·s，差 13%）⇒ 变的不是工作量，而是 **I/O 阻塞时长**。⇒ **单轮墙钟百分比不得单独用于容量规划**；可外推的只有**结构性比例**（`drizzle_run/total ≈ 5.8%–6.0%`、`hips_write/total ≈ 94.0%–94.2%`，三轮稳定） |

| **隔离协议** | `conditions.json` 只有 `proc_stat_percpu_before`、**无 after** ⇒ 「外来负载 > 2 核即 INVALID」这条判据**本轮无法执行** |
| **`scale ≥ 2` / `n ≥ 9` / 4096²** | **未测**。时间预算所限，`--scale 2`（4× 像素）线性外推 ≈ 35 min 超预算。⇒ **这是已知覆盖缺口，不是「已验证 scale≥2 亦如此」** |
| **`--cpuset 0-3` 对照实验** | **未做**（时间预算耗尽），如实登记，不留推测结论 |
| **重复次数** | 本单 `n = 1` 完整轮（轮 A）+ `n = 1` HEAD 复现轮（轮 D）。`PERFORMANCE_MODEL.md` 的基准口径要求 **每 benchmark ≥3 次、记 median/p95**，**本单未达标** |
| **`hips_write` 占比的既有数字** | 代码注释 `module_adapters.cpp:1951` 写的「hips_write 占 drizzle 帧时 **24–30%**」**追不到任何实测来源**：全仓仅该处含此字样；其引用的 A/B 四档实验（`run/P1-PARALLEL-AXIS-REDESIGN-01/`）**测量维度只有墙钟 / 峰值 RSS / CPU 汇总，从未测过 `hips_write` 占比**；且重复次数不达标（A 档 n=3 自身散布 11.8%，C/B/FINAL 均 **n=1**），11.8% 的散布已与「24% vs 30%」这 6 个百分点同量级。⚠️ 本单实测的 **94%** 与之相差极大，且**不可用小批量帧（像素面积小 16×）外推**。⇒ **该注释数字应作为「待裁决」登记** |
