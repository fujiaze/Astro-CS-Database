# 09 · 调度问题与推导（phase1 并行/资源调度）

> 来源：P24（调度研究，已批准）、P12（帧级异步设计）、P21/P22（并行与工作集实测）、P36（调度落地，进行中）。
> 前台自撰；每条标【实测】/【推断】/【外推】。

## 1. 要解决的问题

phase1 单帧在 nside=512、总预算 B=4 核下实测：**一次 phase1 = 78.37 s，Σ 各节点墙钟 = 78.36 s（零重叠）**。

| 段 | 墙钟 | 实际用核 | 说明 |
|---|---|---|---|
| drizzle | 47.93 s（61.2%） | 3.73/4 | 唯一真正吃满预算的节点 |
| cal/psf/phot/snr/wcs/writer 合计 | **30.4 s（38.8%）** | **平均 1.6/4** | 被 `heavy_gate` **全局互斥**，彼此不能重叠 |

⇒ **单帧内部有 38.8% 的墙钟花在低并行度节点上，且这些节点本可彼此重叠**（它们用不同资源：IO / 单线程计算 / Gaia 查询）。

## 2. 两条独立的优化路线（P24）

### 2.1 路线一：帧级异步（多帧并发）
- **触发条件【实测】**：单帧并行效率足够低时才划算。实测 W(1)=224.4 s、W(2)=133.0 s、W(4)=78.8 s ⇒ **每翻倍核数仅 1.69× 加速（效率 71-85%）**；此时把预算拆成多帧优于给单帧加线程；
- **收益【实测】**：等总预算 B=4，K=1 串行 0.727/0.787 帧/min vs **K=2 并发 0.856/0.885 帧/min ⇒ +17.7% / +12.5%**；B=2 下 K=2 比串行 +11.8%；
- **derating【实测】**：同为每帧 2 核，并发单帧 139.11 s vs 串行 129.11 s ⇒ **γ(2)=1.077**（内存带宽/缓存/写盘争用）；
- **模型最优【推断】**：B=4 时模型最优是 **K=4（每帧 1 核）**，预测 0.99 帧/min vs K=1 的 0.74；
- **确定性【实测】**：K=2 vs K=1 —— 6/6 科学 JSON 逐位相同、`signal/`+`support/` 全 tile 逐位相同；唯一差异是 `properties` 的 `hips_creation_date` **墙钟字符串**（**串行跑两遍同样不同**，故与并发无关）。

### 2.2 路线二：帧内节点重叠（释放 `heavy_gate` 全局互斥）
- 就是 §1 里那 **30.4 s / 38.8%**；P36 正在落地（**D1**）；
- **硬约束**：①一个进程仍只有**一个调度器与线程预算源**（§10.4，禁硬编码线程数/禁私有长期线程池）；②**产物与线程预算无关**（绑核逐位一致）；③**总线程数不得超卖**；④内存不得无界增长。

## 3. 为什么本机拿不到帧级并发收益：**内存准入**

- 单帧峰值实测：**T4 auto 8.46-9.01 GB**、**T2 auto 5.72-6.35 GB**（P21/P22）；本机 `MemTotal = 15.62 GiB`；
- 准入判据（D5）：**可用内存 ≥ 2×单帧峰值 + reserve** ⇒ **K_mem(T4 auto) = 1**；
- nside=512 时单帧 1.10-1.86 GB，`K_mem=10` —— **P24 的并发实验就是在该区间做的**；
- ⇒ **生产分辨率下，本机帧级并发不可用**；需要 ≥2×8.5 GB 余量的机器。**这是资源事项（负责人 A3/D6）。**

## 4. 并发与 §10.5 资源门禁的冲突（MON-002）

- **【实测】同配置重复运行，rc 在 0 / `low_avg_cores` / `alloc_reclaim_missing` 之间跳变；并发时更容易判 `alloc_reclaim_missing`**；
- **根因**：门禁的 RSS 曲线是**进程级**的，**无法区分“本帧的爬坡”与“邻帧的爬坡”**；
- **结论**：**并发落地前必须先把 §10.5 指标按帧设域**（P12 §3.8 R5、P21 §1.4 已登记）；
- **与负责人决定的关系**：负责人已决定“**记录外挂、判定由前台/负责人**”（P26 已把程序内失败语义改为只记录 + `--strict-resource-gate` 可复现）⇒ **判定口径的改变已落地，但“分帧可读的记录”仍需 P36 完成（D2）**；
- **宪章层**：`§10.5/§17.6` 的修订草案在 `EXECUTOR_RULINGS.md` 附录 A，**待负责人签字**。

## 5. 与编译期/运行时的既有契约

| 契约 | 内容 | 现状 |
|---|---|---|
| §10.4 统一线程预算 | 一个进程只有一个调度器与线程预算源；禁硬编码 workers、禁私有长期线程池 | P32 把 `ctx.set_provider("baseline")` 硬编码改为宿主观测；线程预算实测绑核 1/2/4 → 1/2/4 |
| `taskset` 是唯一预算手段 | `OMP_NUM_THREADS` 会被 Runtime 覆盖（P28 复验） | 所有确定性验证都用 `taskset` |
| 产物确定性 | 与线程预算无关 | P15a 固定归约序；P35 三态消融绑核 1/4/8 核科学面逐位相同 |
| 无硬编码 ISA | `astrocs benchmark cpu` 决定 ISA/workers/block（§10.3） | P32 接通 provider 发现/加载/选择；**但生产科学 kernel 尚未经过 provider ABI** |

## 6. 未闭合问题（全部登记）

1. **内存准入（D5）**：本机 K_mem=1 ⇒ 帧级并发在本机**不可定标**；需大机器（负责人资源事项）；
2. **MON-002 / §10.5 分帧设域**：P36 的 D2 正在做；宪章修订待签字；
3. **`heavy_gate` 释放的收益上限**：38.8%（nside=512）/ 17.33 s（T4 auto，P12 实测）——**落地后必须用真实帧 A/B 验证，且不得超卖、不得改变产物**；
4. **γ(K) 与 K\* 的定标**：本机只有 nside=512 的 K=2 数据；生产分辨率与大机器上的定标缺失（D6）；
5. **并发下的失败模式**：需明确“内存不足时退化为串行且如实记录”，**不得静默单帧**（D5 契约）；
6. **调度与 phase3 的关系**：P30 修掉的 phase3 退化是**缓存/锁**问题（不是调度），但它使“整链墙钟”叙事改变 ⇒ 阶段 7 的端到端计时需重测。

## 7. 结论

- **帧级异步的机制与确定性已证明**（P24），**收益在本机被内存卡死**（K_mem=1）；
- **本机可立即拿的是“帧内节点重叠”**（38.8%，P36 在落地），代价是必须同时把 §10.5 记录**按帧设域**并保证**不超卖/产物不变**；
- **调度要真正冻结**，缺的是：P36 的落地证据 + 大机器上的 K\*/γ(K) 定标 + 宪章修订签字。

## 8. P36 落地结果（2026-09-15 16:00）——**一条必须先看的负结果**

### 8.1 落地的机制（契约层）
- **D1**：`lib/core/src/scheduler.cpp` 删掉旧 `heavy_mu` **全局互斥**，改为**预留账本 + 需求准入**；三模式由 `ASTROCS_SCHED_OVERLAP` 选择：**`demand`（新默认）/ `fair`（测量用，= 朴素释放互斥）/ `legacy`（`0`/`off`，回滚对照）**。三模式共同不变量：**Σ在途预留 ≤ budget**、`r_i ≤ D_i`、无空租约；
- **D2**：`cli/resource_recorder.h` + `cli/commands.cpp` 按 Runtime `NodeTrace` 生成**分帧/分段**记录（CSV 增 `frame_id,segments`；新增 `resource_segments.json`）⇒ 解决 §4 的 MON-002（进程级 RSS 曲线分不清本帧/邻帧）；
- **D5**：`cli/frame_admission.h` 纯契约；真实产物给出 `K_mem` 与 reason（M42 R @512 峰值 1.478 GiB ⇒ `K_mem=9`、`concurrent=false`、`reason=frame_concurrency_not_wired`；T4 auto 文档峰值 8.46 GB ⇒ `K_mem=1`、`memory_insufficient`）。

### 8.2 **负结果：朴素释放全局互斥是有害的**
真实 M42 R 全帧 4096²、nside=512、`taskset 0-3`（budget 4）：

| 模式 | Σ节点墙钟 | 整 run 墙钟 | 并发峰值 |
|---|---:|---:|---:|
| build-orig（修复前） | 60.48 s | 64.00 s | 1 |
| **`demand`（新默认）** | **60.29 s** | **63.6 s** | 1 |
| **`fair`（朴素释放互斥）** | **84.01 s（+38.9%）** | **69.0 s（+7.8%）** | **2** |

- `demand` **零退化但零重叠**：phase1 所有 `cpu_heavy` 节点都声明满额预算（`plan()` 返回 0 ⇒ `max_workers=budget`），两两冲突；
- `fair` **真的重叠了**（峰值 2），但**逐节点证据**：drizzle 被降到 `cap=2` 后 **35.94 → 51.33 s（+42.8%）**、snr **6.60 → 10.79 s（+63.5%）**；
- **根因**：**模块 OMP team 在节点起始由租约一次性固定**（`ScopedOmpWorkerInjection`），被降级的长节点在同伴结束后**无法恢复宽度** ⇒ 重叠变成纯开销；
- 阴性对照成立：legacy/demand 峰值 1 vs fair 峰值 **2**（重叠判定非恒真）。

⇒ **P24 §4.1 的 38.8% 在 B=4 下不可直接回收**（各段实测并行度：psf 2.94 / phot 1.75 / wcs 2.63 / snr 2.33 核，而长节点 drz 3.95 核 > 4；且 phot→snr 链与 wcs→drz 链互斥）。要兑现需要 **(a) R2 逐内核 benchmark → 节点 profile 需求** 或 **(b) D6 帧并发**（T4 auto B=16 时 drz≈13.5 核 ⇒ 约 2.5 空闲槽；B=4 无空闲槽，任何帧内重叠都是零和）。

### 8.3 前台裁决（建议）
**冻结“契约”，不冻结“朴素重叠”**：
- **冻结**：需求准入 / 不超卖 / 单一预算源 / 确定性 / 分帧分段记录（D1 的不变量 + D2 + D5）；
- **不冻结**：`fair`（`ASTROCS_SCHED_OVERLAP=fair`）——它是**测量用的对照模式**，保留为回滚/研究入口；生产默认 `demand`（零退化）；
- **收益转移**：帧内重叠的收益转交 **R2（profile 需求）** 与 **D6（帧并发，需大机器）**。

### 8.4 附带发现（建议单列）
**同一 1024² 输入：nside=128 的 drizzle 62 s vs nside=512 的 2.2 s（≈28×）**，而 phase1 HiPS 直写**本就要求 nside≥512** ⇒ 现在要浪费完前置算力才在 drizzle 节点内失败。**建议在 phase1 校验层直接拒绝 `nside<512`**（fail-fast）。
