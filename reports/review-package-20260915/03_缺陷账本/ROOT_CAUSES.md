## R1 · 机器门"看着在跑、实际不会红"：校验对象 ≠ 交付对象，或判据取自被检物自身
**机制**：这些门的共同结构是「校验对象≠交付对象」或「判据来自被检物自身」，所以它们不会因为产品变坏而变红——加更多同类门不解决问题。含五种形态：①结构上不会红（恒 `return 0`、空壳门、discover 收 0 用例仍 OK）；②红被制度化豁免（`waivable=False` 却被 `known_failures.json`/SKIP_RETURN_CODE 77 版本化容忍）；③门验错对象（验兼容图产物而交付根图，一旦改验交付物即红且被 golden 锁死）；⑤记账面"0 用例/0 输出/自宣跳过一律记 PASS"。**第 ④ 种（子串断言）因机制与修法不同，另立 R2。** 叠加机制⑬（三层静默同向：`return 0` + 只跑 `--selftest` + `re.S` 吞到文件尾）、机制⑭（元门自身不具判别力，即"用来证明测试有效的那层"失守）、机制⑪（零采集 ⇒ 必漂：有门采集面的镜像漂移 0 处，零采集的 10 个漂移 7 处，100% 对应）。
**代表条目**：M6a-G-001、M5a-G-005、M5b-G-003、M6b-E-001、M5b-G-01、M8-F-002、L23-002、FD-G-002、FD-G-004、V18-N-04、V18-N-05、V18-N-11、V11-N-01、V11-N-10、V9-N-01
**若不修会怎样**：CI 全绿与交付安全永久脱钩，"在册名单与基线名单"继续被当作"门有效"的证据；`linux-main − windows-main = 40 项` 说明 CLI/IO 合同族对 Windows **根本没声明**，不是"验了但恒零"；新增门继续复制同构失守（`--fail-if-no-tests` 缺失、`exit 77` 吸收非豁免门）。**"定向复跑全绿"不构成 fast 绿**（`impact_map` 只触达 71/130 门）。
**原文出处**：SUMMARY.md 簇 1（第 7–41 行，含第 24–33 行"四种失守机制"、第 37–39 行第五种、第 207–211 行机制⑭=簇 1 第 6 种）；机制⑬ 第 195–200 行；机制⑪ 第 185–188 行；INDEX §三第 1 行"机器门结构性不红"。

## R2 · 断言与不变量之间没有逻辑蕴含（子串/文本断言、同源自证）
**机制**：这类断言**有 CHECK、有 ctest、有 PASS**，但判据是文本字面量或被检物自身产出的值，与要守的不变量之间没有逻辑蕴含关系——比"结构上不会红"更难识别。典型形态：用 `find(字面量)` 对文本产物断言（测源文件名不测表内容；守一个由 `cli/resource_recorder.h` 硬写的字面量）；用被测函数自产阈值再乘 1.2 造"超阈"输入，使资源门断言与被测实现同源、恒可自证；"与 Python 参考比对"实为两个生产 provider 互比。
**代表条目**：FD-F-001、FD-F-002、M5a-G-002、M5a-C-004
**若不修会怎样**：值仍不可证伪，**极性翻转后机制一分未动**（M5a-G-002 已把生产者由 `true` 改 `false`、守卫同步改断言 `false`，但仍是 `js.find(子串)`）；子串判据会把截断串**固化为过门必要条件**（改到全精度反而红）。前台明言：守卫要"改成值断言"，否则"修生产者不改守卫就是新红"。
**原文出处**：SUMMARY.md 簇 1 第 ④ 种机制（第 31–33 行，前台新命名 FD-F-001/FD-F-002）；第 34–35 行（M5a-G-002 由静态推演升为历史数据实证）；`_verify/FRONT_LEDGER_CHECK.md` §五 第 1 项；M9.md §5（`p2_seam_gate_test.cpp:71` 基线恒真探针）与 §8（O4 同构，M9-F-2）属同族，按域归 R10。

## R3 · "符合性/已验证"结论的判定式**不含它要证明的维度**
**机制**：`docs/standards/STANDARDS_REGISTRY.md` 六个冻结域的 CONFORMANT 判定式**一律不包含其条款自身的判据维度**（丢"同一单位与语义""误差传播与退化标记""与外部目录真实星点比对""噪声模型与完备性门""J2016.0 历元维"）。因此"某偏差没登记"不是因为查过，而是因为判定式里没有该维度。同族第二、三实例：判定器 `check_standards_registry.py` 本身未进 `ci/checks.json`；其 `C3_evidence_path` 只判文件存在，致 60 个零注册测试源中有 ≥15 个在充当 CONFORMANT 证据。
**代表条目**：M3-G-002、M2a-B-2、M2a-G-1
**若不修会怎样**：宪章 §17.1 的发布前提（全部偏差已登记）**在结构上不可证伪**；偏差清单是"由漏登逻辑自己生成的"。六域横向核已复核：5 域确证命中＋1 域待会签，与"六域同犯"定档一致。
**原文出处**：SUMMARY.md 簇 2（第 43–49 行）；M7.md §4（父层 4 号移交的六域横向核）；INDEX §三第 2 行"符合性结论生成逻辑失真｜M3-G-002（六域）"。

## R4 · 独立 Oracle 缺位："不存在"与"共源"两扇都没有独立的门
**机制**：科学路径的"真值集"要么**不存在**（宪章 §11/§15 承诺的 NumPy rtol 1e-9 复算在仓库内没有实现，且类级 `skipUnless(g++)` 可整类静默跳过；oracle.jsonl 缺失且文件未进 CMake ⇒ 门恒绿），要么**与生产实现共源**（9003 例 Drizzle 真值集全部以生产函数当真值，≈50.7% 直接是生产 ∩ 生产，改判由生产实现自证）。两类需**两扇不同的门**（前者判"EVIDENCE 指针必须出现在 ctest 基线/discover 之一"，后者判"独立真值集禁止调用被测生产函数"），不可用同一门替代。
**代表条目**：M2a-F-1、M4-F-02、M2b-F-01、M7-G-104、M3-F-001、L02-001、L03-006、L15-013、L08-004
**若不修会怎样**：宪章 §12.3-4 的"独立 Oracle"要求对多数科学路径不可执行，"Oracle 全过／CONFORMANT"声明整体失去可核性；改判（正确性）只能由被改对象自己背书。
**原文出处**：SUMMARY.md 簇 4（第 58–62 行）；M7.md §3 家族（第 132 行"Oracle 缺位清单第 7 实例"）；INDEX §三第 4 行"独立 Oracle 缺位｜M7-G-104（七实例）"。

## R5 · 验收门的阈值/判决域在定义上取不到，或引用不存在的标准依据
**机制**：门的阈值或判决域被写成"在定义上就取不到"——第 1 类把判据写在 A 域（未平滑噪声、实数域、位精确）而被测对象在 B 域（平滑像、浮点累加、float32），缺折算因子（7.09、1 ulp、√(3π)/2、1.5625）；第 2 类把判据的外部权威写成引用者自造或错挂的标准条款；第 3 类把判据的证据写成计数口号（"N 例全枚举"且 N 与所列因子乘积不自洽）。三类共同点是**判据的外部性失效**，"门绿"与"科学正确"脱钩。
**代表条目**：M7-G-001、M7-G-105、M7-T-101、M7-A-118、M7-A-214、M7-A-202、M1a-C-001、M1a-C-004、M2b-B-07、M6a-D-001
**若不修会怎样**：任何实现都不满足该门，整改方向本身错误；引用不存在的条款号（FITS paper IV §2.1、Górski order≤29、宪章 §12.1 错挂）会被下游当作权威；冻结精度门"不可达且未裁决"被 registry 描述成"与 SCI 一致的低歧义项"。
**原文出处**：SUMMARY.md 簇 5（第 106–112 行）；M7.md §3 不可达验收门家族表（第 94–109 行，10 成员）；INDEX §三第 5 行"不可达门/依据虚构｜M7-G-001 + M7-G-105"。

## R6 · 承载/溯源面：把"存在"当成"承载"，把登记面互指当成代码侧溯源
**机制**：门的判据退化为"文件存在 + 符号 token 可见"，于是零注册测试源可充当 CONFORMANT 证据、空挂的合同 ID 行恒 PASS（判定器只验表内唯一性/格式/列完整，不验承载）。更极端的是**生成器自造 ID 再自证**：`TEST-UPMW-001..007` 等 16 枚由 `v19r3_traceability.py` 用 f-string 铸造、在 lib/tests/ci/tools 全零命中却被标 VERIFIED——任何引用检查必然通过，因为字符串本来就是它印的。叠加注释溯源无条文（tier1 88 头/13,705 行中**有溯源仅 2.1%**，字段面最重 2.5%）与行锚系统性失效（owner 锚 4/4 全漂；同日 HEAD 推进可见 `+1..+60` 不等量漂移）。
**代表条目**：L28e-E-001、L28e-E-002、M6b-G-001、M6b-E-001、M6b-E-002、L23-004、L28b、M6a-D-010
**若不修会怎样**：追溯矩阵的 VERIFIED 与孤悬 ID 都不构成承载证据；"登记面互指"（第 5 级 README/module.yaml 自指）会被误报成"已引用"；行锚同日失效使一切按行号写的锚/门当天漂移。汇报必须固定带两个数：**66.3%（注释+配置面）** 与 **19.2%（真源任意字面量且排除范围锚后的死锚）**。
**原文出处**：SUMMARY.md 簇 4 补（第 65–79 行，含口径裁定）与簇 4 补二（第 80–105 行，含 L28e-E-001/E-002），并注：其中"生成器自造 ID 自证""只验表内唯一性不验承载"两条**同时属于 R3 的判定式面**，本表按簇归 R6、交叉指 R3；INDEX §三第 8/9/10/14 行（无据 VERIFIED / 追溯双头 / 行锚系统性失效 / 注释溯源无条文 + 双向追溯断链）。

## R7 · 外部输入的边界校验只做一半，且 Windows 侧缺陷与恒零检查构成平台盲区闭环
**机制**：L24 十五条（P0:3）全部落在 gaia 客户端 / AIO / AHPX / HiPS / IO-001 边界，**每条都有同仓正对照**（readPixels 已等长校验、`aio_hips_tile_ipix` 已判负、`hips_join_path` 溢出即报错、`hiss_reader` 已用 `_fseeki64`、`aio_util.h` 已做 UTF-8→UTF-16）。结论：**不是不知道怎么写对，是新边界没继承老边界的纪律**，修复=对齐既有写法（低成本、低争议）。其中三条**只在 Windows 正式平台暴露**，而 CI 主跑 Linux 且 windows-main 关键子检查恒零断言/恒零用例（68 项声明量 vs 有效断言数无人核算）；孤儿测试 TU 在 build/CI 声明文件命中 0。

## R8 · 权威倒置与科学口径无单一事实源：两份 FROZEN 互斥、以代码为准静改、状态多头
**机制**：冲突发生时没有回到唯一权威裁决，而是"**不改 SCI，以代码为准登记**"（ALG:151-153 明写），或让 registry 把"冻结精度门不可达且未裁决"描述成"与 SCI 冻结一致的低歧义项"，或用 ARCHIVED 文档当权威。同一量因此可在 SCI/ALG/合同/实现多面并存互斥口径：§6.3 红线在 SCI/代码/ALG/局限**四面同时失守**（两份 FROZEN SCI 互斥，A-02 待裁决）、SNR 语义被换成已退休的 (A−B)/residual_scale 质量比、min_samples 5 vs 实现 64（12.8 倍）。状态面同样多头：四份 RELEASE_STATUS 并存且 owner 版与 review 版结论相反。
**代表条目**：M3-A-002、M3-A-001、M3-C-003、M4-A-003、M4-C-03、L21-001、L18-002、M1a-C-004、M1a-B-001、L18-010、M6b-G-002
**若不修会怎样**：科学口径永远无法唯一化，任何下游实现只能在若干互斥说法中任选且无人被判错；发布/完成状态自相矛盾，§1.1 权威分层形同虚设。机制⑫（裁决只写进注释与合同、不进登记面）同归此根因：一个"凭据虚构"、一个"凭据未登记"，共同支撑同一个"保留死码"的决定。
**原文出处**：SUMMARY.md 簇 3（第 51–56 行）＋簇 7（第 123–129 行）；机制⑫ 第 190–193 行（并入本 R，不单列）；INDEX §三第 3/11 行"§6.3 support 冒充权重""状态声明无单一事实源"。

## R9 · 控制参数被计算、被记录，但不参与执行（装饰性合规）
**机制**：看似有旋钮、有 schema、有日志，实际读路径恒按另一来源或默认值执行，参数零应用点。于是"可配置/已声明"与"实际行为"脱钩，偏差既不可观测也不可归因。口径订正也随之只停在文档层（主题已订正为"五处 FP64 声明与实际累加域不符 + 两处真实 FP32→FP64 截断"，而非原先的"三处 FP32 累加"）。
**代表条目**：M6a-C-001、M2a-H-1、M5a-G-003、M5a-G-004
**若不修会怎样**：`order_sel` 被算被记但读路径恒按 `hips_order`（SCI §9a-5 未实现）；`precision_mode` 请求 FP64 实得 binary32 累加 + FP64 声明，且只有 f64 manifest 的 DLL 通道能拿真 FP64（通道级不对称）；`--gate-required/--gate-workers` 零应用点而资源门判据不可触发。合规外观继续掩盖运行时偏差。
**原文出处**：SUMMARY.md 簇 8（第 131–136 行，6 成员）；INDEX §三第 12 行"控制参数被算被记不参与执行｜M6a-C-001 + M2a-H-1 + M5a-G-003"。

## R10 · "改过但没人守住"与"修复即扩散"：无回归锁、反向固化、错误口径被复制到交付面
**机制**：修复后没有回归锁（或锁在构建孤儿里、两侧 `tests/` 命中 0），下一批改动可无感退回；更糟的是**反向固化**——测试把缺陷/废止值钉成规格（flux≈90000=振幅、§18.2 已废止的 0.80、损坏文件静默跳过、k_corr `==0.3500` 字符串），使退不改会假绿、真整改会假红。并发修复批次还把**尚未固化的错误口径复制到新的、更可交付的面上**：`p1_sip_write_header_frame` 正按"像素域系数直写 FITS 标准键"的同一口径复制，桥注释还引用不存在的"FITS paper IV §2.1"；`B2-A18` 只修 session 通道、IR 通道无对称门。
**代表条目**：M1a-F-005、L22-005、M3b-A-02、L26-007、L26-001、M9-F-2、M9-A-2、M9-G-2、M3-C-005
**若不修会怎样**：错误口径从"内部计算"升级为"随产品交付"并获得端到端自洽的外观与回归面追认（两种反向形态：M8 域钉住**已废除的旧值**，M9 域钉住**从未正确过的口径**），修复反而表现为测试红。台账规则已定：`regression_test` 留空＝未加锁＝R 层降 PARTIAL。
**原文出处**：SUMMARY.md 簇 9（第 138–145 行）；INDEX §三第 13 行"修复即扩散／反向钉死／声明超前｜M9.md §7 六站点 + M8 §0.3 合格线十一项"；M9.md §7"修复即扩散"子清单、§8"回归保护钉死错误口径"反向形态；`_verify/FRONT_ACTION_LIST.md` §A 施工纪律。
