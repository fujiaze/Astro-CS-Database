### 2.10 参照实现 / 标准口径（用于判断「门该长什么样」）

- **Linux cgroup v2 `cpu.max` / `cpu.stat`**：容器「已分配容量」的可测口径是**配额**（`cpu.max` 的 quota/period），「实际使用」是 `cpu.stat` 的 `usage_usec`。利用率 = 使用 / 配额。⇒ 业界口径 = **分母取「授权上限」**；本项目 `granted_workers`（真实授予）是比配额更严的下界，`min(selected, available)` 才是「配额」语义。
- **本项目的既有裁决痕迹**：`include/astrocs/core/context.h:93-98` 逐字：「B2-A18 (GAP-06/BASE-F3): 租约授予观测 —— 此前 Runtime trace 写的是配置 budget（「创建线程」）而非「实际授予的并行宽度」，资源门又拿 budget 充当观测写入 `set_workers(budget,budget)`（**配置不得冒充观测**, 宪章 §10.5/§17.6）。…哨兵纪律: 0 = 未观测（不是合法并行宽度），**不得以配置值回填**。」
- **`ci/resource_monitor.py` 是纯 shim**（`ci/resource_monitor.py:3-17` 逐字：「不复制监控逻辑，单一事实源始终是 `tools/monitoring/run_monitored.py`」）⇒ CI 侧与本地侧**同源**，不存在「第五套实现」，但存在**第 4 套默认阈值**（judge）。

### 5.2 反方论证（最可能被反驳的点）+ 回应

**反方 1（针对 D-12）**：「`granted_workers` 是**无状态原子峰值**，不保证与统计窗重合；而且租约 token ≠ 真实 CPU 消耗 —— 如果模块租了 16 个 token 但只用 2 个，『观测分母』反而会**放大** U、掩盖低效。」

**回应**：成立，且这是**唯一能把 D-12 判反的论证**。处置：(a) 契约里**同时记录三个分量**（`selected_workers` / `available_cpus` / `granted_workers`），使「分母抬升」可被审计；(b) **保留两条独立于分母的硬失败** —— 「单活跃计算线程」与「逐样本 `U<0.60` 且 `runnable>0` 连续 >10 s」，这两条**不受分母取义影响**（`cli/commands.cpp:859-869` 是逐点算的）；(c) 若审计发现「分母虚高」，改进方向是**把 `peak_active` 换成「统计窗内的时间加权活跃租约」**（一个新的可测量量），而**不是**退回 `budget` —— 退回 `budget` 会重新犯 `include/astrocs/core/context.h:93-95` 明文禁止的「配置冒充观测」。
