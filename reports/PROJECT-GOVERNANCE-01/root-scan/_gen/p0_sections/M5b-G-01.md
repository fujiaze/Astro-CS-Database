- 问题说明: 三层叠加。①**门验的不是交付物**：产品 `astrocs` 由根 CMake 产出（唯一 add_executable，:588），而 CI 又另跑 `cmake -S cli` 产出**同名** `astrocs`；`API-DOCS` 命令树比对（`check_api_docs.py::check_command_tree`）与 CLI golden 族（`test_cli_protocol.py::EXE`、`test_cli001_vpi.py::BUILD`、`test_cli003_semantics.py`、`test_cli_v7_surface.py`、`test_phase123_pipeline.py` 等）全部指向 `build/cli/astrocs`，即 `cli/CMakeLists.txt` 第 1 行自述的「COMPATIBILITY 声明（BLD-002，**非产品事实源**）」二进制；该步骤内根图产物只被执行 `version --json`。②**缺失即零检查**：`check_command_tree` 只有 `if os.path.isfile(exe):`，**无 else** ⇒ 文件不存在时既不 fail 也不告警；`API-DOCS` 挂在 fast/linux-main/windows-main 三个 profile 且 `waivable=false`，而路径写死为无扩展名的 `build/cli/astrocs`，Windows profile 下该路径永不成立 ⇒ 该 profile 中这道门恒为零检查。③**两个同名二进制的源码集不同**：兼容树把 ARCH-001 §7 判为违例的 `aio_pipeline_engine.cpp` 编入并用 `ACS_WARN_SUPPRESS="-w"` 静默（`cli/CMakeLists.txt:18、:165`），根构建面只编 `aio_pipeline.cpp`（`CMakeLists.txt:328`）⇒「命令树/help/退出码均通过」不能被引用为产品二进制的符合性证据。另 `tests/cli/test_cli_protocol.py::built` 在二进制缺失时**自行** `cmake -S cli` 现场构建，故本地跑测永不暴露①的错位。（对 L12-001 的两处修正：`tests/cli` 并非「全部」用兼容树——`test_p1003_drizzle_path.py:13` 用 `build/astrocs`（根图 cp 副本）；`check_api_docs` 的退出码面是双候选路径回退。）
- 影响: §12.3-1/-5 与 §14.4 的全部 CLI 级证据（命令树、JSONL、退出码映射、cancel/crash、run-manifest verify）建立在非交付对象上；交付 `astrocs` 的命令面可自由漂移而三门恒绿；真实数据终验（§13.3）报告的 CLI 行为同属兼容树行为。
- 建议处置: 门禁目标改为安装/发布树中的产品二进制（先 install 再对 `<prefix>/astrocs` 跑 golden），或让 CI 对两棵产物做命令面双向 diff 并声明唯一权威；`check_command_tree` 补 else 硬失败并按平台解析 exe 扩展名；从 `cli/CMakeLists.txt` 源集剔除 `aio_pipeline_engine.cpp` 或删该兼容工程。
