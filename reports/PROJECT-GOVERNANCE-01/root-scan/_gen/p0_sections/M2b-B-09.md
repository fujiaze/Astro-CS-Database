### M2b-B-09 交付 FITS 可恒带 CHECKSUM 全零占位卡（注释谎称「HDU checksum updated」），且 verify 的豁免设在**计算值**一侧，D.fits §6 行仍判 CONFORMANT
- 类别: B_STD_MISMATCH
- 建议优先级: P0
- 位置: runtime/io/fits_core.c::fio_write_header_block（恒预留 CHECKSUM 槽并写全零值）、::acs_fio_writer_end_v1（仅 write_checksum 时 patch）、::acs_fio_verify_file_v1（mismatch 判据的豁免侧）；docs/interfaces/io/IO_001_FITS_STREAM_INTERFACE.md::§9 与示例段；docs/standards/STANDARDS_REGISTRY.md::D.fits 清单行 4（§6 DATASUM/CHECKSUM 行）；tests/io/test_fits_stream_contract.py::write_fits/checksum 用例
- 证据摘录:
  - 恒预留 + 占位值（原文）:「if (reserve_checksum) { checksum_off = total; … fio_card_write(f, "CHECKSUM", "0000000000000000", "HDU checksum updated"); total += 80; }」；调用侧（原文）:「1 /*reserve_datasum*/, 1 /*reserve_checksum*/」＋同段注释「恒预留两个槽, end 时按需改写或保持空白/零值」
  - 仅在显式请求时改写（原文）:「if (write_checksum) { … fio_card_patch(&wr->f, wr->checksum_card_off, "CHECKSUM", cstr, "HDU checksum updated", err, cap); … }」；接口示例与测试默认关闭（原文）:IO_001「fits_writer_end_v1(wr, 1 /*write_datasum*/, 0 /*write_checksum*/, &trace, err);」、test_fits_stream_contract.py「def write_fits(path, bitpix, shape, arr, bunit=None, datasum=1, checksum=0):」
  - 豁免在计算值一侧（原文）:「unsigned long decoded = fio_decode_checksum(cval, 1);」「/* 标准校验: 置零累计应等于 CHECKSUM 卡解码值 (即写时累计); 另兼容 sum==0xFFFFFFFF/0 的全零/未定义情形。 */」「if (sum != decoded && sum != 0xFFFFFFFFUL && sum != 0UL) { … return ACS_FIO_ERR_CHECKSUM; }」

  - 标准原文（实测取回，FITS 4.0 官方 PDF 目录与正文）:「4.4.2 Other reserved keywords … 12」（CHECKSUM/DATASUM 属**保留关键字**，归 §4.4.2）、「Appendix J CHECKSUM implementation guidelines 63 / J.1 Recommended CHECKSUM keyword implementation / J.2 Recommended ASCII encoding algorithm」；而 **§6 的标题是「Random-groups structure」**（实测目录：「6 Random-groups structure 16」）→ 注册表该行既挂错条款、又判 CONFORMANT
  - URL: https://fits.gsfc.nasa.gov/standard40/fits_standard40aa-le.pdf
- 权威依据: FITS 4.0 §4.4.2（保留关键字 CHECKSUM/DATASUM 的语义）+ 附录 J（推荐实现与 ASCII 编码；占位值不得作为交付校验值）；宪章 §8.3、§17.6（禁结构合法但语义虚假的伪产品）、§17.11；STD-REG-001 §1.2/§1.4
- 问题说明: 三件事同条根因：① 头块构造**无条件**预留并写 `CHECKSUM='0000000000000000'`，只有调用方显式传 write_checksum=1 才被真实值覆盖；而接口示例、合同样例与测试默认都是 0 ⇒ 交付文件里留着一张全零校验卡，其注释还写「HDU checksum updated」（并未更新）。按附录 J 的编码约定，全零 ASCII 解出一个确定校验值，等于在保留关键字中声明一个与 HDU 实际内容不符的校验和。② verify 的兜底豁免写在**重算值**一侧（`sum != 0xFFFFFFFFUL && sum != 0UL` 才报错）而非「卡值为占位即跳过并报未校验」，逻辑倒置：重算值恰为 0/0xFFFFFFFF 的文件无论内容如何都判通过（篡改不报），而带占位卡的正常产品在 verify_checksum=1 下会落入 mismatch 分支。③ 在册测试只覆盖 `checksum=1` 组合（write_fits 默认 0，仅 test_checksum_verify_and_tamper 显式传 1），「占位卡 × verify=1」零覆盖。注册表据此判 CONFORMANT 且偏差列写「无」，同时条款号错挂 §6（实为随机群结构）。
- 影响: 对外交付的 FITS 产品可呈「CHECKSUM 不符」，第三方校验器（astropy verify/fitsverify）判不合规；自研校验对自家默认产物可能假失败、对特定重算值假通过 → 校验门判别力被削弱，属产品不合规 + 门禁假绿双命中，故 P0。
- 建议处置: ① 写路径二选一：不预留卡，或预留则**必须**在 end 时改写为真实值（占位只在临时文件期存在）；② 卡注释按实际状态写（未更新则不得写「updated」）；③ verify 的豁免改判「卡值是否为占位」并返回显式「未校验」状态，取消对计算值的 0/0xFFFFFFFF 放行；④ 补两条负测：占位卡 × verify=1、篡改 + 重算值=0；⑤ 注册表该行改挂 §4.4.2+附录 J 并降为 PARTIAL、登记偏差 ID；⑥ IO_001 的示例与默认口径与实现统一（文档说默认不写卡、代码恒预留，二者必须一致）。
- 置信度: 高（占位恒写、豁免侧、测试默认值均为代码事实；「第三方判不符」为按标准编码规则的推论）
