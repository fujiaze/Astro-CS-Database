- 问题说明: 两文件的 `source_commit` 同为 `9f6b72b5`、字段结构同源（Linux 清单 :4；Windows 模板 :4 用 `@ASTROCS_GIT_COMMIT@` 生成，同 commit 即同状态），但同一两个 unit 的 `status` 不同。Linux 判据可核：`astrocs_runtime` 只编 `runtime/artifact_store/artifact_abi_v1.c` 一个源、`astrocs_io` 只编 `runtime/io/fits_core.c` 一个源，`docs/architecture/MODULE_MAP.md:22` 也记为 SKELETON；Windows 无"额外接线"证据——`runtime/module_loader/secure_loader.c` 在 `_WIN32` 下返回 `ACS_ERR_UNSUPPORTED`（README :46-48、ABI_003 :63、`docs/ARCHITECTURE.md:15` 同述），根 CMake 的 F-CI-002-01 注释（现 :132、:145）自述该 SHARED 目标连 Windows 交叉构建都链不动。⇒ Windows 侧只能等于或落后 Linux 侧，标 IMPLEMENTED 属不实完成度。附带：`ARCH-001.md:83` 的 LEG-001 整改登记"CLI 不得直呼 hp_drizzle_run_hips（P1-005）"，而生产 `astrocs` 现链 `astrocs_drizzle`（`CMakeLists.txt:606`）且 `cli/runtime_client.cpp:47` 仍存 `missing 'phase3' object for --phases 3` 文案，同一 commit 上登记与实况互斥。
- 影响: 正式发布平台（宪章 §3.1 唯一正式入口 `astrocs.exe`）的 manifest 把未接线的 runtime/IO 交付单元报告为已实现 ⇒ §16.2/§17-4/§18.3 违反；负责人据 manifest 判断 Windows 就绪度会被误导。
- 建议处置: 模板 status 由 install/verify 结果生成或暂标 SKELETON；ARCH-001 §7 LEG-001 行按实测订正；`CLI_PROTOCOL` 命令树增"废弃选项表"使 `--phases` 残留可核。
