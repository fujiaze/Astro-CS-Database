# 测试标准

> 上游：`docs/ACSD_DESIGN.md` §12.1（科学正确性与三重佐证）、§12.4（验证层级与四层验收）、
> §8.5（模块与 ABI：共址测试）
> 测试矩阵与逐条用例清单：`docs/engineering/TEST_MATRIX.md`

本标准规定测试的覆盖判据、确定性要求、命名与跳过规则、覆盖率分母与回归集合。
每个独立可调度模块的共址测试（单测、合同、负例）随模块在位，由该模块的注册面声明。

## 1. 覆盖判据

- 每条科学契约至少配 1 个 test / oracle（property、oracle 或 Monte Carlo 三选一）；
- 每个度量具备非退化判据，恒真门没有证据资格——真值无效应时度量必须归零或报警；
- 测试必须使用公共生产 API；实现面只有生产一份；
- 三类实验数据（仿真成像、解析代数合成、真实数据）各有独立用例面，
  不以某一类数据代表全部科学正确性。

## 2. 确定性

- 固定 seed；同一输入重复运行逐字节同结果；
- 浮点断言用容差 + 说明容差来源；容差在写测试前冻结；
- NaN / Inf / 缺失的位置与语义与产品逐项精确一致；
- 并行度不改变科学产品：1 worker 与 N worker 在冻结容差内等价，
  逐位等价的锚点见 `docs/engineering/execution_options_contract.md` §5。

## 3. 命名与跳过

- gtest 命名：`Suite.Feature`；
- GPU 或硬件能力不可用时用 `GTEST_SKIP`，不得以伪通过掩盖未执行；
- 负例必须可红：注入缺陷时判红，正确实现时判绿。

## 4. 覆盖率

覆盖率分母明确：shipping 单元与测试单元各自独立计数，不合并成一个数字。

## 5. 回归集合

以下集合为长期回归项，其判据骨架固定，实测数值与逐档读数归实验单元与
`docs/engineering/TEST_MATRIX.md`：

| 回归项 | 判据 |
|---|---|
| HiPS 序列化 | 与外部实现（`hipsgen`）对拍，逐成员一致 |
| 阶段间产品交换 | normalize 输出（signal / support / MOC / SNR / quality / frame_id / manifest）被 mosaic 与外部标准一致读取 |
| UPM 权重 | 并行度改变时权重归一结果逐位等价 |
| 原子发布 | 注入磁盘写满 / 写失败时无完成标记，产物可恢复 |
| 路径与词法 | 路径穿越、符号链接、非法文件名一律判红 |

## 6. 测试入口

| 入口 | 用途 |
|---|---|
| `lib/infrastructure/aio/tests/` | tile mapping oracle、sanitize、原子发布负例 |
| `eng/build/toolchain.ps1 check` | 环境与编译验证 |
| `eng/build/toolchain.ps1 build` | 构建验证 |
| `eng/tools/docs_machine_consistency.py` | 文档与源码的机器一致性判据 |

测试目标随模块在位，命名与目标映射由 `docs/engineering/BUILD_GRAPH.md` 声明。

## 7. 变更纪律

变更模块必须重跑该模块的相关 gate；引用未变更模块的既有产物时，
必须以构建指纹（内容 hash）证明同源，否则重跑。
受影响验证范围由改动集算出，只扩大不缩小。

## 8. 执行范围、改动集与分档

本节是「跑什么、跑多少、跑多久」的正本；门禁分级、判据可信性与豁免面见
`VALIDATION_EVIDENCE_STANDARD.md` §12。

### 8.1 三种执行范围

每次运行只有一个范围，写进结果并逐条可复核；「看起来像全量其实不是」即判红。

| 范围 | 触发 | 含义 |
|---|---|---|
| 增量 | **默认**（无参数） | 影响面增量：只跑与本轮改动集相交的判据 |
| 全量 | **必须显式** | 判据集合整档全量，不做任何按改动的裁剪 |
| 点名 | 显式点名 | 点名判据，不受档位与改动面过滤 |

- 增量是默认，全量是显式动作；全量用于发布前、跨域大改与任何拿不准的场合。
- 档位限定候选集：全量 + 指定档位才是该档整档全量。
- 结果必须携带范围、改动文件、是否升级为全量、未覆盖路径、是否无改动五项，
  供复核者一眼分辨「这次到底跑了什么、依据是什么」。

### 8.2 改动集

- 改动集 = 下列两者的**并集**，路径统一为仓库相对 POSIX 路径：
  1. `git diff --name-only <base>`（已提交但不在基线内的改动）；
  2. `git status --porcelain=v1 --untracked-files=all`（工作树未提交改动，含未跟踪文件）。
- 基线引用默认 `HEAD`。基线引用不存在、仓库不可用或路径无法解析 ⇒ 执行器错误（退出码 2）。
- **空改动集 ⇒ 全绿不在判据面内**：空改动集必须显式打印「无改动」并以退出码 0 结束，
  不跑任何判据。「没选中要跑的东西」记成通过是假绿，禁止。
- 重跑范围只扩大不缩小（§7）：改动集算出的受影响面是下界，追加的历史面与共享面一并计入。

### 8.3 选择规则

- 候选 = 本轮档位内登记的判据；
- 选中 = 候选 ∩ { 判据 | 其输入面路径模式与改动集中某路径匹配 }；
- glob 语义：`dir/**` 命中 `dir` 及其任意子孙；含 `*` / `?` / `[...]` 的模式按 shell glob 匹配
  （`*` 不跨 `/`）；不含通配符的模式为精确路径匹配；
- **受影响的构建与测试 target 由构建图反查得出**，不靠猜路径：数据源是构建系统的依赖边
  （依赖查询输出与构建图边）。运行测试的判据只在它声明的 target 集与受影响 target 集相交时入选；
- 选择结果必须可逐条复核：每条判据给「选中 / 跳过」的结论与命中的路径模式或构建图依据。

### 8.4 增量档必须能红的三条

增量档最大的风险是漏检，因此以下三条一律判红并逐条点名：

| # | 触发条件 | 判红形态 |
|---|---|---|
| 1 | 改动集中存在不匹配**任何**在册判据输入面模式的文件 | 列出未覆盖路径，提示补登记面或显式全量 |
| 2 | 改动命中敏感面（构建入口、构建与依赖声明面、公共头面、合同面、产品清单面、文档索引面） | 自动升级为全量并打印命中的敏感面 |
| 3 | 改动集非空而选中判据数为 0 | 判红 |

- 三条各配一条注入负例（人为构造「改动落在未覆盖路径」「改动命中敏感面」
  「选择器被置为恒空」），必须判红。
- 显式全量与升级后的全量不适用第 1 条（全量本身即补救），但仍须把未覆盖路径打印为登记面缺口。

### 8.5 超时与总预算

- 每条命令都带超时；超时缺失或非法一律执行器错误（退出码 2）。
- 单步超时上界 ≤ max(60 s, 3 × 最近一次实测墙钟)，且不超过该档的硬上限。
- 增量档设总预算：实际耗时超出即报告「应拆分」并以非零退出码结束，不默默跑下去。

### 8.6 分档与代价显式

| 档 | 触发 | 内容 |
|---|---|---|
| 快速档 | 本地与每次改动 | 秒级一致性面：静态、合同、治理、轻量单测 |
| 集成档 | **提交前必跑** | 真起子进程、真跑产品可执行程序、含真实测量窗的用例 |
| 全量档 | 合入前、发布前 | 完整构建 + 完整测试 + 集成档全部内容 |
| 测量档 | 负责人触发，一次性 | 性能测量、真实数据端到端、资源与扩展性测量 |

- **代价必须显式**：快速档变快靠的是把「真起子进程 / 真跑产品可执行程序 / 真实测量窗」的步骤
  移出去，**不是靠放宽判据，也不是靠 skip**。
- **提交前必须跑集成档**，否则事件流、磁盘门、资源门与运行时集成用例无人跑。快速档的汇总行
  必须打印 `integration_not_run` 提示，结果里带同名字段（机器可读）。
  「提交可合」的判据 = 快速档 + 集成档两档全绿。
- 集成型用例以**目录归属**划出，不以 `skip` / `xfail` / 环境变量绕过。
- 重步骤带**输入指纹缓存**：指纹 = 提交 + 相关配置内容 hash + 数据清单内容 hash + worker 数。
  指纹命中则跳过执行并复用已有归档（打印 `reused_fingerprint`）；指纹变化才重跑。
- 每日一次全量；重步骤由负责人按测量档触发。
- 环境：Windows 与 Linux 双平台运行；全部门禁通过后记录运行链接。

### 8.7 运行结果的可复核面

每次运行落一份结果，至少含：范围与档位、基线引用、改动文件清单、每条判据的
`verdict` 与结构化证据路径、是否升级为全量及原因、未覆盖路径、是否无改动、
各步墙钟与超时预算。判结论的门必须有结构化证据（§6 的 Q3 可归因）。
判红输出逐项给检查名、对象计数与被判红的前 10 条对象路径。

### 8.8 失败处置

- 红灯阻塞合入。修复方式是回退该提交或追加补修提交，历史前向追加，不改写既有历史。
- 执行基础设施故障：重跑一次；连续失败由负责人介入，不以豁免放行。
- **所有失败必须有可复现证据**（日志、命令、读数）。「环境问题」「工具问题」的归因
  同样以这份证据为准；无证据的归因不成立，也不得用来降级判据。
- 判红结论的复算按 `VALIDATION_EVIDENCE_STANDARD.md` §9 的盲复算与三态判定执行。
