### 2.2 缺陷

**(1) manifest 的 assessment issue 列表与 sidecar/estimate 不一致（P2/P3，所有产品）**

| 产品 | manifest.assessment.issues | sidecar / estimate.issues |
|---|---|---|

`unsupported` 正是“noise unknown / signal_only”的那条；manifest 把它吞掉了。complete/science/noise

**(2) ProductGraph 根键 ≠ 载荷语义身份（P2，透明性问题）**

每个产品 `manifest.root_object`/`product_id` 是 `sha256:<65b…>`（ProductGraph 内容的存储键），而

`root_object` 不是根的语义身份，三种哈希（内容键、语义 id、manifest canonical id）并存，消费者容易接错。

**(3) 输入不可追溯（P1，科学闭包）**

- f0/f1/f2 的 `manifest.inputs=[]`、`frame_science.inputs=[]`：原始帧 SHA、bias/dark/flat、response、
  Gaia WCS 都不在产物闭包里；`SignalEstimate.effective_response` 只是 `SpatialResponse`（drizzle 核），

- `mosaic/export` 的 `inputs=[]`：export 不记录它来自哪个 mosaic 产品（config 里的 `expected_hash` 不在产物里）。
- 只有 mosaic 的 `inputs` 有 3 个 normalize manifest 哈希。因此 normalize→mosaic→export 的依赖链在两端断开。
- 这与 `S1-P0-B`“持久化 recipe、geometry revision、内容身份、依赖”的要求不符，也使“同一真实源码 SHA +
  真实缓存 hash”的复现无法只靠产物完成。

**(4) mosaic 闭包缺 SkyFit/WeightSolution（P1）**

mosaic 的 8 个对象只有 4 个数组（coadd_signal、leaf_selection、states、coadd_support_area）、Index、

（coadd_weights/weight policy）**。所以 mosaic 的加性改正和等权选择只存在于一次运行中，产物本身不可重开。
执行者文档 `:145-148` 也承认“not reopenable from the product alone”。

**(5) 复开检查不再校验载荷内容哈希（P2，负例缺口）**

改后的 `open_product` 只用 `object_id` 集合解引用，不再把载荷的 canonical JSON 内容哈希与 manifest
`objects[].hash` 对比（product.cpp:1632-1655 的 diff 删掉了 `payload_id != entry.first` 的失败）。块级
`raw_sha256` 仍校验，但**篡改一个对象 JSON 的内容、保留 `identity.object_id` 字符串**即可通过复开。
`S1-P0-B` 要求的“不一致哈希必须拒绝”没有被这条路径覆盖。

## 5. 第 4 项：Mosaic / sky / coadd（FAIL）

### 5.1 数值上 coadd 做到了什么

从产品数组重建每叶三帧贡献（supported 才算）：

- mosaic 索引 23915 叶 = 三帧叶并集；覆盖类别计数：K=3 **23651**、K=2 **135**、K=1 **122**、K=0 **7**。
- 用单帧覆盖叶反解每帧实际施加的常数改正（62 个 f1-only、58 个 f2-only，离散度 0.0039 / 0.00046 **绝对**，
  即相对 1e-15）：

  **f0 = 0，f1 = +3.837177698e12，f2 = −1.037637017e12**（与执行者文档 `:114-116` 一致）。

- 于是对每个 supported 叶，`mosaic = mean_k(s_k − β_k)`（等权 1/K）成立：23908 个叶最大绝对残差 **0.5**
  （信号中位 5.3e12，相对 9.4e-14）。K=1/K=2/K=3 全部一致；权重确实是等权且每叶和为 1。
- `export/signal.fits` 与 `Q·mosaic` 完全相等：max relative diff **0.0**；Q 16777216 行、18,732,256 非零、
  每行和 = 1（无一行偏差 >1e-12）。Q 只触到 **23791** 个叶（= f0 的 23790 叶 + 1 个额外叶
  `(13,373643392)`），不是 sidecar 声称的 23915；7 个 absent 叶不在 Q 里，所以 FITS 无 NaN。

**这一层“加法链自洽”是真的**；问题在下一条：β 本身不是天光差。

### 5.2 反例 A：β 与暗天实测差差 20×/7×，且随星云亮度线性

在 23651 个三帧共同 supported 叶上：

- **最暗 10% 叶**（中位 base 4.083e12，基本是天光）：`s1−s0` 中位 **+1.92e11**（MAD 7.46e10），
  `s2−s0` 中位 **−1.49e11**。这是帧间真实的天光/背景差。
- 拟合施加的 β：f1 **+3.837e12**（≈ 暗天差的 20 倍）、f2 **−1.038e12**（≈ 7 倍）。方向也不对：f2 的暗天
  比 f0 暗 1.5e11，却被加上 1.04e12。
- 把叶心按 0.2° 分 36 个空间格、算每格三帧均值：`s1−s0` 与格均值 **corr 0.951、斜率 0.172**；
  `s2−s0` corr −0.677、斜率 −0.035。即帧差主要是**乘性**的（~17% 相对标度），不是常数偏移。
- 对格均值做“乘性+加性”联合拟合，得到真正的加性分量：
  **f1: scale 1.1722，offset −5.98e11；f2: scale 0.9650，offset −2.46e11**。
  执行者施加的 +3.837e12/−1.038e12 与联合拟合的加性分量差 ~6–7 倍且反号。
- 机理：加性-only 最小二乘在星云主导的 patch 上必然把乘性差吸收成常数，
  `β ≈ 0.172 × (patch 均值)`（patch 均值被亮核拉到 ~2.6e13 → 4.5e12 量级）。这正是工作规范
  `S1-P1-E` 明令禁止的“把不同夜的相对比例差错扣成背景”。

**结果**：改正后三帧在同 23651 个叶上仍不一致——改正后中位 f0 **5.971e12**、f1 **2.872e12**、
f2 **6.970e12**（f2 比 f1 高 4.1e12）。mosaic 是这三组不一致值的等权平均，天光/绝对面亮度被系统性
偏移（K=3 区域平均减去 (β1+β2)/3 = 9.33e11，约为天光中位的 23%），f1-only 叶的天光部分被减到 ~0.26e12。
所以“the corrected signals remove the offsets”只在“减去一个数”的意义上成立，**减的不是天光差**。

### 5.3 反例 B：7 个 absent 叶不是“在所有帧之外”

7 个 absent 叶是：
`(13,351234666) (13,351235153) (13,351255805) (13,351260963) (13,351970187) (13,373637363) (13,373642376)`。
它们恰好是 **f1/f2 的 unresolved 擦边叶**（f1 的 351234666/351255805/373637363，f2 的其余 4 个），
在 f1/f2 的 Index 里存在、只是 `normalizer_lower=0`；叶心距 f1 或 f2 边界 17.7–32.8 px。所以“7 absent
leaves are outside all frames”不成立——它们是**帧内擦边、无有效支持**，不是“所有帧外”。

### 5.4 反例 C：absent 叶被赋 0 信号 + 整个叶面积

`src/coadd/coadd.cpp:1891` 对 `total==0` 的叶直接 `continue`，`combined` 保持 0.0、`leaf_state=0`；

但 mosaic 产品语义错误，未来全并集导出会把它写进图。

### 5.5 反例 D：coadd 没有数值区间、没有权重策略、没有 effective_response

- `estimate->numerical_lower/upper = nullptr`（`src/coadd/coadd.cpp:1942-1943`）→ mosaic 与 mosaic export
