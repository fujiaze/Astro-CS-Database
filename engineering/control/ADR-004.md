# ADR-004：根级构建策略

- 状态：ACCEPTED
- 日期：2026-07-24
- 关联任务：P01-001

## 背景

AstroCS 项目包含 13 个活跃模块（lib/ 下），当前构建系统状态：

- **build.ps1**：8 个模块有 PowerShell 构建脚本（astro_image_io, calibration, healpix_stack, snr_estimator, photometric_calib, plate_solve/ipv, 等）
- **Makefile**：13 个模块基本都有 Makefile（部分过时，如 healpix_stack Makefile 仍引用已归档的 healpix_io）
- **混用问题**：calibration 存在两套构建（Makefile 产 cosmetic_corrector.dll，build.ps1 产 astro_calibration.dll）；healpix_stack Makefile 与 build.ps1 源文件列表严重分歧
- **工具链**：MSYS2 MinGW64（GCC 16.1.0）+ Qt6 6.11.0 + GSL 2.8 + Eigen3 5.0.1，Windows-only
- **路径问题**：GCC/mingw32-make/qmake6 不在默认 PATH，需显式指定 C:\msys64\mingw64\bin

P00-004 依赖图识别 10 个构建问题，P00-005 环境基线识别 3 个路径问题。P01 目标是"干净 clone 中通过统一入口构建所有模块"。

## 约束

1. **Windows-only**：项目仅支持 Windows（MSYS2 MinGW64），无需跨平台
2. **PowerShell 7 强制**：用户规则要求强制使用 PowerShell 7 运行环境
3. **最小改动**：用户规则"Surgical changes: Modify only target code, avoid unrelated refactoring"
4. **不重写现有可工作构建**：现有 build.ps1 和 Makefile 大部分可工作，重写违反"Simplicity first"
5. **可复现**：干净 clone 必须能重建（P01-007 验收）
6. **不引入新工具链依赖**：不要求额外安装 CMake/Ninja 等
7. **统一产物目录**：所有 DLL/EXE 产出集中到 build/ 目录，manifest 含哈希
8. **失败可追溯**：构建失败返回非 0 并保存日志

## 候选方案

### 方案 A：根级 CMake 统一构建
- 重写所有模块的构建为 CMakeLists.txt
- 根级 CMakeLists.txt 编排所有模块
- 优点：跨平台标准、IDE 友好、依赖管理强
- 缺点：重写 13 个模块构建文件、工作量大、引入 CMake 依赖、违反最小改动

### 方案 B：根级 PowerShell 编排器 + 各模块保留现有构建
- 根级 `build.ps1` 编排，调用各模块现有 `build.ps1` 或 `mingw32-make`
- 统一产物目录 `build/artifacts/`，构建后收集 DLL/EXE
- 优点：最小改动、符合 PowerShell 7 偏好、不引入新依赖、保留现有可工作构建
- 缺点：不跨平台（项目本身 Windows-only，非缺点）、Makefile 过时问题需在编排器层面规避

### 方案 C：根级 PowerShell + 逐步迁移 CMake
- 短期用 PowerShell 编排器（同方案 B），长期逐步迁移到 CMake
- 优点：兼顾短期交付与长期演进
- 缺点：双轨制增加复杂度、违反"Simplicity first"

## 证据

1. **P00-004 依赖图**：13 模块中 8 个有 build.ps1，所有模块有 Makefile（部分过时）
2. **P00-005 环境基线**：工具链为 MSYS2 MinGW64，PowerShell 7.6.3，无 CMake
3. **P00-006 审计复核**：B9-L-8 等问题指出 --threads 参数未生效，构建脚本需统一
4. **用户规则**："强制使用powershell7运行环境"、"Simplicity first"、"Surgical changes"
5. **项目实际**：Windows-only，MSYS2 环境，已有大量 PowerShell 脚本

## 决策

**选择方案 B：根级 PowerShell 编排器 + 各模块保留现有构建。**

核心设计：
1. **根级 `build.ps1`**：统一入口，参数化（`-Target all/clean/<module>`、`-Config Release/Debug`）
2. **模块构建适配**：优先调用各模块 `build.ps1`；无 `build.ps1` 的模块调用 `mingw32-make -f Makefile`
3. **统一产物目录**：`build/artifacts/`（DLL/EXE）+ `build/logs/`（构建日志）+ `build/manifest.json`（产物清单含 SHA-256）
4. **工具链 PATH 注入**：编排器启动时将 `C:\msys64\mingw64\bin` 注入 PATH，解决 GCC/mingw32-make/qmake6 不在 PATH 问题
5. **构建顺序**：按依赖图分层构建（基础层 → 中间层 → 顶层）
6. **失败处理**：任一模块失败立即停止，返回非 0，日志保存到 `build/logs/<module>.log`

## 后果

### 正面
- 最小改动，不重写现有构建文件
- 符合 PowerShell 7 偏好
- 不引入新工具链依赖
- 可快速交付（P01-003 bootstrap + P01-004 manifest 即可）
- 干净 clone 可复现（P01-007 验证）

### 负面
- Makefile 过时问题（如 healpix_stack Makefile 引用已归档 healpix_io）需在编排器层面规避（优先用 build.ps1）
- 非跨平台（项目本身 Windows-only，可接受）
- 长期若需跨平台或 IDE 深度集成，需重新评估迁移到 CMake

### 中性
- 各模块构建文件保持现状，技术债留待后续阶段清理（P01-005 clean build 时记录问题）

## 迁移计划

1. **P01-002**：建立 dependencies.lock.json，锁定工具链版本与路径
2. **P01-003**：建立 bootstrap.ps1，检查/安装 MSYS2 工具链
3. **P01-004**：建立根级 build.ps1 + build/ 目录结构 + manifest 生成
4. **P01-005**：逐模块 clean build，记录成功/失败与问题
5. **P01-006**：根级 smoke test（DLL 加载 + 版本查询）
6. **P01-007**：干净 clone 重建验证

## 回退

若方案 B 在 P01-005 clean build 阶段发现大量模块构建失败且无法通过编排器规避（如 Makefile 全面过时），则升级为方案 C（引入 CMake 逐步迁移）。回退不丢弃 PowerShell 编排器，作为 CMake 的上层包装保留。
