# 01 项目章程

## 1. 项目名称

Astro CS Normalization Database（以下简称 AstroCS）。

## 2. 项目目标

将原始 FITS CCD 图像经过基础校准、板解算、星点与 PSF 测量、Gaia 测光定标、SNR 建模、HEALPix Drizzle 重投影、多帧球面梯度校正和稳健叠加，形成：

- `.hiss`：不可变的单帧球面中间产品；
- `.hcsd`：可按 HEALPix 子叶查询、浏览和长期扩充的天球数据库。

最终目标不是“能跑出一张图”，而是形成一个**结果可解释、过程可复现、接口可演进、长期可维护**的系统工程。

## 3. 范围边界

### 本阶段范围

- Windows + PowerShell 7 + MinGW64 的可复现开发环境；
- C++17 核心算法、C ABI DLL、Python 调试与验证层；
- Stage 1 和 Stage 2 的端到端验证；
- HISS/HCSD 与 PipelineFrame 的版本化数据契约；
- 测试数据、配置、日志、检查点、构建产物和发布证据管理；
- Qt 浏览器只在核心数据链稳定后验收。

### 暂不进入主线

- Go 调度层；
- 云端部署与分布式调度；
- 大规模用户权限系统；
- 未经基准测试支持的算法重构；
- 为追求“架构漂亮”而改写已成熟模块。

## 4. 两段主流水线

### Stage 1：FITS → HISS

`READ_FITS → CALIBRATE → PLATESOLVE → PSF → PHOTOMETRIC → SNR → DRIZZLE`

### Stage 2：HISS → HCSD

逻辑上必须包含：

`输入一致性检查 → 重叠关系建立 → 背景/梯度样本构建 → 球面梯度模型 → 稳健离群值剔除 → SNR² 加权叠加 → HCSD 写出与索引验证`

是否在代码中拆成两个 Stage 节点，属于实现决策；但验收证据必须分别覆盖这些逻辑步骤。

## 5. 不可妥协原则

1. **代码现状优先于旧文档描述**，冲突必须登记，不能挑有利的版本解释。
2. **数据契约优先于模块内部便利**，格式改动必须版本化并提供迁移/兼容测试。
3. **接口所有权明确**，谁分配、谁释放、线程模型、错误码、单位与坐标约定必须写清。
4. **先有失败测试，再修缺陷**；无法构造验证证据的问题不能直接标记修复。
5. **一个任务只解决一个受控问题**，禁止 Agent 顺手重构。
6. **所有外部进程和可能阻塞的 Python 操作必须设置明确超时**。
7. **真实数据与合成数据同时验证**，真实数据证明可用，合成数据证明算法边界。
8. **Stage 2 不允许只靠视觉判断**，必须有接缝、通量、离群值、权重和确定性指标。
9. **主分支保持可构建或明确标记阻塞**，禁止“代码先放进去以后再修”。
10. **完成定义是证据，不是描述**。

## 6. 完成定义

任何任务只有同时满足以下条件才可标记 DONE：

- 需求与验收标准明确；
- 代码或文档变更范围受控；
- 自动化测试通过；
- 必要的人工检查有记录；
- 产物、日志和数据可定位；
- 影响的接口、数据格式与文档已同步；
- 回退方法明确；
- `control/` 中状态与证据索引已更新。
