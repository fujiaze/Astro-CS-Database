# 派单前置件 · 正向规格与文档订正意见（05 / 06 两件）

本件是"给每个创新点补 `05_正向规格.md` 与 `06_文档订正意见.md`"这一批派单的共用判据。
派单里只写：批次代号、本点目录、要读的权威文档清单。其余以本件为准。

## 1 硬纪律（违反即作废）

- 被审仓库**只读**：不得在仓库内新建或修改任何文件；不得 `git add/commit/push/checkout/reset/stash`；不得 `git config` 写。
- **不跑**构建、`ctest`、`run_checks.py`、任何 `eng/**` 脚本、任何端到端（负责人已裁：本阶段一切测试与端到端暂停）。
- 不 `import` 仓库内 Python 取常数（会生成 `__pycache__` 污染工作树）；要数值就读文件文本。
- 需要外网取证时 `curl` **必须**带 `-o` 指到 `产出/tmp/<批次代号>/`，绝不落在仓库内。
- 开工前 `git status --porcelain` 存一份，收口再存一份，两次的差异必须只包含本节点在**仓库外**的产出。

## 2 输入面

1. 本点目录的 `01_缺陷清单.md`、`02_已确立的算法与验证程序.md`、`03_修复顺序与验收判据.md`、`04_二次核对.md`（四件全部读完再动笔）。
2. 仓库权威链，按 AGENTS.md §1 的逐层下钻顺序：`ASTROCS_DESIGN.md` → `docs/design/` → `docs/plugins/`（模块正本）→ `docs/science/` 与 `docs/algorithms/` → `docs/contracts/`。派单会点名本点必须读到的具体文件。
3. `独立审计包`（同一交付集）里的 `02_科学/`、`04_代码/经验参数与硬编码清单.md`、`06_实施/打回报告B_设计符合性审查.md` 的相关节 —— 用作风味一致性与"这条是否已被别处判过"的对照。

## 3 `05_正向规格.md` 的判据

目的：开发节点**照本文实现即可，不需要重新推导，也不需要再读上位文档全文**；且日后能据本文独立造门。

1. **只写正向约束**。写"必须／取／等于／在…条件下拒并返回…"，不写"不应该""曾经""历史上"。文中不出现日期、任务编号、commit 号。
2. **每个常数**给五件：值、量纲与单位、来源档（`文献值`／`公式导出`／`实验标定`／`待确认`）、锚（`文件:行` ＋ 一句内容锚）、若为 `待确认` 则给**保守方向上的取值**与影响范围（哪个产品量、偏大还是偏小、量级）。留空不算规格。
3. **每个算法步骤／函数**给：输入域（含形状与类型）、输出值域、**无效输入的具名行为**（必须落到可区分的状态码或具名分支；不得返回一个"看起来合法的好值"，实例形态：取不到值时返回 0、缺失写成 1.0、空集判通过）、精度档（单双精度、容差及其来源）。
4. **每个产品字段**给：语义、单位、缺失的表达方式、与合同字段的对应（字段名逐字）。
5. **接线要求写进规格**：该实现被谁调用、在哪个阶段调用、失败如何传播到退出码。凡"已实现未接线"处，规格里要明确写出"当前调用者为 0，本规格要求的新调用点是 X"。
6. **判据要可独立制门**：每条判据写明三件——读哪个对象（哪个文件/哪个产品字段/哪个内存值）、期望方向（不等式含边界取等号的一侧）、注入什么必红。但**不写门的实现、不写注册表条目**（负责人口径：本轮门禁只记录不设计）。
7. **层级向下、口径唯一**：上位文档已经说清的不复述，指过去（`见 docs/science/XXX.md §n 那句`）；本文只补上位没规定的实现级细节。同一事实本文只说一次。
8. 本文与 `02_已确立的算法与验证程序.md` 的分工：那件记"已核为正确的式子与验证程序、不要动清单"；本文记"实现要长成什么样"。式子只在那件里推导，本文引用其编号。

## 4 `06_文档订正意见.md` 的判据

目的：文档不清晰处**必须给出可直接粘贴的订正文字**，只写"表述不清"不算交付。

1. 每条五字段：① 被订正文件 `:行` ＋ 内容锚；② 现状原文（逐字短引，不超一句）；③ **订正后完整文字**（可直接替换粘贴的整句/整段，不写"建议澄清"）；④ 依据（哪份上位文档哪一条，或哪条一手文献，或实现事实的 `文件:行`）；⑤ 同句还出现在哪些文件（口径唯一要求一并改，逐处列全）。
2. 三类分档并各自成节：**错**（与正本／实现／文献矛盾）、**缺**（无出处、无适用域、无单位、无常数推导）、**乱**（同一事实在多处各说一种、上下级重复正本、层级倒置）。
3. 不写责任归属与过程流水。凡"这句是谁写错的"一律不写。
4. 与 `05` 互指：凡订正后的文字构成本点实现约束的，`05` 里要有对应条目，本文在该条后标 `⇒ 见 05 §n`。
5. 判"某句是错的"之前，先按 ㉙ 的教训自证检索式能命中（本仓出现过两次"0 命中"其实是工具错），并核对该文档现行版本——上游可能已反转该条款。

## 5 输出契约

- 只写派单指定的**本点目录**内两个文件，不得触碰其他点的目录、不得改 01–04 与 README。
- 每完成 3–4 节就把已有内容 **append** 落盘（不要攒到最后一次写）。
- 文末自报：本点 `01_缺陷清单` 共 N 条，`05` 给出正向规格的 M 条／不需规格的 K 条（逐条列编号）、`06` 共 P 条（错 X／缺 Y／乱 Z）。
