# 门禁体系设计

本件规定 ACSD 门禁体系的层次、分档、触发规则、入口形状、fail-closed 与降级语义、受影响范围计算、采样隔离、结果纪律，以及门禁与文档口径的映射原则。读者是开发节点的工程实现者：本件每条规定都必须能照做、能核对、能红能绿；每条门的检验对象、命令、判据、正负例逐条登记在《门禁清单.csv》，旧门逐项结论在《门禁现状与旧门禁处置.md》。

权威来源：《门禁重建设计原则》（标准 05）§1–§7；`docs/ci/CI_SPEC.md` §2/§4/§7/§9；`docs/ci/01_CHECKS.md` §1/§2/§2.1/§3/§4；`docs/ci/03_GATES.md` §1/§3/§5/§6；`ENGINEERING_SPEC.md` §8/§10；`ACCEPTANCE_SPEC.md` §1/§8/§9；《目标文档架构》§4/§6/§7；《索引重建规格》§1/§6（其 C11 写法词表在本件 §7.6 收口）。本件不改变科学判据与默认容差（属 `docs/science/`、`docs/algorithms/` 的冻结面）。

## 0 设计取向与成功标准

### 0.1 三条上位取向

1. **正向质量在先，门禁在后**（标准 05 §1）。本件里的每条门检验的都是《目标文档架构》《索引重建规格》与四条链路核验报告已经确立的口径，不检验"实现现状"。凡某门需要的判据口径在正式文档层还不存在，先补口径再立门——门不得用自建词表充当口径来源。
2. **少而有牙**。门的数量不是资产，`判据能抓到缺陷` 才是。目标规模：重建后在册注册项 ≤ 100 个顶层项，且**每个执行单元都有一条登记在注册表字段里的可执行负例入口**。当前 150 个注册项 / 370 个执行单元里，注册表的命令面与 ID 面上找不出任何负例入口的注册项为 66 个（该读数按"命令含 `--self-test|--selftest|--fault-inject` 或 ID 含 `SELFTEST|NEG|NEGATIVE|REPLAY`"计算，是线索不是定案：一批门的注入入口住在被派发脚本内部而未写进注册命令，因此不可作判据使用，只说明**负例面必须有结构化登记载体**这一条设计前提成立）。
3. **给不出注入负例的判据不进清单**。本件与《门禁清单.csv》中任何一行，只要"注入什么它会红"答不出来，就写成"无负例⇒不进清单"，不允许以"报告项""观察项""后续补"的名义进册。

### 0.2 一条门"允许计入绿"的三条资格（缺一即它给的红绿都不作数）

| # | 资格 | 判据（可机器核对） | 不满足时的处置 |
|---|---|---|---|
| Q1 | **读真实对象**：登记的 `object_class` 与实际读到的对象一致，且对象不是它自己的夹具 | 注册表字段 `object_class` ∈ §1.5 枚举；`inputs` 声明面非空且实算对象数 > 0 | 改造或降级为 `fixture-only`（fixture-only 门不得进发布层，不得被引用为产品证据） |
| Q2 | **有牙**：注入对应缺陷必红，且至少一条负例落在该门自身的豁免/白名单/降级分支内 | `negative` 字段登记的命令真跑后 rc≠0；`--self-test` 走 `gate_trust.emit` 且 `kind=exemption` 用例存在 | 不出绿资格：该门的绿不计入任何层结论，直到补齐 |
| Q3 | **可归因**：本轮它到底跑没跑、跑了几个对象、判了什么值，读者能从跟踪证据复算 | 该单元出现在本轮结果 JSON 的 `steps[]` 且 `verdict=PASS` 属"有效执行"（§2.3 定义）；判"结论"的门有结构化证据 JSON | 整项零执行的门从"绿"的集合里剔除并单列 `not_effective` |

> Q1–Q3 是"少而有牙"的可执行化：一条门不满足任何一条时，它既不给红也不给绿，只登记为"未生效"。这把《门禁现状审计》指出的主问题（大量门"在跑但不判任何东西"、"全部门禁判别力已核"这类无因果的授权）从口径上取消。

### 0.3 本件不解决的问题（显式登记）

- 科学判据与阈值本身对不对（属四条链路核验报告与 `docs/science/`）；
- 双平台构建的可成性与 Windows 侧生产复验（属实施任务书，门禁只如实登记其不可达为 `not_effective`）；
- 测试语料的物理正确性（门只判"口径一致 + 判据非退化"，不判数据真伪）。

## 1 层次与分档

### 1.1 六个层次

层次的划分依据是**对象尺度**，不是脚本存放目录。每个执行单元恰属一层。

| 层 ID | 层 | 检验对象尺度 | 该层"绿"的成立条件 |
|---|---|---|---|
| `unit` | 单元 | 单个函数/类/端口的行为与合同断言 | 该层有效执行数 ≥ `floor[unit]`，且无 Q1–Q3 缺失项被算入 |
| `module` | 模块 | 单模块的端口、生命周期、口径与插件页（`docs/plugins/**`）一致 | 同上，且每个被索引的模块页至少被一条本层门覆盖 |
| `integration` | 集成 | 多模块协作：真起子进程/真跑 CLI/真实测量窗 | 同上，且本层单元全部 `heavy` 或 `requires_monitor` 者走采样隔离道（§5） |
| `e2e` | 端到端 | 三命令（normalize/mosaic/export）全链产品与 manifest 链 | 同上，且产品树由本轮同档单元现算产出（不允许只回放历史轮次目录，§6.5） |
| `visual` | 视觉 | L4 成像目检的机器侧判据（接缝、黑洞、亮斑、几何） | 同上，且判据对象是真实天区产品树而非合成画幅 |
| `release` | 发布 | 发布门清单（`ACCEPTANCE_SPEC.md` §8 九条）的合成 | 前六层全部满足各自条件且 `not_effective=0`、`trust_void=0`、P0 红=0、豁免=0；本层只合成、不新增判据 |

**层结论必须分层取值**（这是对 `docs/ci/03_GATES.md §5`"全部 P0 绿 + P1 绿 → 门禁通过 → 打包发布候选"的订正）：现在的合成式把所有对象类别的绿混成一个"绿"字，而绝大多数门只读文档与源码文本，于是文本面全绿被下游读成"产品正确"。重建后的 `gates-summary` 必须逐层给 `layer / effective / red / not_effective / trust_void`，发布层在任一层 `effective = 0` 时判红并点名该层。

### 1.2 两个耗时档位

| 档 | 目标墙钟 | 成员判据（进档条件） | 允许的最高层 |
|---|---|---|---|
| `quick` | 整档 ≤ 120 s | 静态/文档/合同/注册表/治理/轻量单测；单单元登记超时 ≤ 120 s 且实测墙钟 ≤ 60 s | `unit` / `module` |
| `measure` | 逐单元显式预算，整档无总预算但每单元 timeout ≤ `max(60, 3×实测)` | 真起子进程、真跑 CLI、真构建、真测量、真实数据 | 全部六层 |

- `quick`/`measure` 是对现有 profile 的**归类层**：`fast`→quick；`integration`、`linux-main`、`windows-main`、`linux-deep`、`prerelease`→measure。profile 名保留（工作流与文档处方已在用），不再往 profile 里塞耗时属性——`fast` 档 194 个单元里登记超时 > 120 s 的有 112 个、合计 53 160 s，说明"档"当前只是成员名单、不是预算承诺（实测值取自注册表现算，本件不抄录该读数为阈值，见 §6.6）。
- **档与层的相容性由注册表门判红**：`quick` 档内出现 `layer ∈ {e2e, visual, release}` 的单元即红；`mutates_workspace=true` 的单元不得在 `quick`（既有 R8 保留）。
- `fast` 档汇总行保留 `integration_not_run` 提示与机器可读字段（`CI_SPEC §2.6`），并且：`quick` 档单独全绿**不得**被任何文档表述读作"提交前全绿"。

### 1.3 触发规则

| 事件 | `scope` | 档 | 层 | 说明 |
|---|---|---|---|---|
| 本地/agent 默认（无参数） | `changed` | `quick` | unit+module | 增量是默认，不是可选优化 |
| 提交前 | `changed`→`quick`，随后显式 `integration` | 两档 | +integration | "提交可合"= 两档全绿（`CI_SPEC §4`） |
| `pull_request` | `changed` | `quick` | unit+module | 与本地同口径同入口 |
| `push` 到 `main` | `full` | `measure` | unit…e2e | 双平台各一档，按 §2.4 平台相容过滤 |
| 每日定时 | `full` | `measure` | 全六层 | 兜底：无提交也复跑 |
| 人工点名 `--check <ID>` | `explicit` | 不受档过滤 | 任意 | **点名不豁免零有效执行判红**（§2.3） |
| 负责人触发发布验收 | `full` | `measure` | `release` 合成 | 只有此时才允许出"发布门"结论 |

触发规则的三条硬约束：

1. 触发规则表本身是注册表面：每个单元的 `profiles` ∪ `layer` ∪ `tier` 决定它在哪一行里被选中，`--explain` 必须能逐条回答"为什么选中/为什么没选中"（既有能力保留）；
2. 任何"绕过触发"的手工运行只产生 `explicit` 结果，其 rc 不得被引用为"该层已验证"；
3. 定时全量若某层 `effective=0`，必须显式判红（不允许"这层今天没成员"静默通过）。

### 1.4 每层的下限覆盖（`floor[...]`）

各层的最小有效执行数不得由门自己抄观测值，唯一合法来源是**被覆盖对象的计数面现算**：

| 层 | 下限的定义式（不是数字） | 为什么非退化 |
|---|---|---|
| `unit` | ≥ 跟踪集中 `lib/**` 可构建单元数（`docs/modules/MODULE_MAP.yaml` 的模块 ID 数） | 模块表新增一项而测试族没长 ⇒ 红 |
| `module` | ≥ `docs/plugins/**` 中被 `00_INDEX.md §2` 登记的模块页数 | 新增模块页无门覆盖 ⇒ 红 |
| `integration` | ≥ `eng/tests/runtime/integration/**` 用例文件数 | 目录清空 ⇒ 该档 0 成员 ⇒ §2.3 判红 |
| `e2e` | ≥ 本轮真实数据端到端产品套数（由 `inputs` 声明的数据集个数现算，无数据集 ⇒ `not_effective`，不得当绿） | 干净克隆上必为 0 ⇒ 该层判红并点名"缺真实数据" |
| `visual` | ≥ 验收数据组数（M42 + Galaxy Center，取 `ACCEPTANCE_SPEC.md §6` 的正本口径，不在本件抄数值） | 少一组即红 |
| `release` | = `ACCEPTANCE_SPEC.md §8` 条数，逐条一条结论 | 条款数变更由文档锚门强制同步 |

下限值一律写成"由 X 面现算"的表达式，禁止把某次实测的单元数写死进代码或文档（§6.6）。

### 1.5 对象类别 `object_class`（新增注册表字段）

| 值 | 含义 | 允许进入的结论 |
|---|---|---|
| `product` | 读阶段产品树/产品清单/manifest/落盘 FITS | 任何层，可作发布证据 |
| `contract` | 读 `eng/contracts/**`、`eng/packaging/config/**` 机器件 | 任何层 |
| `registry` | 读注册表/登记面自身（自审面） | `unit`/`module` 治理层，**不得单独支撑发布层** |
| `doc-text` | 读文档文本 | 一致性结论；不得表述为"产品正确" |
| `source` | 读 `lib/**`、`*.cpp/h` 源码文本 | 静态接线结论 |
| `build` | 读构建产物/安装树/符号表 | 构建与发布层 |
| `test` | 读 `eng/tests/**` 用例面 | 单元/模块层 |
| `fixture-only` | 只读门自己造的临时夹具 | 判据自证；不得进 e2e/visual/release |

该字段的用途不是分类好看：发布层的绿要求"至少存在 `object_class ∈ {product, build}` 的绿"，否则合成判红（§6.1）。这是对《门禁现状审计》对象普查一节（167 个派发脚本中读真实产品的只占少数，主体读文档/源码/自身配置）的处置方式——不增设门，而是取消"文本面绿可以合成产品结论"的通道。

## 2 入口唯一化

### 2.1 现状形状（设计前提，不是待议事项）

1. CI 走 `eng/ci/run.py`，文档与人工复跑走 `eng/ci/run_checks.py`：`docs/ci/01_CHECKS.md §2` 为注册项逐个写的复跑命令里，走后者的有 58 行、走前者的 0 行；两个 workflow 的 `run:` 体只允许调前者。
2. 两条入口不是并列而是**串嵌**：注册表校验器 R12 强制"聚合项的 command 必须经 `run_checks.py` 派发 steps"，实算 71 个聚合项 100% 如此，其 step 总数 291 个 ⇒ **370 个执行单元里 291 个的判定住在内层**。
3. 判定面不对称：外层有"零有效执行不得判 PASS"的三分支守卫，内层没有（内层的汇总式是"有 FAIL 才 FAIL，否则 PASS"，而 `FAIL_VERDICTS` 不含任何 `SKIPPED*` 与 `PASS(reused_fingerprint)`）。于是"整批被跳过"在内层是一次 rc=0 的 PASS，外层把它当一条正常成功的命令，守卫在**外层**而洞在**被外层嵌套的那一层**。
4. 同一缺省值三侧各读各的：字段继承只在内层实现；外层不展开 step 且把未声明 `platform` 的 step 当作"本机可执行"；合同侧要求逐 step 显式声明；旧普查读 step 自身字段不做继承。两口径的**真实**差面按 runner 语义（step 显式给出即覆盖，缺省才继承）复算为：面归属不同的单元 **2 个**（两条同族单元自身无 `outputs` 而父项有 1 条），逐字段依赖继承补齐的 step 数为 `requires_monitor` 9、`heavy` 3、`mutates_workspace` 2、`waivable` 2、`outputs` 2、`changed_paths` 2、`prerequisite_tools` 5、`fingerprint` 1；其余 291 个 step 的 `command/profiles/platform/timeout_seconds` 全部自带 ⇒ **继承对必填面是零负载、对可选面是少数承重**（订正：上游件报的"42 个单元面不一致 / 81 个靠父项补 outputs / 88 个补 requires_monitor"把 79 个无 steps 的顶层项当作"缺字段的 step"计入，属口径混用，本件不用该数）。
5. 一致性合同只写在两份文件的注释里，且各自把一致性圈在互不重叠的窄面上（一条管"同一个 77 退出码"、一条管"同一份声明输入判定"），没有任何规范条款管"零有效执行如何判""平台不符如何判"。规范侧对 `explicit` 档明文豁免 profile/改动面过滤，却没有给该档任何"零有效执行"口径。

### 2.2 唯一执行器与唯一派发面

| 项 | 目标态 | 落地动作 |
|---|---|---|
| 执行器 | `eng/ci/run_checks.py` 是**唯一**拥有"选中集→单元→verdict→rc"全链的模块 | 把外层现有的"零有效执行判红""FATDUCK 语义""平台不符"三段裁决提取进共享模块并由内层调用；外层不再有第二份汇总实现 |
| CI 入口 | 两个 workflow 改为直调同一执行器（`python3 eng/ci/run_checks.py --all --profile <p>`），`eng/ci/run.py` 的裁决与汇总路径删除；其被单测引用的纯选择函数迁入共享模块 | 与 §2.6 的第 1 批同提交 |
| 派发面 | 注册表是唯一派发面：workflow 里除执行器调用与产物上传外不得直接执行任何决策脚本 | 新增判据：`workflows` 的每个 `run:` 体必须命中三类白名单且其中不含未在注册表登记的决策脚本 |
| 聚合项 | 取消"自派发命令"：执行器对任何 scope 都直接展开到单元粒度；聚合项的顶层 `command` 不得出现 `run_checks.py --check` | R12 反转（见下） |
| 文档处方 | `docs/ci/01_CHECKS.md §2` 的命令列由注册表**生成**，不手写（§7.2） | 生成器 + `--check` 核对，逐字比较 |
| 字段解析 | `index_steps(registry)` 是唯一"注册项→执行单元（含字段解析）"函数，执行器 / 校验器 / 普查 / 文档生成四方都调它 | 见 §2.5 |

**R12 反转的判据**：`checks.json` 中任何含 `steps` 的注册项，其顶层 `command` 若出现 `eng/ci/run_checks.py` ⇒ 注册表门判红（`R12b aggregate_must_not_self_dispatch`）。理由：嵌套派发使外层守卫永远看不到内层的空集。正例：聚合项顶层无 command 或其值与 steps 展开结果一致；负例：给一个聚合项的顶层塞回 `run_checks.py --check` ⇒ 必红。

### 2.3 有效执行与零有效执行（写死的定义）

**有效执行** = 该单元在本轮真的执行了其 `command`，并给出了 `PASS` 或任一 `FAIL(...)` 判定。

以下四种**一律不计为有效执行**，且不得出现在任何"绿"的合成式里：

| 状态 | 现状如何判 | 目标如何判 |
|---|---|---|
| `SKIPPED(platform)` | 计数但不阻断 rc | 计入 `not_effective`；整项/整档全跳 ⇒ 红 |
| `SKIPPED(waivable)` | 同上 | 同上；且 P0 门不得 waivable（§6.2） |
| `SKIPPED(optional_input)` | 同上 | 同上；`release` 层要求该计数为 0 |
| `PASS(reused_fingerprint)` | 记为 PASS 且不阻断 | **不再算绿**：复用只在"归档证据仍在 + 证据带其生成时的 HEAD 与指纹戳 + 该单元声明允许复用"三条同时成立时合法，且必须单列 `reused`，`release` 层要求 `reused` 单元的证据哈希与本轮可核对 |

**零有效执行判红（跨 scope，一条实现，一处判定）**：任一 `scope ∈ {changed, full, explicit}` 下，选中单元数 > 0 而有效执行数 = 0 ⇒ `verdict=FAIL(scope)`、rc≠0，判词逐条点名每个单元为何未生效（平台/依赖缺失/可选输入全缺/指纹复用）；选中集本身为空 ⇒ 同样判红，唯一例外是"改动集为空的增量档"（必须显式打印 `no_changes` 后 rc=0，这条保留现状）。

**该守卫必须是可跑的红，四条满足判据**（开发节点照此验收）：

1. 在 Windows 本机 `--check` 点名一个 `platform: linux` 的注册项 ⇒ rc≠0（今天为 rc=0）；
2. 在 Windows 本机 `--all --profile prerelease`（64 单元里 53 个被平台跳过）若剩余 11 个全部依赖缺失 ⇒ rc≠0；
3. 构造一个所有单元 `platform: windows` 的合成档在 Linux 上跑 ⇒ rc≠0；
4. `--self-test` 的负例集里必须包含"全部单元返回 77"这一形态，断言整轮 verdict 为 FAIL。

### 2.4 平台语义与 profile×platform 相容

- `platform` 值域收敛为 `{any, linux, windows}`。现状把 `fatduck` 同时当平台与档位用：值域里允许 `platform: fatduck`，但实算没有任何单元登记该值，而 3 个 `fatduck` 档成员全是 `platform: any` —— 两列各说各话。目标：投递渠道是档位属性，不是执行平台属性。
- 新增注册表面：每个 profile 在 `checks.json` 顶层声明 `platforms: [...]`（唯一登记面，不在文档里另写一份）。
- **相容性判据（注册表门，`GATE-PROFILE-PLATFORM`）**：
  - C-a 单元 `platform = X` 且 X 非 `any` ⇒ 其 `profiles` 里每个档的 `platforms` 必须含 X；
  - C-b 每个档的 `platforms` 非空，且该档成员集合在其声明的每个平台上都满足"有效执行数 > 0"；
  - C-c `platform: fatduck` 之类的非平台值出现即红。
- 现例即该门的负例样本：`CHK-ALGO-WIRING` 登记 `platform: linux` 同时进 `windows-main` 且 `waivable: false` —— 同一个注册项在 CI 面必判 `FAIL(prerequisite)`、在人工面判 rc=0。修数据（把它从 `windows-main` 移出或改 `platform: any`）与该判据同提交落地。

### 2.5 字段解析唯一化（消灭三侧口径）

- 唯一函数 `index_steps(registry) -> [unit]`，输出**解析后自描述**的单元（每个单元带全量字段，不含"待定"）。
- **废除隐式继承**：`waivable / heavy / requires_monitor / mutates_workspace / outputs / inputs / optional_inputs / prerequisite_tools / changed_paths / timeout_seconds / platform / profiles / command` 全部要求逐单元显式登记。合同侧（`STEP_REQUIRED` 扩为全字段）与执行器侧（去掉 `INHERIT_FIELDS` 路径）在**同一提交**内改；数据回填（291 个 step）与字段扩表也在同一提交内，避免"改了校验器数据全红"或"改了数据校验器全红"的中间态落 main。
- 该决定的代价明确：`checks.json` 体积上升、复制字段增多。换来的是"注册表行的形状 = 真实被强制的形状"：直接消掉 §2.1 第 4 条的三侧分叉（现真实分叉面为 2 个单元的面归属与逐字段的 9+3+2+2+2+2 处补齐），这是"少而有牙"里"能核对"那一半，接受。
- 负例：删掉任一 step 的 `platform` ⇒ 注册表校验红（今天：一个红、一个继承、一个当 any）。

### 2.6 入口迁移的事务顺序（防死结）

| 批 | 动作（同批内必须一起完成） | 批间顺序约束的理由 |

| 2 | 注册表字段扩表（schema + validator + 执行器三方同批），并逐 step 回填全字段，同时删除 `INHERIT_FIELDS` 路径 | 三处任一先动都会红（§3.4 的白名单死结） |

## 3 fail-closed 与降级语义

### 3.1 判红清单（关键口径缺失 / 前提不满足 / 读端不识别）

| 情形 | 判定 | 具名判词 | 现状 |
|---|---|---|---|
| 声明的 `inputs` 路径不存在 | 红 | `FAIL(inputs_missing)` | 有，但只覆盖 10/370 单元（因只有 10 个声明了 inputs） |
| `inputs` 扫描面目录为空 / glob 零命中 | 红 | `FAIL(inputs_empty)` | 有，同上 |
| 判据所需的登记面（台账/白名单/映射表）缺失或不可解析 | 红 | `<TOOL>_ANCHOR_MISSING` | 抽查的 5 个扫描型门均在实现内自守（§3.2 要求把它挪到注册表面） |
| 关键口径（被 `clause` 指向的文档节）不存在 | 红 | `CLAUSE_MISSING` | 无（新门 `GATE-CLAUSE-MAP`） |
| 读端不识别必要结构（schema 版本不符、字段缺、词表外取值） | 红，不得"未知即忽略" | 逐具名 | 部分 |
| 依赖工具缺失 | 非 waivable ⇒ 红；waivable ⇒ `not_effective` | `FAIL(prerequisite)` / `SKIPPED(waivable)` | 有 |
| 检查器自身崩溃 | rc=3，红绿均不采信 | `GATE_TRUST_FAIL` | 有且做得对（§3.3） |

**注册表级 fail-closed 判据（`GATE-DECLARED-INPUTS`）**：除 `object_class = fixture-only` 与被标 `pure-builder` 的构建步骤外，每个非 waivable 单元必须声明 `inputs` 或 `optional_inputs` 之一；缺失 ⇒ 注册表门红。这条把"每道扫描型门自己记得写零对象守卫"变成"没声明输入的门进不了册"，使 runner 能独立复核"这一步到底看了几个对象"，而不是依赖读者对实现体的信任。

### 3.2 零对象守卫的强度要求

`inputs` 声明本身可以是空的或假的，因此判据必须是两条而不是的一条：

1. 声明非空且实算对象数 > 0（否则红）；
2. 声明的对象数**必须与该门实际消费的数一致**：门在证据 JSON 里输出 `n_objects`，注册表门核对 `n_objects` 与 `inputs` 面实算数（目录取递归文件数、glob 取命中数）之差 ≤ 声明容差；差异过大判红并点名。

- 正例：某文档门声明 `docs/ci/**`，证据里 `n_objects = 5`，实算 5 ⇒ 绿。
- 负例：把该门的输入根参数指向一个空目录 ⇒ `n_objects = 0` ⇒ 该门自己判红；把 `inputs` 改成一个不存在的目录 ⇒ runner `FAIL(inputs_missing)`；把 `n_objects` 写成常量 ⇒ 第 2 条判红。
- 这条专门对付"输入对象数为 0 时空扫描判绿"这一母题，并同时堵住它的变种（守卫在外层、洞在被嵌套的内层：`GATE-DECLARED-INPUTS` 的判据面在单元级，不在项级）。

### 3.3 崩溃与判红分离（保留并补全）

三态退出码（0 绿 / 1 红 / 2 runner 配置或环境错误 / 3 门自述不可信）在两侧一致，且条目级显式拒绝把崩塌平成 FAIL —— 这一面保留为正本。两处缺口按以下方式收：

1. "门自述崩"现在靠输出里的 `GATE_TRUST_FAIL|SELFTEST_FAIL` 字面量正则识别，注册表侧无任何字段登记"本门具备 rc=3 声明能力"。改为**注册表字段** `crash_declared: true`，并由注册表门核对：声明该能力的门，其 `negative` 命令必须存在一条以 rc=3 为期望的注入用例。禁止再用命名与正则承载判定。
2. 启发式把"先打印过 verdict: PASS 再抛 Traceback"的单元记为 FAIL 而非 CRASH（方向安全但归因错）。改为：只要检测到未捕获异常栈帧，就在结果 JSON 里同时记 `verdict` 与 `trust = void`，`trust = void` 的单元其本轮红与绿都不进任何层结论（§6.1），读者能看到"内容红了，但这条红来自一条不可信的门"。

### 3.4 降级语义（合法降级的三条同时成立）

一次降级合法，当且仅当：**(a)** 由显式旗标或显式配置触发（不是"依赖没找到就顺手少查一点"）；**(b)** 落结构化证据：结论 JSON 里 `degraded: {face, reason, effect}` 三件齐备；**(c)** 不改变科学语义（不减少被检对象、不放宽阈值、不把缺失当为零）。

- 降级单元在轮级汇总里计入 `degraded[]`，`release` 层要求 `degraded` 中不含任何 `object_class ∈ {product, contract}` 的门。
- 负例：把某产品门对"缺失 manifest"的处置从判红改为按零处理 ⇒ 该门的 `--self-test` 里对应负例必红（`ENGINEERING_SPEC §10`："文件不存在"按"无违规"通过即假绿）。
- 禁止的降级形态（写成硬约束）：把"没跑"降级为"跑了且绿"；把"判不了"降级为"跳过且整轮 rc=0"；把"输入为空"降级为"无违规"。

### 3.5 注册表字段扩表的死结与拆法（实现约束）

校验器对字段是**严格白名单**：`step` 出现未登记字段 ⇒ `R2 unexpected fields` 红；顶层字段同样严格。因此"给注册表加新字段"不可能先于"校验器与 schema 认识该字段"落地。拆法（对应 §2.6 第 2 批）：schema 增字段 + `STEP_OPT_FIELDS` 增字段 + 执行器读该字段 + 数据回填 + 校验器把该字段升为必填，五件事在**同一提交**内成对完成；期间不允许出现"字段可选但文档已称必填"的中间态（该中间态本身由 `GATE-CLAUSE-MAP` 判红：文档说必填而 schema 标可选 ⇒ 红）。

## 4 受影响验证范围如何由改动集计算

### 4.1 改动集（保留现有口径，唯一实现点）

改动集 = `git diff --name-only <base>` ∪ `git status --porcelain=v1 --untracked-files=all` 的路径集，统一为仓库相对 POSIX 路径；`--base` 默认 `HEAD`。基线 ref 不存在 / 仓库不可用 / 路径不可解析 ⇒ **runner error（rc=2）**，绝不允许"空改动集 ⇒ 全绿"（`CI_SPEC §2.2`）。

三条路径形态判据（进 `GATE-IMPACT-COVERAGE`）：

1. 注册表里所有 `changed_paths` / `inputs` / `outputs` 必须是仓库相对 POSIX 路径、无 `..`、无绝对路径（既有 R13 保留）；
2. 每个 `changed_paths` glob 的基目录必须存在（既有 `CHK-PATH-DOMAIN-ANCHORS` 保留，其家族前缀预留面必须显式登记且自带棘轮判据）；
3. **覆盖完备性**：跟踪集里每个文件必须被至少一条在册单元的 `changed_paths` 命中，否则该文件属"改了没有任何门会跑"——按目录族逐族登记，未登记即红。这条把"覆盖面只增不减"从口号变成机器面：新增目录而未登记 ⇒ 红；删除目录而登记未回收 ⇒ 由锚存活判红。

### 4.2 选中集 = 三源并集（只增不减）

| 源 | 判据 | 载体 |
|---|---|---|
| 路径域 | 改动集 ∩ 单元 `changed_paths` ≠ ∅ | 注册表字段 |
| 影响映射 | 改动命中 `impact_map.json` 的某条规则 ⇒ 选中其 `checks`；命中 `base_checks`/`fallback` 语义不变 | `eng/ci/impact_map.json` |
| 构建图 | 运行 ctest 的单元声明 `ctest_targets`，与受影响 target 集相交才入选；受影响集由 `ninja -t deps` + `build.ninja` 边反查 | `eng/ci/incremental.py` |

三源**并集**，不做交集裁剪（宁可多跑）。增量档总预算超出即判红并提示"应拆分"，不许靠放宽判据或 skip 换速度（`CI_SPEC §2.6` 的代价条款保留）。

### 4.3 强制升级与 fail-closed 三条（保留 + 补一条）

| # | 条件 | 处置 |
|---|---|---|
| 1 | 改动集中存在不匹配任何 `changed_paths` 的文件 | 红 `UNCOVERED_CHANGED_PATHS`，逐条点名（保留） |
| 2 | 改动命中全局敏感面（`eng/ci/**`、`eng/cmake/**`、根 `CMakeLists.txt`、`CMakePresets.json`、`lib/include/**`、`eng/contracts/**`、`eng/packaging/config/**`、`docs/DOCUMENT_INDEX.yaml`） | 自动升级 `scope=full` 并打印命中项（保留）。**新增**：敏感面清单的唯一载体是注册表顶层字段，文档只写判据不抄清单；新增门禁基建目录未登记进敏感面 ⇒ 红 |
| 3 | 改动集非空而选中数为 0 | 红 `EMPTY_SELECTION`（保留） |
| 4 | **新增** 任一 scope 下有效执行数 = 0 | 红（§2.3，跨 scope 一条判据） |

### 4.4 全量必须显式，发布必须全量

- `full` 只能由 `--all` / `--full` / 敏感面升级 / 定时任务产生；结果 JSON 顶层 `scope` 如实登记，"看起来像全量其实不是"即判红（`CI_SPEC §2.1` 的这句现在是实现选择，重建后成为判据：`scope=full` 而选中单元数 < 注册表该平台成员数 ⇒ 红）；
- `release` 层结论只在 `scope=full` 且 `tier=measure` 的运行里合成；`explicit` 运行永远不出发布结论（即便全绿）。

## 5 并行判据互不污染采样

### 5.1 三道调度保留，独占依据改为字段

执行器的三道（独占道 / 并行道 / 末位屏障 `reads_run_results`）与资源键互斥（`outputs` ∪ `--build-dir` ∪ `--test-dir` ∪ `--work-dir`）保留为正本。两处订正：

1. **独占依据不能是命令文本**。现在 `step_is_exclusive` 用"命令里含 `resource_monitor.py`/`run_monitored.py`"判定，于是把监控包装从命令里删掉就静默失去隔离，而 CPU 利用率判据照旧出绿。改为：`requires_monitor=true` ⇒ 独占；且注册表门核对"`requires_monitor=true` 的门其 `outputs` 必须含监控证据 JSON"。负例：删掉某监控门的 `resource_monitor.py` 包装 ⇒ 注册表门红（今天：静默并行、采样互相污染、利用率仍判绿）。
2. **跨注册项的并发必须显式**。执行器对每个注册项内部并行，项间串行；若将来项间并行，独占道必须升到"整轮互斥"级别，且这条约束要在 `CI_SPEC` 写明（当前规范未定义项间并发语义，属规范缺口，重建时补一句"项间默认串行，独占道在整轮内互斥"）。

### 5.2 测量类判据的自证负例

所有出"利用率/内存/吞吐"结论的门，其 `--self-test` 必须包含一条**并发污染负例**：在同一沙箱里并发跑两个采样者并断言此时判据不得为绿（或显式 `not_applicable`，且 `not_applicable` 在 `release` 层按红处理，见 `CI_SPEC §9.2` 的既有分类）。这条把"互不污染"从调度器的实现性质升级为被测性质。

### 5.3 独占资源与重计算看门狗

`heavy`/`requires_monitor` 单元必须由资源监控包装执行（既有 R7 `heavy ⇒ requires_monitor` 保留，方向补齐见 §5.1 第 1 条）。生产侧内存看门狗的调用参数不在本件规定（属 `AGENTS.md §3` 与 `eng/tools/monitoring/mem_guard.py` 的运营口径），但门禁侧要求：**监控证据缺失即红**，不得因"忘了套看门狗"而降级为绿（既有语义，保留）。

## 6 结果纪律

### 6.1 一次"绿"的合成条件（唯一口径）

轮级 `verdict=PASS` 当且仅当同时满足：

1. `failures = 0`（`FAIL*`、`TIMEOUT`、`CRASH`、`FAIL(scope)`、`FAIL(inputs_*)`、`FAIL(missing_output)`、`FAIL(empty_outputs)`、`FAIL(monitor_gate_missing)` 全算）；
2. **有效执行数 > 0**（§2.3），且每个被声称"已验证"的层满足其 §1.4 下限；
3. `trust_void = 0`（§3.3：门崩时它给的红和绿都不算证据——它既不贡献 failures 也不贡献绿的集合，且必须把整轮结论降为不可信）；
4. `not_effective = 0`（对 `release` 层；其它层允许 > 0 但必须逐条点名，不得沉默）；
5. 对 `object_class ∈ {product, build}` 的门，若整轮该类别有效执行为 0 ⇒ 不得合成"产品/发布可用"（§1.5）。

结果 JSON 顶层字段随之扩为：`scope`、`tier`、`platform`、`effective_executions`、`not_effective[]`、`reused[]`、`degraded[]`、`trust_void[]`、`zero_skip: bool`、`layers: {layer: {effective, red, not_effective, trust_void}}`。"零豁免、零跳过的结论以实际输出为准"由此成为读者一次读字段即可核对的事，而不是要读者自己从 counts 里推。

### 6.2 三张放行面各自的纪律

| 面 | 目标态规则 | 负例（注入什么必红） |
|---|---|---|
| 豁免 `exemptions.json` | 红灯不以 waiver 静默覆盖：豁免条目必须带 `{id, reason, approved_by, granted, expires}` 五件；过期即红；`high_water.max_entries` 只减不增；**P0 门不得豁免**（现值：豁免 0 条，且 `known_failures` 内无任何门级红——这一面如实成立，保留） | 给一条 P0 门登记豁免 ⇒ 注册表门红；豁免条目缺 `expires` ⇒ 红；条目数 > 高水位 ⇒ 红 |
| `waivable` | P0 ⇒ `waivable: false`（`validate_registry.py` 新规则 R16，读 `01_CHECKS.md §2` 的"门禁"列）。现例：真实数据端到端门在文档里标 P0、注册表里 `waivable: true`，于是一次 rc=0 的运行里它可以从未执行过 | 把任一 P0 行对应项改成 `waivable: true` ⇒ 注册表门红 |
| `known_failures.json` | 已知失败仍判红（`KNOWN_FAIL` 不洗绿，保留外层语义）；条目必须带条件与到期核对；不得用该面登记门级红以绕开 P0 | 往该面塞一条 `CHK-*` 门级条目 ⇒ 红（该面只允许 ctest 用例级，理由须在条目里写明） |

**SKIP 不计通过**（标准 05 §6）：任何把 SKIP 计入通过率的汇总式（含人类读的 `gates-summary.md`）都不允许；`SILENT_OK_UNITS` 白名单冻结为现两员（`API-DOCS`、`UNIT-CLOSURE`），新增即红——该白名单本身要有一条负例证明它按 ID 生效而非全局兜底（执行器自测里已有这一形态，保留并纳入普查）。

### 6.3 证据纪律

1. **结构化证据**：凡判"结论"的门（输出"合规/违规/通过/失败"的门），其 `outputs` 必须含一份结论 JSON，字段至少 `{gate_id, verdict, n_objects, findings[], degraded, head_sha}`；只打印一行 `OK: 0 violations` 不满足（现 155/370 单元 `outputs` 为空，runner 对零证据的唯一防线是"stdout 或 stderr 至少一行非空"，任何一句打印即满足）。
2. **证据归属唯一**：一个 `outputs` 路径只能被一个执行单元登记。现例：某口径一致性门的自检单元登记了该门本体的证据路径 ⇒ 自检的"证据存在"是本体跑过留下的，属证据互串（普查中唯一一例，改成自检写自己的 `*-selftest.json`）。负例：给两个单元登记同一路径 ⇒ 注册表门红。
3. **白名单不得吞掉登记义务**：判"结论"的门若既无 `outputs` 又不在 `SILENT_OK_UNITS`，注册表门红（对应 §6.3 第 1 条）。
4. **证据必须可再生**：任何被文档/合同引用为证据的文件，必须有一条在册单元声明它是自己的 `outputs`。禁止"在册证据由无入口的脚本产出"（现例：一份极性普查证据的 `generated_by` 指向一个在注册表、workflow、step 面全部零命中的死件；该证据不可再生、不可复核）。处置只有两条：把该脚本接成在册门，或撤下其证据面。

### 6.4 回放与现算必须同面（专治"只回放归档件"母题）

| 类型 | 允许读什么 | 判据 |
|---|---|---|
| 现算门 | 本轮或指定轮的产品树，且 `inputs` 声明该树 | 树缺失 ⇒ `FAIL(inputs_missing)`；不允许静默改用归档 |
| 回放门 | 跟踪件里的归档证据 | 必须显式 `mode=replay`，其结论只能表述为"历史证据在当前判据下应为红/绿"，不得表述为"当前产品正确" |
| 端到端/视觉层门 | **本轮现算产出的产品树** | 若该树无任何在册单元产出，判红并点名"输入无生产者"（`GATE-INPUT-PRODUCER`，§8 清单项） |

**`GATE-INPUT-PRODUCER` 的判据**：对每个 `object_class = product` 的单元，其 `inputs` 里每条路径必须能被解析为"同档或前置档某个在册单元的 `outputs`"或"显式登记的只读数据集（`testdata/**`、`gaia/**`）"；两者皆非 ⇒ 红。正例：端到端门的输入是本轮上游单元登记的 `p3_verify.json`。负例：把输入改成硬编码的某历史轮次目录名（今天真实存在的形态：某端到端门的校验模式读一个硬编码历史轮次目录，而注册表里没有任何单元产出它；某视觉层门的产物模式读 `run/ci/` 下一个无生产者的目录）⇒ 红。这条同时消灭"从目录名派生判据集合，干净克隆上失明或恒红"这一母题的门禁侧形态。

### 6.5 数值口径纪律（文档里不许有手抄的测量值）

规范与说明文档里**禁止出现绝对计数与阈值读数**（"N 个执行单元 / M 个注册项 / K 个适用面"这类），一律写成"以注册表现算为准 + 生成命令指针"；具体读数只能出现在带 `head_sha` 的跟踪证据件里，并由 `GATE-EVIDENCE-FRESHNESS` 核对：证据的 `head_sha` 与被声明对应的登记面（注册表文件哈希）一致，不一致即红。

- 依据：登记门禁事实的两处文档计数（230/78/226 与"8 检查/11 单元"）与注册表现值（150/370/366/13）已全量漂移，且其中一处自称"生成自 `eng/ci/checks.json`"却少列 2 个单元；同一普查的注册命令其实每轮在现值上重跑，只是产物落 gitignore 目录——所以缺陷不是"门不跑"，是**跟踪件与文档的数字停在历史读数**，修成"让门重跑"无效。
- 判据：文档里出现"整数 + 个执行单元/个注册项/个适用面"形态的字面量 ⇒ 红，并给出行号与替代写法（`GATE-NO-HAND-COPIED-NUMBERS`，§8 清单项）。
- 负例：在 `03_GATES.md` 抄一句"对 N 个执行单元注入三面" ⇒ 红。正例：句子写成"对 `index_steps()` 的全部单元注入，读数见本轮证据 JSON"。
- 例外（必须显式）：**阈值**若本身是合同数值（如 L2 四条冻结判据、接缝门限），其唯一数值源是 `eng/contracts/**`，文档只写语义与来源指针；这类不算手抄读数。

### 6.6 性能门真实判红

利用率、内存、热点、比值/斜率类门必须"越界即红"，不许"只记录不裁决"。已成立面保留为范本：真实重计算面利用率门的两态断言（忙碌态必须 rc=0 且判绿、串行注入态必须 rc=10 且判红，且同时核对监控 rc 与 `frozen_gate.verdict` 双件）、L2 冻结判据回放（历史 `verdict=pass` 的违规证据现在必须判红）、worker 均衡指标判别力自测（退化派生件/恒定序列必须红）。所有阈值以 `eng/contracts/resource_gate_v1.json` 为唯一数值源，不得在门内写字面量副本。

## 7 门与文档口径的映射原则

### 7.1 一条门 ↔ 一条口径

- 每个执行单元登记字段 `clause = {doc, section, title}`（三者齐备）。`doc` 是被检口径所在文档的仓库相对路径，`section` 是节号，`title` 是该节标题原文。
- 校验用**号—标题双要素**（与《索引重建规格》C7/C8 同一判据形状，共用实现）：节号必须实存，且登记标题与该节标题去空白后逐字相等；只给号不给标题即红。这条专治"挂错节也能长绿"的既有形态（同一仓内曾出现 73 条把机制挂到号对但标题错的节上）。
- 一个门不得登记多条口径（多口径必拆门）；一条口径允许多个门（分层覆盖），但反向覆盖判据要求：每条被索引登记的正本口径要么有门引用它，要么在文档侧显式登记 `无门覆盖：<理由>`，两者皆无 ⇒ 红。

### 7.2 登记面唯一：文档表由注册表生成

- `docs/ci/01_CHECKS.md §2` 的表体（ID / 类别 / 命令 / 门禁级 / 判据对象 / 层 / 档 / 对应口径）由生成器从 `checks.json` 现算产出；文档正文其余部分（原则、退役契约、分级定义）人写。
- 校验器 `--check` 模式逐字比较生成结果与文档现状，任何手工漂移即红；`§2.1` 的退役契约与 RESERVED 表仍人写并单独受 `DOC-*` 锚门管。
- 这直接消灭"注册未登记 / 文档承诺无实现"这一对差集的一半：8 个在册项在文档集零登记、291 个 step 不在任何映射面、4 个 step 靠散文出现被误当登记——这些形态在"文档表是派生物"之后不再可能出现。
- 双向一致门的判据面从"顶层 ID × 表首列"改为"执行单元 ID × 生成行"，粒度对齐到执行单元（这是对现有 `CHK-REGISTRY-DOC-SYNC` 的改造方向，见清单）。

### 7.3 口径变更如何强制同步

| 变更 | 强制机制 | 失败表现 |
|---|---|---|
| 文档节被删/改号/改标题 | 该节被任一门的 `clause` 引用 ⇒ 锚门红；被索引引用 ⇒ 索引门红 | 红，点名是哪条门的哪条口径 |
| 门改判据语义不改文档 | `clause` 所指节的正文含"判据/通过条件"表述与门的证据字段名不符 ⇒ 由 `GATE-CLAUSE-MAP` 的字段名词表核对判红（只比字段名集合，不比长句，避免复述口径句子） | 红 |
| 新增门 | 同提交内必须有 `clause` + `negative` + 生成器重跑后的文档行 | 注册表门红（缺任一字段） |
| 删除门 | 走退役契约（无参打印退役标识 exit 2、原实现留显式入口、`--self-test` 在位），并在 `id_migration_map.json` 登记去向 | 命名面/锚门红 |
| 阈值变更 | 唯一数值源文件改 + 科学阈值正本（`docs/algorithms/GATES_AND_TOLERANCES.md`）同批改 | 阈值对照门红（既有门的职责） |

**谁登记**：门的作者（开发节点的实现任务）在实现同一提交内登记 `clause`/`negative`/`object_class`；审查节点只核对，不代登。理由：口径与判据必须同手，否则登记面变成第二套真相（标准 05 §1"门禁设计独立于被检验代码的作者视角"约束的是**判据内容**，不约束登记动作）。

### 7.4 与文档包侧门的分工（不开第二套表）

- 文档层门（`DOC-INDEX`、`ALG-LINE-ANCHORS`、`CHK-DOC-HYGIENE`、`GATE-NO-HAND-COPIED-NUMBERS` 等）按《索引重建规格》C1–C12 执行，本件不重复其判据；
- 门禁层新增的注册表属性**一律进 `eng/ci/checks.json` + `eng/ci/checks.schema.json`**，由 `CHK-REGISTRY-VALIDATE` 校验。禁止为门禁属性另立 JSON 台账——"唯一源"类判据最常见的失效形态就是判据自己开了第二套表。已存在的台账类只有在其对象不是注册项时才合法（如 ctest 冻结目标基线、mutation 门登记册、命名面保留类）；
- 反向要求：新增登记面必须回答"它和哪个已有面不同对象"，答不出即并入已有面。

### 7.5 追溯映射的落位

机制 ↔ 门 ↔ 证据 的映射正本 = `docs/traceability/`（《目标文档架构》§3.2 已定该角色格）。本件的 `clause` 字段提供"门 ↔ 口径"半边，"口径 ↔ 证据"半边由追溯登记面承载；两者不互抄，追溯面只写指针。

### 7.6 写法判据的词表（收《索引重建规格》C11 的移交）

C11 要求"正文无日期、无流水号、无 commit/散列字面量、开头无元信息块；命中即红并给行号"，把词表留给本件定。词表是判据的输入面，必须固定登记、不得现算自目录：

| 类别 | 命中形态（逐条封闭枚举） | 适用层 |
|---|---|---|
| 日期 | `YYYY-MM-DD`、`YYYY/MM/DD`、`YYYY 年 M 月 D 日`、`MM-DD` 独立出现、`Q[1-4] 2025|2026` | 仅正式文档层：`docs/**` 与仓库根 `*_SPEC.md`、`ASTROCS_DESIGN.md`、`AGENTS.md` |
| 流水号/工作项 | `[A-Z]{2,6}-\d{2,6}`（排除：`SCI-`/`ALG-`/`DISP-`/`CFG-`/`IO-`/`FATDUCK-` 等**在册标识**，其唯一词表 = `docs/DOCUMENT_INDEX.yaml` 登记的 ID 命名空间面）、`任务编号[:：]`、`工单`、`回执` | 同上 |
| commit/散列 | 40 位或 7–12 位十六进制独立 token；`sha256[:=]` 后随字面量（字段名允许，值不允许） | 同上 |
| 元信息块 | 文件前 5 行内出现 `状态:`、`版本:`、`日期:`、`作者:`、`ID:` 形式的键值行 | 同上 |
| 历史叙事 | `此前`、`曾经`、`已作废为`、`历史上` 与"某轮次名 + 曾"的组合（只判形态，不判语义，避免误伤科学文档里的对照句） | 同上 |
| 豁免面 | `docs/research/**`、`docs/references/**`、`artifacts/**`、`实验/**/results/**`、`工程控制/**`、`docs/ci/01_CHECKS.md §2.1` 的退役登记 | 这些位置以任务编号/过程为主键，按《总目录》§3"写法判据按层施加，不跨层套用"处理，改判为"角色错放/缺处置登记" |

- 负例：在任一 `docs/ci/*.md` 正文加一行「> 状态: FROZEN 〈一个日期字面量〉」 ⇒ 红并给行号。
- 正例：同样内容写进 `artifacts/evidence/**` 的证据件 ⇒ 绿。
- 守卫：词表为空（解析后规则数为 0）⇒ 红，禁止"词表读不到就当全部合规"。

## 8 判别力普查：谁测 runner、谁测门

现有那道被称作"全门禁 fail-closed 普查"的门，其三面注入全部作用在同一个共享判定函数上，注入物是它自造的沙箱目录与一份硬编码坏证据字面量，**被普查单元的命令从未执行**（文件级事实：无 `subprocess` 族，import 面只有标准库 + 该共享函数）。它判"某门通过普查"的充要条件是一个纯元数据谓词（"该单元声明了 outputs"或"outputs 空且非 waivable"），与该门实现读什么、能不能抓缺陷无因果；把任意门的实现整段删空、判据换成 `print("PASS")`，普查表一字不变。因此本体系把它拆成两道各判各的门：

### 8.1 `GATE-RUNNER-EVIDENCE-CONTRACT`（如实改名，职责收窄）

- 对象：执行器自身的证据裁决管道（缺失证据 / 坏证据 / 无输出三面对共享判定函数的反应）。
- 名号必须与对象相称：门名、`--md-out` 表头、`docs/ci/03_GATES.md`、`docs/ci/01_CHECKS.md` 四处一律写"runner 证据管道契约普查"，且它在 `03_GATES.md §3` 的"阻塞合并"含义限定为"runner 契约红"，**不得**被读作"全部门禁判别力已核"。
- 它的自测不得再把"没有 failures"同时充当"跑通"与"无假绿"两件事：拆成结构断言（跑通、单元数 = 实算值）与内容断言（逐条点名哪个面给了什么判定）。
- 它的豁免分支必须被自己的负例触及：`SILENT_OK_UNITS` 名单、`waivable`、`path_exists` 的 glob 三条分支各一条注入，缺一即该门的 `kind=exemption` 面不成立（这是本仓已有的纪律，只是过去只有执行器自己做到了）。

### 8.2 `GATE-DISCRIMINATION-SURVEY`（新门：逐门真跑注入普查）

合格定义七条，逐条都是判据：

| # | 要求 | 判据实现 | 不满足时 |
|---|---|---|---|
| S1 | 对象是被普查的门 | 对每个在册单元：物化其 `negative` 登记的注入命令，**真跑**（子进程），断言 rc≠0 且判词点名该门的真实对象 | 记 `not_covered`，不计入通过 |
| S2 | 同时验证绿 | 未注入时同一命令必须 rc=0（防"一律判红"的假门） | 该门记 `trust_void` |
| S3 | 负例落在该门自己的豁免/兜底分支 | `negative` 里必须有一条 `expects: red-through-exemption`：构造一条"会被本门白名单/降级分支放行"的违规，断言仍红 | 记"fail-open 面未覆盖"，不得计入通过 |
| S4 | 面归属与执行器同源 | 单元集合取自 `index_steps()`（含字段解析），并断言"普查读到的强制面 == 执行器实际会强制的面"；今日真实分叉面 = 2 个单元（面 A/面 C 互换）+ 逐字段的 9 处 `requires_monitor` 等补齐，全部列为该项的验收负例 | 普查本身判红 |
| S5 | 规模锚用实算值 | 断言 `units == len(index_steps(registry))`，或 `>=` 登记高水位且只增不减并留痕；禁止任何无来源魔数阈值 | 红 |
| S6 | 内容级负例 | 把某个真门的判据函数换成恒绿（只换它，不换共享函数），普查必须点名**该门**；今天的注入点是共享函数本身，等价于把自己的总分擦掉再证明能发现分数被擦 | 红 |
| S7 | 产物可核 | 普查结果落跟踪件并带 `head_sha` 与注册表哈希；`GATE-EVIDENCE-FRESHNESS` 核对读数与现算一致 | 红 |

- 沙箱要求：注入命令必须接受根重定向（`--root`/`--repo`），普查在临时副本里跑，绝不写仓库跟踪件。可行性核对：128 个在册 `check_*.py` 里 121 个的 argparse 面已含 `--root`/`--repo` 类旗标（口径：文件内出现该字面量；逐门实际可用性由 S1 真跑验证，未通过者进 §9 第 3 批改造名单）。不接受根重定向的门 ⇒ 注册表门判红并要求改造或标注为"不可普查"，后者一律出绿资格（Q2）。
- 与已有 mutation 登记册的关系：`eng/ci/mutation_gates.json` 的对象是**科学缺陷注入**（近似实现被抓没有），不是**门禁判别力**（门能不能抓到东西）。两者对象不同，因此两张面都合法；普查门不吞并它，也不引用它作为"门有牙"的证据。

### 8.3 普查的分档

| 档 | 内容 | 触发 |
|---|---|---|
| 快速 | 只跑 `negative` 的 self-test 面（不起构建、不碰真实数据） | `quick` 档每次 |
| 测量 | 全单元真跑注入 + S4/S6/S7 | `push main`、每日、`release` 前 |

## 9 落地顺序（给开发节点的可执行批次）

每批一个原子提交序列，**批次内顺序不可换**；每批的"完成判据"都是可跑的红或绿，不依赖声明。

| 批 | 内容 | 完成判据（必须能红） |
|---|---|---|
| G0 | 注册表字段扩表：`layer`/`tier`/`object_class`/`clause`/`negative`/`crash_declared`/`allowed_platforms`；schema + 校验器 + 执行器三方同批，字段先可选 | 注入"字段名拼错"⇒ 校验器红；缺字段 ⇒ 此批不红（过渡态） |

## 10 覆盖率自报、未覆盖项与需实跑才立证的部分

### 10.1 本件覆盖

### 10.2 本件未覆盖（显式登记，不静默丢弃）

1. **单元/模块层的具体测试内容**：本件规定"每层必须有下限数量的有效执行"，不规定哪些函数该有单测（属实施任务书与 `docs/plugins/**` 的端口面）；
