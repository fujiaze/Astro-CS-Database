# 门禁现状与旧门禁处置

本件对在册门禁给出处置结论与理由（标准 05 §7 第 3 项），重点是**哪些门必须删除或改造之后才被允许计入"绿"**，以及删除/改造之间的先后依赖怎么拆。逐条门的检验对象、命令、判据与正负例在《门禁清单.csv》，本件不复述判据正文。

依据：《门禁重建设计原则》（标准 05）§2/§3/§5/§6/§7；《门禁现状审计》28 条结论与其逐条处置表；《门禁入口复核》两条确认与三处数字订正；`docs/ci/CI_SPEC.md` §2/§4/§9；`docs/ci/01_CHECKS.md` §1/§2/§2.1/§3；`docs/ci/03_GATES.md` §1/§3/§5/§6；`ENGINEERING_SPEC.md` §10；《目标文档架构》§4；《索引重建规格》§1/§6/§7。

## 0 处置口径

### 0.1 四档处置定义

| 档 | 含义 | 判定入口 |
|---|---|---|
| 保留 | 判据、对象、负例三面已成立，只做登记面回填（新字段、文档行） | 满足 §0.2 三条资格且无 §1 名单命中 |
| 改造 | 判据方向正确但**绿不具证据资格**（对象错位、零执行可记绿、无负例、无证据、结论写死） | 命中 §1 任一类 |
| 合并 | 与其它门同一对象同一判据，或它的价值是另一条门的用例载体 | 与另一条门的 clause + 对象集完全重合 |
| 退役/删除 | 判据对象已不在库内、无任何调用方与文档点名、或职责被新门吞并 | 标准 05 §5 孤儿定案三选一 |

### 0.2 "允许计入绿"的三条资格（与《门禁体系设计》§0.2 同一套）

Q1 读真实对象且对象类别如实登记；Q2 有可执行注入负例且至少一条穿过自身豁免分支；Q3 本轮是否执行、执行了几个对象、判了什么值可从跟踪证据复算。**三条缺任一条，该门本轮的红与绿都不进任何层的结论**，只登记为 `not_effective` 或 `trust_void`。

## 1 必须删除或改造后才允许计入"绿"的门

判定式：一条门若其"绿"可以在**它从未检验任何东西**的情况下产生，它现在就是假绿授权面，必须先改造再计入结论。按机理分五类。

### 1.1 入口与判定面：整批零执行仍返回 0

| 对象 | 为什么它的绿不算证据 | 处置 | 改造后的判据 |
|---|---|---|---|
| 唯一执行器的汇总式（原 `run_checks.py` 判定链） | 全部单元 `SKIPPED*` 时 failures 为空 ⇒ verdict=PASS ⇒ rc=0；`FAIL_VERDICTS` 恰不含任何 SKIP 与 `PASS(reused_fingerprint)` | **改造**（不退役：它是唯一执行器的宿主） | 跨 scope 的零有效执行判红（清单 `GATE-ZERO-EFFECTIVE`）；判词逐条点名未生效原因 |
| 外层入口（原 `run.py`） | 它自己有"零有效执行不得判 PASS"的三分支守卫，但对 71 个聚合项它只把 `run_checks.py --check <ID>` 当一条命令跑 ⇒ **守卫在外层、洞在被它嵌套的那一层**，覆盖面 291/370 单元；另有 `FATDUCK_PENDING` 这一"rc=0 且有效执行为空"的字面出口 | **退役其裁决路径**（保留被单测引用的选择函数，迁入共享模块） | 入口唯一化（设计件 §2.2）；rc=0 的非 PASS 态一律禁止 |
| 23 个可整项全跳的注册项（`CHK-BUILD-LINUX`、`CHK-NWORKER`、`CHK-P3-EXPORT-STREAM-RSS`、`CHK-P3-PROJ-DECL`、`CHK-P3-PROJ-DECL-SELFTEST`、`CHK-PKG-CONSISTENCY`、`CHK-PLUGIN-SYMBOL-CLOSURE`、`CHK-SYNTH-P1`、`CHK-SYNTH-P3` 等 9 项为文档处方且 P0；23 项里共 20 项在文档标 P0） | 数据本身不坏（platform 登记正确），坏在**入口对"整项没跑"给 rc=0**；注册表写 `waivable: false` 的 P0 门照样被记成一次 PASS（平台判定在 waivable 判定之前） | **保留（数据不动）+ 由入口改造统一收口** | 点名这些项必须 rc≠0；不在文档里逐条加限定语（那是第二套口径） |
| `CHK-REALDATA-E2E` | 文档标 P0 而注册表 `waivable: true` ⇒ 前置或平台任一不满足即 `SKIPPED(waivable)`，P0 门可在一次 rc=0 的运行里从未执行；同时它是真实数据端到端（L3 的唯一产品级证据） | **改造** | P0 ⇒ `waivable: false`；数据集缺失走 `optional_inputs` ⇒ `not_effective`（不是绿），并由 release 层红来逼出实跑 |
| `CHK-ALGO-WIRING` | `platform: linux` 与 `profiles: [windows-main]` 并存且 `waivable: false` ⇒ 同一注册项在 Windows CI 必判 FAIL(prerequisite)、在人工面判 rc=0，两列今天互相打脸 | **改造（纯数据）** | `GATE-PROFILE-PLATFORM` 上线同批修数据 |
| `CHK-COVERAGE` / `CHK-SANITIZER` / `RESOURCE-GATE-REAL(-NEG)` / `CHK-SPARSE-PUNCH-PROBE` 等平台单向项 | 同 1.1 第 3 行的入口面问题；另 P2 报告项的"绿"被计入层结论 | **改造（表述与档）** | 报告类只记 `produced`，不进达标分子 |

### 1.2 结构在、对象不对（本类必须删或改造，否则整类门的绿都是虚假授权）

1. **`CHK-FAILCLOSED-SURVEY`（现名"全门禁 fail-closed 普查"）**——三项证据：全文件无 `subprocess` 族 ⇒ 被普查单元的命令从未执行；三面注入全部作用在同一个共享判定函数上，注入物是它自造的沙箱与一份硬编码坏证据字面量；"某门通过普查"的充要条件是注册表两列的形状谓词，与该门读什么、能不能抓缺陷无因果。把任意门的实现删空、判据换成 `print("PASS")`，普查表一字不变。
   处置：**拆分 + 名号订正**。收窄为 `GATE-RUNNER-EVIDENCE-CONTRACT`（只测执行器自己的证据管道，且三条豁免分支各带负例），另建 `GATE-DISCRIMINATION-SURVEY`（逐门真跑注入，S1–S7）。
   落地边界（否则会被误做成"让门重跑就行"）：注册命令本身是现算的（只有 `--json-out`、无 `--md-out`），CI 每天在 370 单元上重跑并 rc=0，但产物落 gitignore 的 `run/`；停在跟踪件与两份文档里的读数（230/78/226）才是历史快照。**缺陷不是门不跑，是它跑的东西不检验任何门，而跟踪证据与文档数字停在旧读数。**
   连带订正：其自测 G1 的两个合取中，`units > 50` 是**无来源魔数**（脚本与归档件同一次落地，当时观测量为 230，50 从未等于任何已知读数），不是"把历史观测量抄成阈值"；`not failures` 拿普查自己的 0 红当自己的正例（循环自证）。改法：单元数改实算相等或单调棘轮；"跑通"与"判别力"拆成两条断言。
2. **`CHK-REGISTRY-DOC-SYNC`（注册表 ↔ 文档双向一致）**——名字承诺双向一致，实现在"顶层 ID × §2 表首列"这一个笛卡尔子集上：基线上必判红（8 个在册项在文档集零登记，其中 7 个在 `docs/**` 零出现），而 287 个 step ID 不在任何映射面上（4 个靠散文出现仍不算登记），命令列与实际入口是否同串完全不核。
   处置：**退役 + 替换**。文档表体改为注册表派生物（`GATE-DOC-TABLE-GENERATED`），粒度对齐执行单元；口径映射另立（`GATE-CLAUSE-MAP`）。它的 4 个执行单元逐个登记去向。同批吞掉两类既有断言：`注册项待写入 ⟹ 该 ID 不得在册`（现有一处文档与注册表互相矛盾而无门可见）、门禁级列 ⟹ `waivable` 一致（见 1.1）。
3. **`eng/tools/check_p1_symbol_map.py` + `lib/phase1_session/README.md` §7 点名**——README 以现在时向下游声明"该模块的符号映射完整性有机器判据"，而该脚本 (a) 从未在册、(b) 模块级读一个已随归档提交删除的文件 ⇒ 一跑即在 import 期抛异常、(c) 判据对象已不在库内：**三重虚假授权**。另 `docs/ci/01_CHECKS.md §2.1` 把它分类为"非检查器（无判据、无退出码语义）"，而该文件本体明写三条判据并有非零出口 ⇒ 分类不成立。
   处置：**两处同提交删除**（删 README 点名行 + 删脚本 + 订正分类理由）。拆开做必红（见 §4.2 第 3 例）。
4. **`eng/ci/polarity_evidence.json` 与其署名生成者 `polarity_probe.py`**——一份在册证据的 `generated_by` 指向一个在注册表、workflow、step 面与 import 面全部零命中的死件 ⇒ 该证据**不可再生、不可复核**；`reconcile_state.py`、`verify_ciqa_report.py` 同类。
   处置：`polarity_probe` 优先**改造后注册**（它的"逐门真跑命令"探针面正是 1.2 第 1 项缺的那一层），另两件退役或删除并撤其证据面。禁止"保留证据、不保留生产者"。
5. **端到端门的回放形态**——某端到端链门的登记命令是校验模式，读一个**硬编码的某历史轮次目录**，而注册表里没有任何单元产出该树；某视觉层门的产物单元同样读 `run/ci/` 下一个无生产者的目录。干净克隆上它们要么红（判据本身 fail-closed，方向安全）、要么被人工塞进目录后"绿"（结论无对应现算）。
   处置：**改造**（`GATE-INPUT-PRODUCER` + 命令面改为现算产出 + inputs 登记生产者）。这类不删判据，删的是"输入可以来自任何目录名"的自由度。

### 1.3 证据面缺口：绿只有 rc 没有读数的门

| 面 | 现状 | 处置 |
|---|---|---|
| 零登记证据的单元 | 155/370 无 `outputs`；runner 对零证据的唯一防线是"stdout 或 stderr 至少一行非空" ⇒ 任何一句 `print("OK: 0 violations")` 即满足留痕 | 判"结论"的门必须带结构化结论 JSON（`GATE-EVIDENCE-OWNERSHIP`）；`SILENT_OK_UNITS` 两员冻结，新增即红 |
| 证据归属互串 | 全表唯一一例：某口径一致性门的自检单元登记了本体的证据路径 ⇒ 自检的"证据在场"是本体跑过留下的 | 改造：自检写自己的证据件；一条路径只允许一个单元登记 |
| 静默通过白名单 | 按 ID 生效、面很小（2 员），执行器自测已能证明不是全局兜底 | 保留（并把该写法推广为普查 S3 的范本） |
| 无生产者输入 | 见 1.2 第 5 项 | 新增判据 |

### 1.4 数值口径漂移：把历史读数当现状的门与文档

- 两处登记"门禁事实"的文档句子与注册表现值全量漂移（规模读数 +140 单元 / +72 注册项；一处自称"生成自 `eng/ci/checks.json`"的对照表少列 2 个单元）；四条"无适用面"清单逐字相同 ⇒ **漂移只在总量，不在结构**。
- 处置：文档删绝对计数、只留判据与生成命令（`GATE-NO-HAND-COPIED-NUMBERS`），读数进带 `head_sha` 的跟踪证据并由 `GATE-EVIDENCE-FRESHNESS` 核对；证据落位从"某个固定历史轮次目录"改为"每轮 `run/` + 稳定证据锚"。
- 连带：凡引用旧普查跟踪件作为现状的结论（含对外与对上材料、以及本包内对该普查的自引）一律降级为"历史读数"，不作证据；旧件保留不删（它是恒真门被改真判红这一事实的唯一见证）。

## 2 批量规则（其余在册项不逐条判，按规则归类）

在册 150 个顶层项 / 370 个执行单元中，本包**实际读过实现体或判据面**者才在本件 §3 逐个定案；其余按下表批量归类。**批量结论的效力低于逐个定案**：开发节点在 G0/G1 回填字段时若发现某单元不满足其批次前提，必须就地降级并登记，不得沿用批次结论。

| 规则 | 适用面（按命令形态与对象分类，单元数按继承解析后现算） | 批量结论 | 例外处置 |
|---|---|---|---|
| B1 | ctest 单目标族（共用同一目标驱动，116 个单元） | 保留：驱动侧零命中守卫方向正确且覆盖 46+ 单元，是全仓最重要的一类守卫 | 登记 `shared_driver` 并在汇总面按驱动去重报"独立判据数"；两侧方言（登记 glob × 命令正则）做集合等价校验 |
| B2 | unittest discover 族（45 个单元） | 保留：用例采集数>0 与"直跑脚本必须贡献用例"的守卫已成立 | 必须落机器可读结果件；逐文件独立进程跑的做法推广（整目录 discover 的绿可能是路径顺序副作用） |
| B3 | 单脚本直跑族（183 个单元，其中 77 有 outputs、9 有 inputs） | 批量改造：五字段（inputs/outputs/object_class/clause/negative）回填 + 证据归属唯一 + 命令须接受根重定向才能被普查 | 不满足 Q1–Q3 者定案：改造或降级 `fixture-only`；降级者不得进 e2e/visual/release |
| B4 | 文档/文本一致性族（读 docs/** 或根规范，约 98 个脚本面） | 批量改造：判据集合必须来自固定枚举或跟踪集登记文件；同 clause 重复判定者合并 | 从目录名/文件名现算判据集合者一律改造（干净克隆上失明或恒红的根因族） |
| B5 | 已按退役契约处置的 10 件 | 保留退役态、不计入在册门总数 | 见 §1.5 的两处订正（不合规件与同名件） |
| B6 | 既未点名、也无普查覆盖其判据语义者 | **待定案**，不得当作"已审"或"已绿" | 在 §1.1 名单内的由入口改造统一收口，不逐个判 |

**"独立裁判数"的正确算法**（写死，防 370 冒充 370 个裁判）：`独立判据数 = 按 (shared_driver, clause) 去重后的单元数`。该值必须出现在 `gates-summary` 与 `03_GATES.md` 的生成面里，且不得由人抄。

## 3 逐项结论（标准 05 §7 第 3 项格式）

理由列回指本件类别（§1.x）或《门禁清单.csv》对应行；不重复判据正文。

| 对象 | 处置 | 理由 | 前置依赖 |
|---|---|---|---|

## 4 删除与改造的先后依赖（死结与拆法）

**总规则**：一条判据从"数据不存在"到"enforce"之间，**中间态不得落 main**。凡"改 A 会让 B 红、改 B 会让 A 红"的成对动作，必须在同一原子提交里完成；判据本身可以分两态上线（见 §4.3），但两态的切换点必须与数据回填同批。

### 4.1 字段白名单死结（最高频，必须先拆）

注册表校验器对字段是**严格白名单**：顶层与 step 出现未登记字段即 `unexpected fields` 红；同时合同 `checks.schema.json` 的 step `required` 与执行器的继承面各自决定"缺字段怎么办"，三侧今天不同向。因此：

| 顺序 | 动作 | 若先做会怎样 |
|---|---|---|
| 1 | schema + `STEP_OPT_FIELDS`/`OPT_STR_LIST_FIELDS` + 执行器读取路径三处同批改，字段先"可选但合法" | 只改注册表数据 ⇒ R2 红（未知字段）；只改校验器 ⇒ 数据没有该字段、判据恒绿或恒红 |
| 2 | 逐单元回填全字段（370 行）并**同批**删除执行器的继承路径 | 先删继承 ⇒ 2 处 `outputs`、9 处 `requires_monitor`、3 处 `heavy`、2 处 `waivable`、2 处 `mutates_workspace`、2 处 `changed_paths` 的补齐面瞬间消失，普查与证据面同时错位 |
| 3 | 把字段升为 required（校验器 + schema 同批） | 先升必填 ⇒ 未回填的行全红 |

### 4.2 其它成对依赖（逐例给死结与拆法）

1. **先改数据还是先改门（waivable）**：把 8 个 `waivable=true` 中的 P0 项（含真实数据端到端门）直接改成 `false`，会在缺前置的机器上立刻 `FAIL(prerequisite)` ⇒ 整轮红 ⇒ 现场反应是"把判据放宽回去"。**拆法**：`waivable=false` 必须与"`not_effective` 语义 + `optional_inputs` 面 + release 层对 `not_effective` 的红"同批落；红的位置从"该项红"移到"release 层缺产品级证据"，才不会被当成噪声关掉。
2. **入口切换 vs 外层独有守卫**：workflow 改指唯一执行器之前，外层独有的三条守卫（零有效执行、fatduck 语义、HARD_FAILURE 值集）必须已全部迁入共享模块并被内层调用；否则切入口当天 CI 失去保护。**拆法**：G1（共享模块）先于 G3（切入口），且 G1 的验收判据就是"两入口对同一注入情形给出同一 verdict+rc"。
3. **README 点名行 vs 脚本文件**：只删脚本 ⇒ 文档指针悬空，文档索引门红；只删点名 ⇒ 死件留在跟踪集且不在任何面上（正是本次要防的形态）。**拆法**：两处同提交，且同批改 `docs/ci/01_CHECKS.md §2.1` 的分类理由与悬空台账条目（`dangling_ledger.json` 里已登记它 ⇒ 台账回收也在此批）。
4. **ID 退役/改名 vs 命名面与迁移映射**：改任何 ID（含把普查门改名）若不同批登记 `eng/ci/id_migration_map.json`、改 `01_CHECKS.md` 行、改所有 `changed_paths`/`inputs` 里的旧引用 ⇒ `CHK-NAMING-SURFACE` 的 R1/R5 与锚门立即红。**拆法**：改名批 = 迁移映射 + 生成器重跑 + 引用回查（"收口不改指"是本仓已定的判据）。
5. **R12 反转 vs 聚合项顶层 command**：顶层 `command` 是 required 字段，直接删聚合项的 command ⇒ R2 缺字段红。**拆法**：先在校验器里让"有 steps 的项可免 command"（与执行器不再依赖顶层 command 同批），再把 71 个顶层 command 清掉，最后把 R12 换成 R12b。
6. **普查改名 vs 四处名号**：门名、`--md-out` 表头、`03_GATES.md`、`01_CHECKS.md` 四处必须同批改，否则"出现全门禁字样即红"这条判据会先把改到一半的自己判红。
7. **末位聚合判据 vs 档位重排**：既有的"某档末位必须是聚合型基线门"判据（R10）与 `reads_run_results` 屏障绑定；若为修 §1.2 的档位问题（把超档单元移出 fast）而重排成员，末位可能不再是它 ⇒ 立刻红。**拆法**：档位重提批必须显式复核末位约束并同步 R10 的判据对象。
8. **文档表切生成器 vs 现状差集**：生成器第一次跑必然与现状不等（缺 8 行 + step 粒度）。**拆法**：第一提交 `--write` + 提交消息逐条列补了哪些行；此后 `--check` 才成为 enforce 面。禁止"先开 enforce 再补数据"（会把已知缺登记变成未知噪声）。

### 4.3 新门的 enforce 两态规则（有界，不是缓兵）

| 态 | 允许用于 | 不允许用于 | 退出条件 |
|---|---|---|---|
| `report-only`（出清单不判红，结果落证据件） | 判据依赖尚不存在的数据回填类：档位预算（需实测墙钟）、改动集覆盖完备（需先出未覆盖族清单） | **裁决面**（零有效执行、崩溃分离、豁免纪律）与普查面（S1–S7）——它们先 enforce，否则又造出一批"在跑但不判"的门 | 一次批次内转 enforce；未转即视为该门未完成，不计入门总数 |

`report-only` 是降级，因此必须满足 §3.4 的三条：显式（注册表字段 `state: report-only`）、可溯（清单落跟踪证据）、不改语义（期间不得把该面的"无红"读成"已核"）。
