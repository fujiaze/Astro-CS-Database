### CR-240-03 · 本文件 I/O 薄转发层把三种失败压成同一个 `false`，删除失败返回值被丢弃
- 轴：R
- 位点：`:184-186` `inline bool write_atomic(const std::string& p, const std::string& text) { return aio_atomic::write_file_atomic(p, text, nullptr) == 0; }`；`:190-192` `inline void remove(const std::string& p) { (void)aio_atomic::remove_file(p); }`；`:175` `return aio_atomic::path_exists(p, nullptr) != 0;`
- 上位依据：`ASTROCS_DESIGN.md §9.73 裁决 U5`（§7.2 记 exit 10＝磁盘满、§10 记磁盘满是失败瞬间分类）；`lib/infrastructure/aio/src/aio_disk_full.h:10-13` 明写「错误码 = Windows `GetLastError()` / POSIX `errno`（0 = 未知）」——底层**提供**了可区分 errno；`docs/contracts/DATA_P2_HIPS.md §7.2` 的"磁盘满＝产品未发布"主张依赖能区分"满"与"其它 I/O 失败"。
- 现状：`write_file_atomic` 的具体 errno（ENOSPC vs EACCES vs EPERM）与"哪个 staged 文件没删掉"在本层被折叠成单个 `bool`/`void`，调用点再也拿不到 errno；`path_exists` 无法区分"不存在"与"stat 失败（EACCES/EINVAL）"，两者都 `return 0`⇒`exists()==false`。
- 差在哪：本层的职责是薄转发（:171 自述"零策略/零缓存/零语义"），但把错误信息**有损压缩**正是加了一层语义；且 `(void)` 丢弃返回码使"清理未成功"对上层完全不可见。
- 后果：磁盘满场景若调用点只看 `bool` 再自行分类，分类信息缺失即退化为笼统 I/O 错误（弱化的"产品未发布"归因）；`exists()` 把权限类 stat 失败报成"不存在"，可让"缺产物"与"产物存在但不可读"走同一条兜底分支。具体是否发生要看调用点分支，本段范围内未见消费点。
- 定级：S3
- 怎么算修好：`write_atomic`/`remove`/`file_size` 增传出参或返回带 errno 的小结构；`remove` 至少把非零码向上冒（清理失败要么记日志要么判红，不得 `(void)`）；`path_exists` 与 `stat 失败` 分开。改时须同批给 `run_checks` 里"磁盘满分类"门补一条注入 ENOSPC 的正例，否则该门会因签名变化判红。
- 置信：PARTIAL（未逐一取证段外调用点是否二次分类；单条 finding 取证已用 6 条命令）
