### AUD401-001 · lib 顶层：算法并联面基本成立，但有三处结构性破口

## 三、我证伪了任务书的哪个前提

1. **"p3_projection.cpp 在跟踪面但不在生产构建图"的表述不成立——它在构建图内**。真实情况是：它被 `eng/tests/unit/CMakeLists.txt:1424-1426` 的测试 target 直接列源编译，`lib/algorithms/projection/CMakeLists.txt` 也确实只声明 `p3_wcs.cpp`。正确判据是"不在生产 target"而非"不在构建图"。按此重算，同型情形的规模是 **10 条（测试独占的非测试目录 TU）+ 31 条（完全无 target）**，而不是"还有没有第二处、第三处"的开放问——第二处是 `p3_proj_v6.cpp`（同目录），第三处起是 `executor.cpp`、`snr_estimator.cpp`、`hips_core.c`、`ahpx` 三件、`p3_v6_export.cpp`（见表 2.2B）。
2. **"phase1/2/3_session 被生产入口调用没有"的前提隐含"它们在生产链上、只是该退役"**。实测相反：三会话**都不在生产调用面**——`p1_session` 连工厂注册都没有（`P1Api` 全仓 0 引用），`p2/p3_session` 只挂在两个 ID 错为 `astrocs.phase{2,3}.resample` 的注册项上，而生产 IR 从不引用这两个 ID（仓库台账 `registry_ir_parity.json` 自证"永不被调度"）。因此整改的主动作是**删除注册 + 退役目录**，不是"接线"。
3. **"阶段名不该出现在代码目录上"这一改动面比任务书设想的小，但比标准04 允许的更宽**。目录层的阶段名只有 3 个 session 目录 + `wrapper_phase1`×6 + `integration/v6_phase1`；阶段名真正密集的地方是 **CMake target 名（22 个）**与文件名（81 个）。同时最高设计 §8.4:637/:655 **明文允许** `lib/phase{1,2,3}_session` 目录存在，与标准04 §1:20 的"归并后退役"直接冲突——任务书把这个当成既有共识，实际是两个权威的打架，必须上呈裁决而不是默认按标准04 执行。
4. **"三阶段实例是否真不共享内存/会话/运行时状态、内存管线是否各自一套"的提问方式预设了三条内存管线的存在**。实测：一次调用单阶段单 Runtime ⇒ 隔离成立；但**三阶段一条内存管线都没有**（生产节点间走 `output_dir` 文件约定，`BlockFrame`/`StageBlockFlow`/`PipelineFrame` 两套实现都无生产消费者）。所以该项答案是"不成立但原因不同：不是各自一套，是零套"。
5. **任务书预设"noise_snr 有两份噪声模型实现待收口"的旧叙述仍在生效**。实际 `CMakeLists.txt:327-339` 记录 §9.67 定案 3 已把 `wrapper_phase1/noise_model.cpp` 判退、现跟踪面只剩 `cpp/src/noise_model.cpp` 一份（`git ls-files | grep noise_model` 实证）；同一文件 `:320-325` 的旧叙述未清理（AUD401-020）。按旧文去找第二份会得出错误结论。
6. **任务书把 `lib/` 下 11 个旧顶层目录（astro_image_io/calibration/common/healpix_db/phase2/plate_solve/…共约 2800 文件）当作潜在架构违规面**。它们全部在 `.gitignore` 内、0 跟踪、内容是历史构建产物（DLL、build 目录、第三方 eigen 副本），按"只审跟踪内容"口径不入立案，仅在此登记为环境噪声。
