### CR-67-05 · 本头自称的 host 服务清单有 9 项，实际总表 `acs_host_api_v1` 只有 7 项：`metrics` 与 `progress` 两项被点名却完全没有 ABI 面
- 轴：D（设计符合：点名能力未实现）
- 位点：`lib/include/astrocs/abi/host_api_v1.h:10-13`

  ```
   * 服务清单（12 §3 + 03_TARGET §4 + ARC-001 host service 列表）:
   *   allocator / logger / metrics / cancel / progress /
   *   executor+thread budget / artifact+manifest(data services) /
   *   config query / registry query(只读)。
  ```
  对照同文件 :75-95 的结构体成员：`head / allocator / logger / cancel / executor / artifacts / config_query / registry_lookup_module` —— **无 metrics 服务、无 progress 服务**。
- 上位依据：`docs/contracts/ARCH-001.md:44` 依赖图把 services 列为 `logger/metrics/resources/artifacts` 四类；`docs/contracts/API-001.md` §3（:53）冻结的**运行事件流**必含 `kind` 枚举 `progress/resource/artifact/backend/final/stage_start/stage_end`（progress 是对外的唯一事件种类之一）。即：metrics 与 progress 在上位合同里都是被点名的对外面。
- 现状：全仓检索 `acs_metrics_v1|acs_progress_v1|metrics_report|progress_report` → **零命中**（检索式即该四个词的 alternation，作用域整个跟踪集）；`ACS_METRIC_*` 五个枚举值除本头声明外**无任何使用点**（同一次检索的 `ACS_METRIC_` 命中仅 host_api_v1.h:36-40 自身）。也就是说模块侧既拿不到上报计数器入口，也拿不到进度回调入口。
- 后果：(1) "模块在计划期声明要上报的计数"（:34 原话）这条能力在 ABI 面不成立，`ACS_METRIC_*` 成为恒不消费的枚举；(2) 运行事件流的 `progress` 类事件无法由模块驱动——真实模块的科学进度（如逐帧/逐 CCD 完成度）只能由 host 猜测或不发，`ASTROCS_DESIGN.md` §7.2 的事件流对外面在含模块的阶段是残缺的；(3) metrics 缺位在 `ARCH-001` 依赖图被列为服务，等于构建图承诺了接口面没有的东西。
- 定级：S2（不产生产物字节错值；触发路径不到产品 ⇒ 按前言硬门槛不升 S1。缺"运行时触发路径到产物"的一跳）
- 怎么算修好：要么补 `const acs_metrics_v1* metrics;` + `const acs_progress_v1* progress;`（含 `counter_add(id, delta)` / `report(fraction, stage)` 成员，按 `status_codes.h` 规则带 `acs_head`），并把 `ACS_METRIC_*` 接到 metrics 服务；要么把 :10-13 的服务清单与 :34 的"计划期声明上报"注释删到与实际表一致——**删注释与删枚举必须同批**，且要一并检查 `eng/contracts/config/module_lifecycle_contract.schema.json` 与 `docs/api/COMMON_ABI_V1.md` 是否把 metrics/progress 登记为在途合同项（否则文档面继续虚标）。
- 置信：CONFIRMED（服务表逐字段清点 + 全仓零命中检索式已给）

### CR-67-20 · backend 自检失败码两歧：legacy 族 ABI 宣称 5，模块族契约定 9；实际 loader 对任一非 OK 都退 baseline，造成“自我门”对外失效
- 轴：C（同一事件取不同码），副轴 R
- 位点：`lib/include/astrocs/common_abi_v1.h:161`

  ```
  	acs_status (*self_test)(const astrocs_host_services_v1* host);  /* 失败→5, 不得运行 */
  ```
- 上位依据：模块族 ABI 与机器合同共同冻结 `ACS_ERR_SELFTEST=9`（`module_api_v1.h:124` / `lifecycle_v1.h:232` / `module_lifecycle_contract.schema.json:60`）；loader 侧处理逻辑在 `lib/infrastructure/benchmark/backend_host/backend_loader.cpp:184-187`：`if (... self_test(...) != ACS_OK) { ... return FALLBACK_BASELINE; }` —— **不论返回码几，只要非 0 即降级为 baseline**，不会返回 `ACS_ERR_SELFTEST(9)` 给上层。
- 现状：两条路说的两件事：(a) ABI 文档说"失败→5"，5=UNSUPPORTED，理论应走 fallback；(b) module 契约说"失败→9，不得运行"，应拒载；(c) loader 实际实现：任何 fail → FALLBACK_BASELINE（继续跑 baseline）。因此对外主张的"self-test 失败不得运行"在 backend 通道上不成立：它会**降级的**（偏绿）。
- 后果：一个自检失败（如 AVX-512 kernel 算错）的 backend 会被静默降级为 baseline 并继续参与生产执行，这既掩盖了 backend 缺陷（测试没抓出"不得运行"的门），又让"self-test 门"的对外主张无法验证。更糟的是，如果 baseline 也被选不上（极端 case），则生产完全不可用，但目前只见过退化路径。
- 定级：S2（触发路径到产品字节需再走一行 profile 生成器或生产调度器，本批清单不含这两部分，故按前言硬门槛不升 S1）
- 怎么算修好：统一为 `ACS_ERR_SELFTEST=9`，并在 loader 增加 `case ACS_ERR_SELFTEST` 分支，将失败直接拒绝（不再 FALLBACK_BASELINE），并在 `module_lifecycle_contract.schema.json` error_mapping 中补充这条；同批改 backend 族头注释，删除「失败→5」。
- 置信：CONFIRMED（两处 ABI 原文 + loader 源文均已逐字读到）

### CR-67-21 · legacy ABI (common_abi_v1.h) 与 modular ABI (abi/*.h) 两套并行的 C 接口，width/name/model 均不同且无一致性机器门
- 轴：C（代码／合同／schema 说的不是同一个）
- 位点：`lib/include/astrocs/common_abi_v1.h`（legacy）与 `lib/include/astrocs/abi/artifact_api_v1.h/host_api_v1.h/module_api_v1.h/status_codes.h`（modular）
- 上位依据：status_codes.h:25-29「兼容说明（与 legacy astrocs/common_abi_v1.h）:本头族与 legacy 单头共享基础类型名（acs_head / acs_status / acs_span 系列 / acs_allocator 及数值），语义与数值与 legacy 冻结一致（v1 互操作：acs_status 数值位图相同，ACS_ERR_EXCEPTION=10 为本层新增，legacy 不产生该值）。二者不得在同一 TU 混合 include（legacy 随模块迁移退役，ABI-002/006 处理收编）」；CR-67-02 已指出 "ARC-001 FORBID-002, 03_TARGET §4" / "12 DLL_ABI_AND_LOADER" / "tasks/02_ABI_BUILD_CLI_TASKS" 三份控制包规范不在跟踪集 ⇒ 无法核对"兼容说明"的真实性。
- 现状（同一概念的四处差异）：
  - allocator：legacy `acs_allocator` (struct_size+abi_version 两裸 uint32)  vs modular `acs_allocator_v1` (含 `acs_head head` 成员)；两者都有但名字不同，且 modular 的 `host_api_v1` 用指针注入，legacy 的 `astrocs_host_services_v1` 用值注入（字段内嵌）。
  - precision/determinism: modular uint32 枚举 vs legacy uint8 enum；数值相同但类型宽度不同，layout 不一致。
  - entry point: modular `astrocs_module_query_v1` / `astrocs_provider_query_v1` vs legacy `astrocs_backend_get_api_v1`。

### CR-67-22 · fixed-length char buffers (science_contract_id[32]/backend_id[48]...) 无长度上限检查与 NUL 终止保护，静默截断后 strlen 可能越界
- 轴：R（运行时正确：未定义行为），副轴 C
- 位点：`lib/include/astrocs/common_abi_v1.h:126-131`

  ```
  	char     science_contract_id[32];   /* 如 "ALG-P3-003"; NUL 结尾 */
  	char     algorithm_id[32];
  	char     kernel_version[16];
  ```
- 上位依据：`status_codes.h:12`「跨 DLL 边界类型白名单:……长度显式 UTF-8 span」——字符串必须带显式长度，而不是依赖 NUL 终止 C string（后者不安全、易越界）。
- 现状：buffer 大小写死，但无任何 `sizeof(name) <= strlen(...)` 的检查，也没有在注释中给出"最长 X 字符"的上限与超长的响应策略（截断？返回 ACS_ERR_PARAM？）。`ACS_KERNEL_ENTRY(sci_id,alg_id,ver,...)` 宏直接把 C 字面量塞进去，若字面量长度超过 buffer，C 标准下 char 数组初始化会丢掉多余的字符且不保证 NUL（`char a[3]="abcd"` 合法但不 NUL terminated），随后 `strlen` 会越过 buffer。
- 后果：若某 provider 的实际名称超过 32/16 字符，manifest/provenance 中会出现截断后的短名，甚至因缺 NUL 而触发 UB（crash 或错名进下游 JSON）。**这是能把产物数据读错的一类**。方向：**偏绿**（不会报错，只会错名）。当前唯一在役的 ID 都很短（ALG-xxx），所以尚未暴露，但 latent。
- 定级：S2（当前 no-op，但有潜藏风险；需要找到超长名称的生产用例才能写出触发路径）
- 怎么算修好：(a) 改为 `acs_str_v1`（带长度）; (b) 或至少加静态断言 `sizeof(k) <= 32`（对字面常量）并修改 `ACS_KERNEL_ENTRY` 宏做边界检查（compile-time assert on sizeof(string)+1 ≤ buffer）。
- 置信：CONFIRMED（静态分析得出；缺 runtime 用例）

### CR-67-23 · `nested_parallel_allowed` / `aliasing_contract` / `precision_class` / `determinism_class` 四个字段从未被任何 gate 读取，backend 可以谎报而不被发现
- 轴：R（运行时正确：gate 缺失），副轴 D
- 位点：`lib/include/astrocs/common_abi_v1.h:152-158`
- 上位依据：`docs/standards/CONCURRENCY_STANDARD.md:20-21`「生产并行默认确定性：相同输入 → 相同输出；浮点累积顺序固定」、「线程数：外部可配置，默认 min(可用核，配置上限)」；`docs/contracts/RT-001.md` 提到 "resource_class must match descriptor" 的校验责任，但未指定如何校验 `nested_parallel_allowed`。
- 现状：全仓检索 `nested_parallel_allowed|aliasing_contract` 的 consumption 为零：只在赋值处出现（`backend_table.inc:90-91` 写 `=0`），没有被任何 `if (...) == 1` 或 switch 分支用到。这意味着：(1) 若某 backend 设置 `nested_parallel_allowed=1`，runtime 不会阻止嵌套并行；(2) `aliasing_contract=1` 允许重叠读写，但调度器不知道，可能导致数据竞争。同时 `precision_class` 和 `determinism_class` 也从未被读取（只有 `plan_estimator.cpp:131` 使用 `execution_class` 但没有 `precision_class` 的消费）。
- 后果：这些字段的声明与实现在 ABI 层面脱节，成为“名义上的合同”，可以被 backend 随意篡改而不受惩罚。**偏绿**：允许说谎。由于它们目前都是硬件相关的属性，且生产环境不会主动查询，因此当前不产生产物错值，但一旦被某些新功能引用（比如引入基于 determinism_class 的路由策略），就会出现隐蔽的错误。
- 定级：S2（写不出到产品字节的触发路径：当前无 gate 读取这些字段，所以即使被篡改也不会触发；但若将来引入门，就可能暴露）
- 怎么算修好：要么删除这四个字段（它们实际上未被消费），要么在 loader/scheduler 处增加对应的消费门，并确保每个 field 都有明确的“如何判定/如何响应”的策略。否则这些字段会成为虚假承诺。
- 置信：PARTIAL（缺：未遍历 scheduler/loaders 全部路径，检索式仅覆盖 lib/目录；若 CLI 内部有隐藏消费者则需要补检）

## #1 · backend 自检失败码两歧：legacy ABI 说 5，模块 ABI 说 9；loader 对任一非 OK 都退 baseline，导致“自测门”对外失效（偏绿）

**影响**: 新版模块按合同尾扩一个字段后，旧 loader 握手失败（`ACS_ERR_ABI_MISMATCH`），破坏"旧/新双向兼容"承诺；虽不致产物错值但使 ABI 尾扩机制失效。
