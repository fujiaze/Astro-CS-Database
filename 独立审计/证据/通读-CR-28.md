### 1.3 Findings

### CR-28-1 · 该接缝把 aio 返回的全部 errno 就地丢弃，使设计"日志写失败即运行失败"在 ipv 侧根本无法成立
- 轴：R（主）+ C
- 位点：
  - `lib/algorithms/platesolve/cpp/ipv/src/ipv_log_sink.h:35` `aio_atomic::AppendSink* h = aio_atomic::append_open(path, nullptr);`

  - 同文件 `:51` `if (sink && sink->handle) (void)aio_atomic::append_flush(sink->handle);`

- 上位依据：`ASTROCS_DESIGN.md:534`「**日志写入失败即运行失败**（非 0 退出码），不静默」；`ASTROCS_DESIGN.md:520`「每个失败都产生稳定错误码（空 catch、**忽略返回码**、只写日志、降级为"警告后继续"四类形态都无错误码，属未传播）」；`docs/design/LOG_AND_ERROR_SYSTEM.md:125`「写失败 ⇒ 记 stderr 摘要 + **置运行失败标志**，运行结束以非 0 退出」与 `:129`「日志写失败一律显式」；被调方契约 `lib/infrastructure/aio/src/aio_atomic_file.h:208-209`「append_write 返回 0 成功 / errno；append_close 返回 0 或 errno」，且 `aio_atomic_file.h:288`「返回原始系统错误码…**策略**(状态码映射)留给调用方」。
- 现状：四个接缝函数的返回类型全部是 `void`（`ipv_log.h:49-52` 的声明面同样没有错误出参），`append_write/flush/close` 的返回被 `(void)` 丢弃或直接不调用返回值，`append_open` 的 `err` 出参被传 `nullptr`（连失败原因字符串都不取）。调用侧 `ipv::Logger::init`（ipv_log.h:68-77）只看 `sink_` 是否为空来置 `enabled_`，此后任何一次 write/flush 返回 ENOSPC/EIO 都不改变 `enabled_`、不置任何失败标志。
- 差在哪：aio 明确把"errno→状态码"的策略层留给调用方，而本文件正是 ipv 唯一的调用方策略层——它选择了零策略，于是"忽略返回码"这一设计点名的未传播形态在这里是**结构性必然**，不是偶发疏漏。
- 后果：两处对外主张失真——(a) §7.3 的"日志写入失败即运行失败"在 ipv 模块无法被实现（没有任何一条通道能把失败上抛到退出码）；(b) 盘满时（AGENTS.md §3 记录本机 `run/` 单轮端到端可达数十 GiB、盘满会伪装成随机故障）ipv 日志会在无提示的情况下停止增长，证据文件看似存在实则半截。缓解项须如实记：`ipv_log.h:118` 有 stderr 镜像，所以行内容不丢，丢的是"落盘成功与否"这一状态本身。
- 定级：**S2**。触发链已逐跳写出（见下），但不进产品字节、不改任何数值，故不升 S1。生产触发链（legacy orchestrator 路径）：`lib/infrastructure/pipeline/orchestrator/cpp/src/orchestrator.cpp:1967-1969`（`log_dir = project_root_dir_ + "/run/logs/plate_solve"`，非空）→ `ipv_solver.cpp:411`（`params.log_dir` 非空判据）→ `ipv_solver.cpp:416` `logger_.init(dir + "/ipv_solver.log")` → `ipv_log.h:68` `sink_ = log_sink_open(path)` → 本文件 `:35`。
