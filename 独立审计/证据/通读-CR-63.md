### CR-63-18 · 枚举自称"数值不对外承诺稳定性"，而两处 C ABI 出口把 0/1 当合同值硬写进文件头的 dtype 字段
- 轴：C（主）／R
- 位点：`astro_scalar.h:26` `// - 数值不对外承诺稳定性, 比较请使用枚举常量而非魔法数字`；反例位点：`lib/infrastructure/aio/src/aio_fits.cpp:877` `out->dtype = 1;  // FP64 (与 AstroScalarType::FP64 一致)`、`:909` `out->dtype = 0;  // FP32 (与 AstroScalarType::FP32 一致)`、`aio_xisf.cpp:589`/`:616` 同形两处

- 差在哪：同一件事（dtype 线上编码）一侧说"不承诺"、另一侧按"承诺"使用，且没有任何机器锚（断言/合同表）把它们钉在一起。

### CR-63-19 · 两个运行时查询用"非 FP32 即 FP64"的三元式，非法 dtype 被报成合法的 float64/8 字节
- 轴：R
- 位点：`:68` `return (t == AstroScalarType::FP32) ? "float32" : "float64";`；`:76` `return (t == AstroScalarType::FP32) ? 4 : 8;`
- 上位依据：`:73` 该函数的自述用途——"用于**缓冲区分配**、**ABI 校验**等需要**精确**字节数的场景"；`:26` "比较请使用枚举常量"（本函数只与 FP32 比较，把 FP64 当成 else 而非显式常量）。条文面对"非法 dtype 标签如何报告"零规定；合同 dtype 域实际有三个值（`phase_product_exchange.schema.json:165` `["float32","float64","u8"]`）。
- 现状：`uint8_t` 底层枚举可由外部输入（配置文件/文件头/Python 侧）落成 2…255 任一值，`static_cast` 即得；此时 `astro_scalar_type_name()` 返回 `"float64"`、`astro_scalar_type_size()` 返回 `8`，两者都是**合法外观**的答值；`precision_context.h:45,48` 的 `scalar_size()/scalar_name()` 原样透传给消费者。
- 差在哪：一个声明"用于 ABI 校验"的函数对非法输入不产生任何异常信号，只产生一个自洽的（且与真实数据不符的）答案；且第三档 `u8` 在本头文件里根本无法表达，任何 u8 载荷经此路径会被报成 float64。

- 定级：S2（本文件内两个函数无生产调用者直达磁盘边界：`astro_scalar_type_size` 的唯一 lib 消费者是 `precision_context.h:45`，我未追到它是否由文件头/配置驱动 ⇒ 缺完整触发跳）
- 怎么算修好：`astro_scalar_type_name` 非法返回 `nullptr`（或 `"unknown"`）；`astro_scalar_type_size` 非法返回 `0`（0 步长无法被误当合法解释）；两处都改成对两个枚举常量的显式比较＋穷尽 else；若 `u8` 需要 ABI 表达，就在枚举里显式加值并同时处理 CR-63-18 的线上编码（同改，否则加了 `U8=2` 会让现有"else 即 FP64"的调用面全部读错）。
