### CR-30-01 · oracle 的方窗高斯通量少了一个因子 2，导致 mag 期望系统性偏亮 0.75 mag
- 轴：R（主轴）＋ S
- 位点：`lib/algorithms/star_detection/tests/p1star/p1star_oracle.hpp:49`
  ```cpp
  return amp * M_PI * sigma * sigma * ex * ex;
  ```
- 上位依据：`docs/algorithms/STAR_DETECTION_ALGORITHMS.md:108`「(2R+1)² 用候选 R（钳 [5,200]）与候选中心；`box_sum≤0 → mag=NaN`」＋ `docs/contracts/DATA_SEMANTICS.md:902`「正常星=−2.5·log10(Σ_box(pixel−B_fit))」——即 oracle 要复算的是「方窗内模型像素和」。夹具 `p1star_fixtures.hpp:79` 逐字为 `s.amp * std::exp(-(dx * dx + dy * dy) / (2.0 * s.sigma * s.sigma))`，`amp` 为**峰值振幅**（`p1star_fixtures.hpp:34` 注释「峰值振幅 (bg 之上)」）。
- 现状：`gaussian_flux_in_box` 返回 `A·π σ²·erf(R/(σ√2))²`。正确闭式：∫₋ᴿᴿ e^(−x²/2σ²)dx = σ√(2π)·erf(R/(σ√2))，二维可分离平方后 = **2π**σ²·A·erf²。**文件内部自证**：同文件 L31 `gaussian_flux_analytic = A·2πσ²` 是本函数 R→∞（erf→1）的极限，两者相差恰为 2 倍；注释 L47 又写 `√(π/2)σ`（平方得 (π/2)σ²），与代码 (πσ²)、与真值 (2πσ²) 三者互不相同。
- 差在哪：被用作期望值的解析式少一半，不是精度问题而是定义错误。
- 后果：`p1star_tests_core.cpp:659-660` 的 `m_exp = oracle::magnitude(amp * gaussian_flux_in_box(1.0, σ, 6.0))` 偏差恰为 −2.5·log10(2) = **0.7526 mag**（相对 flux 因子 2）。任何以该期望为准的 mag 断言要么恒红（说明该断言从未在 CI 通过），要么被放到能吞 0.75 mag 的宽度（说明 mag 语义实际未被约束）。两种情形都使「mag 由合同 §2 定义并被独立复算核对」这条对外主张失去证据。**本项在 file 3（core.cpp:605-710）读毕后定案是哪种。**
- 定级：S2（缺生产触发路径——本文件为测试件，不进产品字节；测试期望值本身按 §4 不报缺陷，但**期望式的数学错误**属可辩护指控）
- 怎么算修好：L49 改 `2.0 * M_PI`；L47 注释同步为 `σ√(2π)·erf(··)` 的平方；同批必须核对 `core.cpp:659` 的容差与 `6.0`（R）与生产 box 语义一致（R=max(ceil(3.7172·Sr),…,5) 钳 [5,200]，不是硬编 6），否则改对期望反而判红。

## 2.2 findings

### CR-30-04 · 故障注入用双向翻转 `ok = !ok`，一个 ambient／错位的注入名可把真实失败翻成"ok"⇒误绿；同谱系两篇均为单向强制判失败
- 轴：R（主轴）＋ C
- 位点：`p1star_test_main.hpp:55-58`
  ```cpp
        if (fault_hit(name)) {
            ok = !ok;
            std::printf("FAULT-INJECT %s\n", name);
        }
  ```
  对照同谱系实现 `lib/algorithms/calibration/tests/p1cal/p1cal_test_main.hpp:53-56`：
  ```cpp
        } else if (faultname != nullptr &&
                   p1cal::FaultRegistry::instance().injected(faultname)) { \
            (cs).note_injected(faultname);                                 \
            ++(cs).failures;                                               \
  ```
  （`eng/tests/unit/p1wcs/p1wcs_test_main.hpp:155-160` 同形；`git grep -ln "ok = !ok" -- lib` 全仓仅命中本文件一处。）
- 上位依据：`eng/contracts/data/aio_abi_contract_v1.json:163`「每个注册名使对应断言确定性翻转并输出 FAULT-INJECT 行（**验收：注入必败**，不存在恒 PASS 占位）」；本文件头注 L9-11「命中的 CHECK 断言翻转 (通过→失败) 并打印 "FAULT-INJECT <name>"; 自检组用它演示"注入必败", **其余组在无注入时必须全绿**」。
- 现状：`record()` 对 `fault_hit(name)` 的站点执行逻辑非，把头注承诺的方向（"通过→失败"）实现为**无方向**的双射：cond 为真→假，cond 为假→**真**。匹配按名字面量精确比对（L49），不校验该站点当前是否 PASS，也不校验名字是否存在。
- 差在哪：判据方向已定死——翻转算符把「真实失败的断言」变成 `ok` 并按通过计数，`cs.failures` 不增（`core.cpp:471` 型 `return cs.failures == 0 ? 0 : 1;` ⇒ rc=0）。因此一条 ambient 的 `ASTROCS_P1STAR_FAULT=<恰好在红的断言名>` 使 ctest 全绿。而 core 三组的注册位（`CMakeLists.txt:85-89`）只设 `OMP_NUM_THREADS=1`，**不清除** `ASTROCS_P1STAR_FAULT`，继承面敞开；selfcheck 那两站之所以能证明机制，是因为它显式 `unsetenv` 并要求基线先全绿。
- 后果：①「注入必败／无恒 PASS 占位」这条合同验收在被注入站点已经红的时候**不成立**（此时注入反而把它改绿）；②真实回归＋同名注入位残留 = 机器门假绿，掩盖的正是 P1-STAR 五组的全部断言面。按已登记的上游结论（`artifacts/evidence/audit-2026-01/OWNER_DECISIONS.md:182`：注入名全集 501 名／787 站，其中 226 站的注入名是变量而非字面量，CI 真驱动仅 2 名 ≈ 0.4%），CI 侧几乎不驱动注入，故本缺陷的**现实暴露面**主要是"环境残留"而非"日常使用"，这也是它长期未被观察到的原因。
- 定级：S2（写得出 CI/ctest 入口到此的逐跳路径，但**不改产品字节**；触发需环境预置同名注入位，非生产常态 ⇒ 不升 S1）
- 怎么算修好：①L56 改单向 `ok = false;`（与 p1cal/p1ws 同形），保留 FAULT-INJECT 打印；②未命中的注入名必须报错：`CheckState` 记录"已消费"集合，组结束时对未消费的注入名 `++failures` 或返回 2；③`CMakeLists.txt:82-89` 三组注册位补 `ASTROCS_P1STAR_FAULT=` 显式置空（与 :159 一致）。**必须同批**：`p1star_tests_selfcheck.cpp` 阶段 2/3 的判据按新语义仍成立（基线先全绿⇒翻转与强制失败等价），不需回退；但若任一 fault 名对应的是"预期为假"的负例断言（形如 `P1STAR_CHECK(cs, !bad, ...)`），单向改法与翻转改法结果相同，改名不改判据即可，不必动 core.cpp 断言本体。
- 置信：CONFIRMED（两处源码逐行比对＋注册面 grep＋rc 计算式实读）

### CR-30-05 · 框架记录了 `checks` 却从不据其判红：零断言的组与全通过的组在 rc 与 stdout 形态上不可区分
- 轴：R（主轴）＋ D
- 位点：`p1star_test_main.hpp:29` `int checks = 0;`、`:54` `++checks;`；消费面判定式 `p1star_tests_core.cpp:471`（及 `:599/:707/:881`）`return cs.failures == 0 ? 0 : 1;`
- 上位依据：`AGENTS.md §9`「对"看起来通过"的结果保持怀疑：**空断言、SKIP 充数**、证据文件为空、检查器静默退化都算未完成」；`p1star_tests_selfcheck.cpp:5` 引的模板验收「不得写永远 PASS 的占位」。
- 现状：`CheckState::checks` 只被自增与（core 内）打印，从不进入 rc 计算；`run_all_groups` 亦不读取。任何组体若在循环开始前返回（夹具数组为空、被 `#ifdef` 编译掉、前置 `return`），`failures==0` ⇒ rc=0 ⇒ ctest 绿，且 stdout 只有 `== group X ==` 一行加零条 `ok`。
- 差在哪：判据方向明确——"无任何断言"落入 `failures == 0` 的通过分支，故"绿"不蕴含"验过东西"；这是判据自身的构造性缺口，不是某个用例的偶发。
- 后果：P1-STAR-TEST 对外的「五组验收关键词齐备」主张，其证据强度依赖人工数 `ok` 行；门本身对断言数退化不设防。与 CR-30-04 叠加时最坏形态是：一组退化到 0 断言＋一个 ambient 注入名 ⇒ 全绿且无 `ok` 足迹。
- 定级：S3（本文件层面为框架缺口，无生产触发路径；**具体是否有某组当前零断言，待 file 3/5 逐组数 `P1STAR_CHECK` 站点后再定，若命中则该处升级并回填本条**）
- 怎么算修好：`record()` 之外增 `finalize(cs, min_checks)`：`cs.checks < min_checks` 即 `++failures` 并打印 `FAIL <group>_min_checks (got N)`；每组注册常量下限。改后必须同步：各组现有断言数打印处（core 末尾的汇总行）与 selfcheck 阶段 1 的基线判据，避免下限取高导致恒红。
- 置信：PARTIAL（框架面 CONFIRMED；"当前是否已有组落在零断言"缺 file 3/5 的站点计数）
