### 6.2 findings

#### CR-56-23 · "内存上界断言"比的是夹具自己的容量，与被测函数无关，恒成立
- 轴：R（主）+ D
- 位点：`PERF:67-71`
  ```cpp
  const double stack_bytes = static_cast<double>(fx.stack.capacity()) * sizeof(float);
  const double contract_bytes =
      static_cast<double>(fx.n_frames) * static_cast<double>(NPIX) * 4.0 * 1.5;
  P1CAL_CHECK(cs, stack_bytes <= contract_bytes, "memory_upper_bound");
  ```
- 上位依据：ALG§9:472-474「**资源**: heavy run 资源监控（CPU/RAM/线程时序）随测；内存上限断言（generate_master_flat ≤ n_frames·npix·4B×1.5＋余量）；无 RSS 持续增长（约束 D.9）」；ALG§4:324 与 §5:345-346 指明该界对应 `generate_master_flat` 的 `norm` 主缓冲（`GEN:193`）。
- 现状：LHS 取夹具输入向量容量——该向量由 `FIX:106` `assign(n_frames*npix, 0.0f)` 构造，capacity 恒等于 n_frames·npix ⇒ `stack_bytes = (2/3)·contract_bytes` **恒成立**；RHS 用的是同一次数乘 1.5。被测侧一次都没被测到，而且计时/内存路径调的是 `ac_generate_master_bias`（`PERF:50-52`），合同这条界写的是 `generate_master_flat`。文件头 `PERF:13-15` 自己承认「通过统计量采样无法直接测 RSS, 由资源监控组覆盖」，但仍以 `memory_upper_bound` 之名计入本组判据。
- 差在哪：判据方向钉死——不等式对任何被测实现都不敏感（改 `GEN:193` 的缓冲翻倍甚至改测 flat 都不影响本条）⇒ 恒真偏绿；同时"内存上界已断言"这一表述把一个空判据登记在验收面上。
- 后果：`CMakeLists.txt:22` 把本组描述为 "perf 基线哨兵 (parity/trend/bitwise)"（连内存项都没提），而 `ALG§9:472-474` 的资源项在 p1cal 面内实质无承载；母版生成若引入 O(n_frames·npix) 以上的额外拷贝（真实 4500×3600×N 帧会到数十 GB），本面不会变红。
- 定级：S2（`ac_generate_master_*` 无生产调用方，ALG §4:326；无产品字节触发路径）
- 怎么算修好：(1) 把断言改为对 `ac_generate_master_flat` 的**被测峰值**：调用前后采样 RSS（或 `mallopt`/自定义 operator new 计数）并对照 `n_frames·npix·4B×1.5`；(2) 若本组不做，就把 `memory_upper_bound` 判据与本组头注释、`CMakeLists.txt` 描述一并改为"资源项未在本面验收，归属 X 组"，并把 X 组名写实（现文件头只写"由资源监控组覆盖"，未给可核对的组名/ctest 名——`eng/ci/ctest_baseline.json` 里与本模块相关者仅 `p1_resource` 属他模块）；(3) 同批不要在两条路上都留"内存已断言"的表述。
- 置信：CONFIRMED

#### CR-56-24 · 性能组对"并行是否有效"零判别力：负载缩到合同的 2.6%（注释自称 0.2×），判据带 [0.4, 4.0] 完整包含零加速，而合同唯一的串并行数值主张（≥1.60）在本面没有任何承载，其"由逐内核 benchmark 采集"的推诿与 ALG§6 直接矛盾

  ```cpp
  P1CAL_CHECK(cs, ratio <= 4.0, "perf_parity");
  ```
