### CR-38-1 · 线程不变式探针的 `.canon` 逐 leaf 转储漏掉 `sumNorm`，而 `sumNorm` 正是 pixfrac<1 时发布面亮度的分母
- 轴：R（主）＋ C
- 位点：`p1drz_thread_probe.cpp:102-107`
  ```

               (unsigned long long)parent, local,
               (unsigned long long)bits_of<Scalar>(acc.sumFlux),
               (unsigned long long)bits_of<Scalar>(acc.sumArea),
               (unsigned long long)bits_of<Scalar>(acc.sumVarNum),
               acc.nContrib);
  ```
- 上位依据：`lib/algorithms/drizzle/healpix_drizzle/drizzle_engine.h:64`「release 叶单元字段: sumFlux/sumArea/sumNorm/sumVarNum(累加量) + nContrib(计数)」；`docs/science/DRIZZLE.md:152`「FP64 累积 `F_p/sumVarNum/D_p/N_p`（`TileAccumulator sumFlux/sumArea/sumNorm/sumVarNum/nContrib` 线程局部后串行合并）…`pixfrac=1` 时 `pixel_area` 与 `drop_area` 是同一变量 ⇒ `sumNorm ≡ sumArea` 逐位相同（默认路径零回归）」；主张条文 `docs/algorithms/DRIZZLE_GEOMETRY.md:228-230`「**1/N 确定性成立（跨线程数 bitwise）**…同输入在不同 worker 预算下产物科学载荷逐字节一致」。注意 `DRIZZLE_GEOMETRY.md:225-226` 自己把合并字段序写成「sumFlux→sumArea→sumVarNum→nContrib」，同样漏 sumNorm（该文件不在本批清单，见收工节）。
- 现状：转储只打印 4 个字段，`acc.sumNorm` 从不落任何面。实测的登记面消费关系：`p1drz_merge_pipeline_lock.sh:54` 比较 `sha256sum "$tag.canon"`，`p1drz_taskset_invariance.sh:47` 只比较 `"$WORK/b$b.norm.hiss"`；而产品写入侧 `drizzle_engine.cpp:2543-2545` 每 leaf 只落 `sum_flux / sum_area / n_contrib` ⇒ **sumNorm 既不在 .hiss 字节里，也不在 .canon 里**。
- 差在哪：跨预算逐位不变式的两把锁，比较的是 4 个字段加产品 3 个字段，而载荷定义面（`drizzle_engine.h:64`、`DRIZZLE.md:152`）是 5 个字段——被漏掉的恰好是唯一与 pixfrac 相关的归一分母。

- 定级：S2（缺陷位在证据面，不改产物字节；缺"sumNorm 真的随预算变化"的运行时触发路径）。要升 S1 需要 pixfrac<1 × 多预算实跑复现 sumNorm 差异。

### CR-38-3 · 探针只回报"请求的线程数"（恒为 0），不回报实际 worker 数，锁因此无法证明两档预算真的不同
- 轴：R（主）＋ D
- 位点：`p1drz_thread_probe.cpp:120-121`
  ```

               tiles.size(), (long long)st.nHealpixPixels, (long long)st.nSourcePixels);
  ```
  其中 `threads` 是 `:135` `std::atoi(argv[2])`，两把锁都传 `0`（见 CR-38-2 的调用行）。
- 上位依据：`docs/algorithms/DRIZZLE_GEOMETRY.md:218-220`「worker 数唯一来自 `config.threads`（>0）否则 `omp_get_max_threads`（`drizzleTiledImpl`）」；`p1drz_taskset_invariance.sh:8-10` 口径注释「用 taskset 固定 CPU affinity, 引擎以 config.threads=0 走 omp_get_max_threads() 读取真实预算」。消费侧只把它当显示字段：`p1drz_taskset_invariance.sh:49` `thr=$(grep -o "threads=[0-9]*" ...)` 后 `echo`，无任何断言。

- 差在哪：若 taskset 未真正收窄（busybox 实现吞参、容器忽略 cpuset、affinity 被上层重置），所有运行都在同一 worker 数下执行，sha256 相等便平凡成立——主张的证据就退化成"同一配置跑五遍一样"。探针是这条主张唯一的产物级载体，它却没记录它声称在扫描的量。

- 定级：S2（不改产物字节；缺的是证据面自证能力）
- 怎么算修好：探针在并行区取实际 worker（例如把 `omp_get_max_threads()` 读到的预算与区内 `omp_get_num_threads()` 一并 fprintf），两把锁改"预算档实测值必须两两不同，否则 FAIL"；同批更新 `p1drz/CMakeLists.txt:95-97` 用法说明。**注**：脚本改动不在本批清单，故本条修好动作跨文件。
- 置信：CONFIRMED（打印变量与消费面逐字核过；"taskset 是否真会失效"为假设性诱因，不作为定级依据）

### CR-38-8 · 自称"代表性生产探针"，其板尺×nside 组合违反引擎自身的 auto-nside 域，属生产决策不会产出的构型

### CR-38-9 · 线程预算与 Tile 深度都是硬编码字面量，其中 tile_depth=9 落在冻结公式声明为不可能的域内
- 轴：D（主）＋ C
- 位点：`representative_probe.cpp:50` `cfg.threads = 8;` 与 `:53` `cfg.tile_depth = 9;`
- 上位依据：AGENTS.md §6 硬禁令「不硬编码线程/ISA/block：由 `benchmark` 生成的 profile 决定」；`lib/infrastructure/aio/src/hiss_common.cpp:60-62`「d = min(9, log2(NSIDE/16)) / tile_nside = NSIDE / 2^d / 保证: 满 Tile 最多 4^9=262144 叶像素, tile_nside >= 16」；`drizzle_engine.cpp:336-339`「有效 Tile 分组深度 (config.tile_depth 优先, 0=auto)」`return c.tile_depth ? c.tile_depth : hiss::compute_tile_depth((uint32_t)c.nside);`。
- 现状：nside=512 时冻结公式给 d=5（tile_nside=16，叶槽 4^5=1024），本件写 9 ⇒ tile_nside = 512>>9 = **1**（<16，公式注释的"保证"被破坏），每 tile 叶槽 262144；`eff_tile_depth` 对 config 值**无任何域校验**，静默采纳。
- 差在哪：一处是纪律面（并行/block 参数须来自 profile，探针自称生产代表却把两者钉成字面量）；另一处是数值面（本件跑的 tile 几何落在格式公式声明不可能出现的域，且被调侧不拒绝）。
- 后果：本件的 `wall_sec`、`heap_allocations`、`geometry_cache_*` 全部来自"8 线程 + tile_nside=1"这一组合，与生产 profile/格式规则不同 ⇒ 作为剖析证据的计时与内存结论不可外推；`eff_tile_depth` 的无校验静默采纳同时意味着：生产 JSON 一旦把 tile_depth 误填成与 nside 不配的值，产物 tile 几何会偏离格式保证而不报错（此点在本件仅作为暴露面，改点在引擎）。
- 定级：S2（`eff_tile_depth` 的静默采纳有生产可达路径：`hp_drizzle_api.cpp` 读 config → `drizzleTiled` → `writeHisTilesT` 用 `eff_tile_depth` 定 tile_nside；本件自身仍只是暴露者）
- 怎么算修好：本件改 `cfg.threads = 0`（走引擎 omp 预算口径）与 `cfg.tile_depth = 0`（走公式），或在头注写明"本探针刻意偏离 profile/公式，结论不入性能主张"；**必须同批**给 `eff_tile_depth` 加域校验（tile_nside<16 ⇒ 显式拒绝，勿静默夹逼，与 `docs/science/DRIZZLE.md:140` 的"非法值显式拒绝不静默夹逼"同一口径），否则只改探针等于把门藏在被测侧之外。
- 置信：CONFIRMED（两式与调用面均逐字核过；未实跑确认产物字节影响面，故本条按暴露面报）
