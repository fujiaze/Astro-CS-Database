### CR-70-1 · `Logger` 的序号分配与 sink 迭代全程无锁，`seq_` 是非原子 `uint64_t`，违反 LOG-001 §3"临界区内分配、严格递增无空洞"
- 轴：R（主）/ C
- 位点：`lib/include/astrocs/core/logging.h:68`「`uint64_t seq_ = 0;`」、`:67`「`std::vector<std::shared_ptr<LogSink>> sinks_;`」；实现 `lib/infrastructure/scheduler/src/logging.cpp:64`「`e.seq = ++seq_;`」、`:69`「`for (auto& sink : sinks_) sink->emit(e);`」
- 上位依据：`docs/architecture/observability/STRUCTURED_LOGGING_CONTRACT.md` §3「`seq` 由**唯一进程内分配器**在事件提交临界区分配」「进入临界区顺序 = seq 顺序 = 事件接受顺序；**seq 严格递增、无空洞**」「生产实现必须保证 emit 在临界区内完成或 seq 与写序一致（LOG-002 强制）」；§8 A4「两个线程并发各写 N 条 → 合并后 `seq == 1..2N` 且无重复/空洞」
- 现状：`Logger::log()` 函数体内无任何 `lock_guard`；同文件 `MetricsAggregator` 每个方法都取 `mtx_`（logging.cpp:74,82,88,94,100,107），`Logger` 自己的 `emitted_` 特意声明为 `std::atomic<uint64_t>`（logging.h:69）⇒ 并发在考虑范围内，唯独承重的 `seq_`/`sinks_` 漏掉。`eng/tests/unit/core_logging_test.cpp` 五个用例全单线程（`:58-67` 只顺序调三次 `info`），A4 并发验收在本实现面无对应用例。
- 差在哪：多线程同时 `log()` 是 data race（UB），`++seq_` 可丢增量 ⇒ 产生 seq 重复或空洞，正是 §3 明令排除的形态。
- 后果：任何以 `seq` 为顺序键的重放/审计（§3「消费方（监控/运行图/审计）以 `seq` 为顺序键重放」）在并发 run 下得到错序事件流；A4 对外主张不成立。
- 定级：S2 —— **缺运行时触发路径**：`astrocs::core::Logger` 全仓唯一调用点是 `eng/tests/unit/core_logging_test.cpp:19,33,43,59`，生产 Runtime 走 `RunContext::log`（见 CR-70-3），写不出从 `normalize` 入口到此的路径。一旦按 §7 接入 Runtime 即 S1。
- 怎么算修好：`seq_` 改 `std::atomic<uint64_t>`（或整段 `log()` 入临界区），并把 `attach()` 与 `log()` 对 `sinks_` 的访问纳入同一锁（否则运行中 attach 仍 UB）；补 §8 A4 双线程并发用例，断言合并 seq 集合 == 1..2N 且无重复。**必须同批改**：只原子化 `seq_` 而不锁 emit，seq 顺序与写序仍可不一致 ⇒ 判据假绿。
- 置信：CONFIRMED（逐行读 `Logger` 类定义与 `Logger::log` 全函数体，并核对测试文件无并发用例）

### CR-70-4 · `to_jsonl` 对自由文本不转义、不脱敏，且用 512 字节 `snprintf` 静默截断 ⇒ 产出非法 JSON 行
- 轴：R（主）/ C
- 位点：`lib/infrastructure/scheduler/src/logging.cpp:35-38`「`std::snprintf(buf, sizeof(buf), "{\"ts\":\"%s\",\"level\":\"%s\",\"component\":\"%s\",\"event\":\"%s\",\"message\":\"%s\",\"seq\":%llu", ts_utc.c_str(), ..., message.c_str(), (unsigned long long)seq);`」+ `:34`「`char buf[512];`」+ `:39`「`std::string out = buf;`」；声明侧 `lib/include/astrocs/core/logging.h:31`
- 上位依据：LOG-001 §2.1「单行 = 一个 JSON 对象（无嵌套对象数组、无跨行）」；§5「写入 `diagnostic`/`message` 等自由文本**前必须执行脱敏**（参考实现 `redact()`）」并列出 `/home/<user>/…`、`C:\…`、UNC、`password=/token=/secret=/api_key=` 模式；§6「单行（含 `\n`）上限 **4096 字节**…超限按 UTF-8 边界截断 + 省略号」。本仓已有合规实现可对照：`lib/infrastructure/cli/jsonl.h:78` `redact_free_text()`、`:172`「`{"message", redact_free_text(message)}`」
- 现状：`message`/`component`/`event` 原样 `%s` 拼入，无引号/反斜杠/控制字符转义，无脱敏；`snprintf` 的截断返回值被丢弃，既不报截断也不加省略号。
- 差在哪：含 `"`、`\`、换行的 message（错误消息夹带路径或 JSON 片段是常态）会产出**语法非法的 JSONL 行**；>511 字节被切成半截对象；合同 §5 的强制脱敏在此完全没接。

- 定级：S2（同 CR-70-3：`to_jsonl` 无生产调用点，写不出从三命令入口到该行的路径；接入即 S1）
- 怎么算修好：走 JSON 序列化（仓内已有 `nlohmann::json`，见 `cli/jsonl.h`）或补转义函数；自由文本先过 `redact_free_text()`（**与 CLI 面共用同一模式表，不要复制第二套正则**）；上限取合同的 4096 并在截断处加省略号；补负例：message 含 `"`/换行/绝对路径/超 4096 字节 ⇒ 断言产物仍是单行合法 JSON 且无路径泄漏。
- 置信：CONFIRMED（读完整函数体并与 `lib/infrastructure/cli/jsonl.h` 的转义/脱敏实现比对）
