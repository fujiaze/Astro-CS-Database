#### CR-283-01 · SNR 丢弃原因计数包含未填充项，误导诊断

- **轴**: R
- **位点**: `orchestrator.cpp:4543-4553`, 打印 `OUTSIDE_TILE=`、`NO_OVERLAP=`、`INVALID_WCS=`、`OTHER=`
- **上位依据**: SCI-SNR-003 §3: “丢弃原因分类”应只统计此处逻辑覆盖的三类 (INVALID_PSF, ZERO_FLUX, NOT_DROPPED)；其他原因在 drizzle 阶段判断，“此处为 0”已在注释中标明 (第 4517 行)。
- **现状**: 日志打印了全部 7 类计数器，但 `drop_counts[SNR_DROP_OUTSIDE_TILE]` 等 4 项始终为 0 且从未被赋值；这制造了一个“已统计这些原因”的假象。
- **差在哪**: 注释自称“此处为 0”，但日志输出不标注“均为 0/DRIZZLE PHASE ONLY”，运维会误以为这些类别被完整追踪。
- **后果**: 诊断面板可能把 0 展示为有效指标，掩盖真实丢弃分布；严重度 S3(诊断误导性)。
- **怎么算修好**: 要么移除这 4 项打印，要么明确加上注释`(drizzle phase)`；推荐前者，因本阶段不负责这些原因。
- **置信**: PARTIAL (缺对 SNR_DROP_REASON_COUNT 枚举定义的核对，假设其含 7 项)

#### CR-283-02 · NoiseWeightModelV1 饱和过滤降级声明可能静默被忽略

- **轴**: R  
- **位点**: `orchestrator.cpp:4734-4737`, LOG_WARN("饱和过滤降级：帧元数据无 SATURATE/DATAMAX...")
- **上位依据**: SC-008 §4：“未取到电平⇒**显式降级声明**，消费方可据此 fail-closed”。
- **现状**: 代码确实在写 WARN 并落盘三 KV (`NOISE_SATURATION_LEVEL=0.000000`, `FILTER=DISABLED_NO_METADATA`, `SOURCE=DISABLED_NO_METADATA`)，但没有在返回码或错误标志中体现，Stage1 仍继续运行。
- **差在哪**: WARN 级别日志容易被日志聚合系统降噪/丢弃，下游若只看 exit code=0 会错过该信号。
- **后果**: 饱和过滤静默关闭时，variance 统计会被饱和像素污染，导致权重系统性偏软 (ivars 偏大)，合成图像信噪比虚高；S2(科学参数偏差，触发路径依赖下游是否检查 KV)。
- **怎么算修好**: 
  1. 增加 KV `NOISE_SATURATION_ENABLED` (true/false)，避免解析 `level>0` 的歧义；
  2. 或增加 `result.warning_flags |= WARNING_SATURATION_UNSET` 并在 manifest 中暴露；
  3. 或者将 WARN 提升为 ERROR 并设 exit_code=WARNING_SATURATION_UNSET (如需严格 gate)。
- **置信**: PARTIAL (缺对 Stage1 result 结构与警告码机制的跨文件核查)

#### CR-283-03 · legacy stage2 统一失败无替代指引路径

- **轴**: D
- **位点**: `orchestrator.cpp:5499`, `result.error_msg = "legacy Stage2 removed in V17; use astrocs-stage2"`
- **上位依据**: ASTROCS_DESIGN §2: “Phase2 唯一生产入口 = astrocs-stage2.exe”，旧入口应明确废弃。
- **现状**: 当任何人用旧入口调用 run_stage2 时，立即返回 GENERIC_ERROR，错误消息指向新可执行文件。
- **差在哪**: 没有提供迁移命令示例或配置 JSON 差异说明；用户可能不知道如何构造新命令。
- **后果**: 阻碍迁移，导致用户在旧接口上卡住；S3(可用性缺陷)。
- **怎么算修好**: 在 error_msg 中加入简短迁移提示，如 `"Legacy Stage2 removed; run: astrocs-stage2 --input <hiss_dir> --output <hcsd>"`。
- **置信**: CONFIRMED
