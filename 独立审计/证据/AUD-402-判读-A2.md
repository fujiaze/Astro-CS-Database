### 3.2 该导出却硬编码（§4 第 2 条）

**L-05｜Linux USER_HZ 被当定义常数硬编码（本类主案，且反证在同一文件内）**
`monitor.h:257/:258` 把 `/proc/self/stat` 的 utime/stime 除以 **100.0** 得秒。Linux 的 tick 频率是内核构建期选项（`_SC_CLK_TCK`，常见 100/250/300/1000），proc(5) 亦明示这些字段以 clock tick 计 ⇒ 该量**可导出**。同文件两处已经导出对了：`:204-205`（iowait）与 `:277-278`（`read_thread_cpu`）都用 `sysconf(_SC_CLK_TCK)` 并只在返回 ≤0 时兜底 100 —— 同一物理量三处两套口径，且本行的连"兜底"形态都不符既有写法。影响链静态闭合：本行只喂 `cpu_seconds`（:262/:237）→ `:430` 等效核 → `cpu_cores_used` 事件、`work_core_seconds`、GateConfig；而每线程 CPU 走 `hz` ⇒ 非 100 Hz 内核上同一份报告里 `per_thread_cpu_sum_pct` 与 `cpu_cores_used` 相差 hz/100 倍，且**现无任何门交叉核对二者**（查交叉校验：0 处）。本结论不依赖本机实际 HZ（本节点禁止执行探测），依据是"同文件两套口径＋该常量可导出"。修法：:257/:258 复用 :277 的 `hz`（两行必须同处同改，否则 user 与 sys 口径分裂）。
对照行（同形不同性质，判为已核无问题）：`monitor.h:233` 的 `10000000.0` 是 Win32 FILETIME→秒的定义换算（FILETIME 单位 = 100 ns）✓；`memory_report.h:481` 的 `1024.0*1024.0` 是 MiB 定义 ✓；`process.cpp:106` 的 `1000.0` 是 s→ms 定义 ✓；`monitor.h:447`/`memory_growth.h:87` 的 `100.0` 是百分数定义 ✓。
