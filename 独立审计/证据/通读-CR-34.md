### CR-34-1 · 未知组名／零个组被执行时执行器返回 0（假绿），且无任何门拦得住
- 轴：R（主轴）＋ D
- 位点：`lib/algorithms/psf/tests/p1psf/p1psf_test_main.hpp:156`　`if (group != "all" && group != groups[i].name) continue;`　与　`:170`　`return total_fail == 0 ? 0 : 1;`
- 上位依据：`ACCEPTANCE_SPEC.md`／`docs/ci/CI_SPEC.md` 规定 ctest 为机器门（AGENTS.md §3、§4"构建、测试、机器门全过后交前台验收"）。**"组名不匹配必须判红"这条规则在条文面零提及**，检索式：`git grep -n "unknown group\|no test ran\|未匹配\|零条断言" -- lib/algorithms/psf ACCEPTANCE_SPEC.md docs/ci`；`git grep -n "add_test(NAME p1psf" -- lib` 亦无任何 PASS_REGULAR_EXPRESSION。
- 现状：`group` 由 argv 位置参数直接赋值（:136），与 `groups[i].name` 做**精确串比较**；不匹配则 `continue`，循环可以**一个组都不执行**，`total_fail` 保持 0 ⇒ 进程 `return 0`。stderr 上没有任何输出，stdout 反而打印 `[p1psf] == P1-PSF-TEST: %d 通过, 0 失败 (组级) ==`，其中"通过"= `(int)n - total_fail`（:169）即**注册组总数**。
- 差在哪：选择器的失败模式是"成功"——参数写错与断言全通过给进程留下完全无法区分的 0 码，且汇总行主动宣称全部组通过。
- 后果：`ctest` 面上 5 个 p1psf 门（`p1psf_units/properties/oracle/negative/boundary`）中任一名字与 core 组表脱钩，该门即变成"零断言执行的绿"，对外"PSF 科学断言已由 ctest 覆盖"的主张失去证据资格。方向钉死：**被执行组数 = 0 ⇒ total_fail = 0 ⇒ rc = 0 ⇒ 偏绿**（不是偏红）。

- 怎么算修好：在 :154 前后加"被执行组计数"，`matched == 0` 时打印 `UNKNOWN GROUP <name>` 到 stderr 并 `return 2`；同时把 :169 的"通过"改为**实际执行且 rc==0 的组数**，与注册组数分开打印。必须同批改的东西：`p1psf_tests_selfcheck.cpp` 的基线相断言（它若假定 rc∈{0,1}，新增码 2 会把它判红）与 `CMakeLists.txt:52-56` 的组名——**先跑一遍五名逐一比对再改**，否则会误伤。

### CR-34-4 · 不报的核过项（文件 1）
- **注入是单向的（派单本查项 ②）**：`P1PSF_CHECK`/`P1PSF_CHECK_MSG` 的分支结构是 `if (注入) { ++failures; } else if (!(cond)) { ++failures; }`（:86-95、:114-123）——两条分支都只做 `++failures`，**不存在"翻转 ok／把 false 当 true"的语句**，注入只能增加失败、结构上不可能把真红灯翻成绿。此结论按派单要求写清其边界：它同时意味着**注入相里真实 `cond` 从不被求值**，故注入跑的绿/红都不能为真实逻辑背书（该后果归入 CR-34-5，不另立条）。检索式：`grep -n "!.*ok\|flip\|invert\|翻转" lib/algorithms/psf/tests/p1psf/*.hpp lib/algorithms/psf/tests/p1psf/*.cpp`（命中 0 处判据翻转）；`git grep -n "P1PSF_CHECK" -- lib/algorithms/psf/tests/p1psf | wc -l` 用于确认宏形态只有这三种。
- **`flatten9` 的 9 列顺序与合同布局 B 同一套**：逐字段核过 B,A,cx,cy,sx,sy,theta,fwhm_x,fwhm_y 与 `docs/contracts/PUBLIC_API.md:658`、`docs/contracts/DATA_SEMANTICS.md:754` 一致（本批派单本查项 ⑤ 的"两份合同面"之一，另一处 `psf_information.h` 在文件 6 处置）。附注：`9` 与列序在测试面靠**硬编码字段名＋偏移**复制了一份，无 static_assert 与 `DPSF_PSF_PARAMS_SCHEMA` 串联；因布局变更同时会打断实现头，不构成可辩护指控，不单立 finding。
- **argv 解析越界**：`--group` 缺值时（:135 `i + 1 < argc`）静默保留前值，`ASTROCS_P1PSF_FAULT=",",,a,` 空 token 已过滤（:148）——均无判据后果，不报。

### CR-34-7 · `P1PSF_CHECK_EQ` 向 `long long` 收窄比较，超 64 位与浮点期望值会误判

- 位点：`p1psf_test_main.hpp:100-101`　`const long long _g = (long long)(got); const long long _w = (long long)(want);`

- 置信：PARTIAL（缺 core 侧实参类型清单，见文件 2 处置）

### CR-34-8 · flux 恒等式把生产公式原式手抄两份，绕开指定的独立权威函数 `oracle_flux`，而 README §9 明文禁止"与生产共用同一公式实现"
- 轴：D（主轴）＋ S
- 位点：`p1psf_tests_core.cpp:321`　`P1PSF_CHECK_MSG(cs, rel_err(r.flux, 2.0 * M_PI * r.A * r.sx * r.sy / 3.0) <= tol().flux_rel,`　与　`:588`　`P1PSF_CHECK(cs, rel_err(r.flux, 2.0 * M_PI * r.A * r.sx * r.sy / 3.0) <= tol().flux_rel, F_ORC);`
- 上位依据：`lib/algorithms/psf/README.md` §9 原文："**oracle**：解析 Moffat4（β=4）合成图上回收 7 参数（参数真值与容差由 fixtures 生成器给出，**禁止与生产共用同一公式实现**）"，同段又列 "**property**：`flux=2π·A·sx·sy/3` 解析积分恒等"。指定的权威函数在 `p1psf_oracle.hpp:47-50`（注释自署"β=4 Moffat 整平面解析积分"、段首 :44-45 "解析恒等式 (PSF.md 冻结定义, **独立于生产实现**)"）。
- 现状：`oracle_flux` 在跟踪集**零调用**——检索式 `git grep -n "oracle_flux" -- lib eng` 命中 3 行，本模块仅其定义行 :48（另两行是 drizzle 模块的无关同名前缀函数 `oracle_flux_closure`）。测试两处逐字重写 `2.0 * M_PI * A * sx * sy / 3.0`，与生产 `dpsf_psf.cpp:429`　`double flux = 2.0 * M_PI * A * sx * sy / 3.0;` **字符级同式**；`p1psf_oracle.hpp:130` 的容差注释自己承认是 "oracle **同式重算**"。
- 差在哪：README §9 的 property 要成立，期望侧必须独立于产生 `r.flux` 的那条式子；现行两侧同式，且唯一被指定的独立实现被弃为死代码。
