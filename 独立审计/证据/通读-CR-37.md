### CR-37-006 · 未知组名与"零条断言被执行"都返回 **rc=0**：执行器无任何"命中/断言基数"守卫
- 轴：R（主轴）+ D
- 位点：`p1drz_test_main.hpp:124` `if (group != "all" && group != groups[i].name) continue;` 与 `:138` `return total_fail == 0 ? 0 : 1;`
- 现状（自己数出来的两条 rc=0 路径，不预设）：

### CR-37-016 · perf 两条门在"完全没有并行"时恒真：只有上界、没有下界，也没有任何"真用了 N 个 worker"的证据
- 轴：R（主轴）+ D
- 位点：`p1drz_tests_perf.cpp:68` `P1DRZ_CHECK_MSG(g_perf_cs, t2 / t1 < 4.0 && t4 / t1 < 4.0, "perf_parity",` 与 `:71` `P1DRZ_CHECK_MSG(g_perf_cs, t4 / t1 >= 0.25, "perf_trend",`

- 上位依据：`docs/algorithms/DRIZZLE_GEOMETRY.md` §9 不变量「1/2/4 线程一致性」；`AGENTS.md` §6「不硬编码线程/ISA/block：由 benchmark 生成的 profile 决定」；`p1drz/CMakeLists.txt:28` 把该门描述为「perf 基线哨兵 (parity 4x/trend 0.4x)」——"哨兵"要盯的是并行退化/缺失，现判据盯不到"缺失"。

### CR-37-017 · `perf_trend` 的名义（"无负加速趋势"）与实现的不等式方向相反：真正发生负加速时它永不判红
- 轴：R
- 位点：`p1drz_tests_perf.cpp:71` —— 逐字：`P1DRZ_CHECK_MSG(g_perf_cs, t4 / t1 >= 0.25, "perf_trend",` + 注释 `:6-7` `//   perf_trend  : T(4w)/T(1w) ≥ 0.25×  (无负加速趋势, 共享负载环境容噪; 本负载 4w 实测 ~0.38, 2.6× 合法加速)`

- 差在哪：判据方向与其声明相反（前言 §2 R 轴"判据方向反了"的教科书形态）；两门合起来的实际语义是"加速必须落在 [1×, 4×) 内"，其中"≥1×（不许变慢）"这一半**没有任何一条判据**，与 :5 的"并行不倒退"名义不符。
- 后果：名义上覆盖"负加速趋势"的门不覆盖它；读 §9/注册表面的人会把"trend 门存在"当成"退化有证据"，而 perf 组对"越并行越慢"的真实回归（例如归并锁竞争、按线程序合并引入串行长尾）完全无判据——这与 `AGENTS.md` §9「门禁/判据本身不合理时改进门禁本身」直接相关。
- 定级：S2（判据方向错；无生产触发路径）
- 怎么算修好：把"防负加速"独立成一条**有实测余量**的门（如 `t4/t1 <= 1.0 + 共享负载容噪带`，容噪带须用实测标定并登记标定件），并把 `>=0.25` 这条**改名**为它实际在防的东西（如 `perf_superlinear`/`perf_sublinear`），或按注释先例 `p1cos_tests_perf.cpp:9-10` 的措辞统一命名；两处命名（perf 文件与 CMake 注释）必须同批改（防"改对反而判红"：改名会牵动 selfcheck 的注入名单，见 CR-37-019）。

## 6.2 findings

### CR-37-022 · 注入相把"任何非 0 且非 127 的 rc"当作注入生效，且注释承诺的第二条判据（`FAULT-INJECT` 行）从未被捕获 ⇒ 子进程崩溃/被信号杀/零用例都判绿
- 轴：R（主轴）+ D
- 位点：`p1drz_tests_selfcheck.cpp:89` `const int rc = WIFEXITED(status) ? WEXITSTATUS(status) : -1;`；`:90` `if (rc == 0) { … ++failed; }`；`:95` `else if (rc == 127) { … ++failed; }`；`:99-102` `else { std::fprintf(stdout, "[p1drz-selfcheck] injection %s → rc=%d (必败 ✓)\n", c.name, rc); }`
- 上位依据：本文件头 :5 「injection: `ASTROCS_P1DRZ_FAULT=<name>` 重跑 → **必 FAIL + FAULT-INJECT 行**」；`p1drz/CMakeLists.txt:64`「baseline 必 PASS + 注入必 FAIL 双向排除恒常」；`AGENTS.md` §9「空断言、SKIP 充数、证据文件为空、检查器静默退化都算未完成」。
- 现状：① 判据是"排除 rc==0 与 rc==127 两个码"，其余（含 −1＝信号死亡、134＝SIGABRT、139＝SIGSEGV、137＝OOM-kill、任何引擎早崩退出码）一律打 `必败 ✓`；② 子进程的 stdout/stderr 直接继承父进程，本文件**没有任何** pipe/临时文件/`dup2` 去捕获 `FAULT-INJECT <name>` 行（全仓 `git grep -n "FAULT-INJECT"` ⇒ 只有产生点 `p1drz_test_main.hpp:58` 与本注释 :5，无消费点）；③ `k_injections` 基数只进 printf（:108），没有 `>0` 守卫；④ 与 CR-37-009 合成：因为 `g_cs` 跨组累积，任一翻转使四组全红 ⇒ 即使 rc 真是 1，也无法证明翻转发生在该名字所声称的那条断言上。
- 不等式方向（前言 §3 硬门槛）：接受集合 =  ℕ\{0,127}，比"注入导致的可控失败"大 ⇒ 只可能把不该算证据的情形算成证据 ⇒ **偏绿**，指控成立。
- 后果：「故障注入能让测试失败」这条验收（模板 `<prefix>-TEST`，亦是 `AGENTS.md` §9「能红能绿」要求）在 p1drz 族只有**弱**证据：一个在注入相里根本没能启动/中途 abort 的子进程同样满足它；而 `DISP-DRZ-*` 与 §9 冻结容差的"负例判据可判红"对外主张正是靠这个门背书的。
- 定级：S2（判据强度主张不成立；无生产触发路径）
- 怎么算修好：① 判据收紧为「`WIFEXITED && WEXITSTATUS==1` 且子进程输出里出现且仅出现预期的 `FAULT-INJECT <name>`」——用 `pipe(2)`+`dup2` 或临时文件捕获子进程 stderr 并在父进程检索；② 显式把信号死亡/OOM 归为 selfcheck 失败（`WIFSIGNALED ⇒ ++failed`）；③ 加 `if (sizeof(k_injections)/sizeof(*k_injections) == 0) return 1;`；④ 配合 CR-37-009 的复位修法，改为断言"只有该名字所属组红"；⑤ 同批把 perf 三名纳入名单（CR-37-019 修好可达性之后），否则名单基数与代码里的 faultname 全集仍不一致。
- 置信：CONFIRMED（判据分支逐字读得；`FAULT-INJECT` 无消费点由全仓 `git grep -n "FAULT-INJECT"` 确认——命中仅 `p1drz_test_main.hpp:8`（注释）、`:58`（打印）、本文件 `:5`（注释））

### CR-37-023 · `argc >= 1` 恒真 + `run_child_phase` 的非空 fault 分支为死代码：父子相的区分实际只看环境变量，手动带注入变量跑自检会跳过 baseline
- 轴：R（主轴）+ C
- 位点：`p1drz_tests_selfcheck.cpp:49` `if (argc >= 1 && std::getenv("ASTROCS_P1DRZ_FAULT") != nullptr) {`；`:34-41`（`run_child_phase(const char* fault)` 的 `if (fault && …)` 分支）
- 现状：`argc >= 1` 对所有 hosted 实现恒真（C/C++ 标准保证 `argc` ≥ 1 且 argv[argc]==nullptr），因此该 `&&` 的第一项永不起作用；本文件唯一以非空 `fault` 调用 `run_child_phase` 的地方不存在（:57 只传 `nullptr`），注入相走的是 :50–52 的另一份手写 argv 构造 ⇒ 两处逻辑重复实现同一件事（第二副本，见 :39 与 :51 的 `argv2` 完全同形）。
- 差在哪：意图是"仅当被 execve 重入时走注入相"，实现成"只要环境里有这个变量就走注入相"——于是**人**在 shell 里 `ASTROCS_P1DRZ_FAULT=uniformity ./p1drz_selfcheck_test` 时得到的是"跳过 baseline、直接返回注入相 rc=1"，看起来像"自检挂了"，而不是"你正在用自检工具做单点注入"；恒真的 `argc>=1` 还会让后来者误以为已有父子区分。
- 后果：无产物影响；造成（a）误读门禁日志的风险，（b）注入相 argv/env 构造有两份实现，改一份即漂移（与 CR-37-015/018 同族）。
- 定级：S3（写不出对外主张被破坏的路径）
- 怎么算修好：用一个显式的哨兵参数区分，例如子进程 argv[1] 传 `"--phase=injection"` 并以其为唯一判据（env 只带值不带角色）；删掉 `run_child_phase` 的 `fault!=nullptr` 死分支或让它成为注入相的唯一实现路径（两处合一）。
- 置信：CONFIRMED
