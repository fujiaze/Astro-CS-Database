### CR-68-05 · `to_json` 写出的单位与 dtype 字面量，`from_json` 读不回来：头承诺的"序列化 roundtrip"对 `electron^2`/`surface_brightness`/`u8`/`i16`/`i32` 直接失败
- 轴：C（主）/ R
- 位点：`lib/include/astrocs/core/artifact.h:113`
  `  // 序列化 roundtrip` ／ `bool to_json(std::string* out) const;` `static bool from_json(...)`
- 上位依据：`eng/contracts/data/artifact_manifest.schema.json:5` description 明写"单位/坐标/dtype/shape/plane/invalid 策略/所有权语义见 docs/interfaces/data/DATA-001_ARTIFACT_CONTRACT.md"（该文档登记为悬空，见 `eng/tools/doccheck/dangling_ledger.json:61-65`）；C++ 侧"roundtrip"能力的条文面唯一表述就是本头这两行注释——检索式：`git grep -n "roundtrip" -- docs lib/include` 无第二条规定其定义域。
- 现状：写出侧 `artifact.cpp:101` `s += key("unit", unit_name(unit))`，而 `unit_name` 可产出 `"electron^2"`（`core/artifact.h:45`）与 `"surface_brightness"`（`:47`）；读回侧 `artifact.cpp:176-179` 的分支只覆盖 `ADU / electron / ADU^2 / 1/variance / deg / 1 / UNKNOWN`，落到 `:179` 的 `else { if (err) *err = "bad unit " + s; return false; }`。dtype 同理：`unit_name` 对应面 `artifact.cpp:173-174` 只认 `f32 / f64 / u16`，而 `scalar_type_name` 可产出 `i16 / u8 / i32`（`core/artifact.h:26-28`）。
- 差在哪：写出集合是 8 个单位 × 6 个 dtype，读回集合是 7 个单位（缺 2 个）× 3 个 dtype（缺 3 个）——**同一对象的两次编码不对称**，缺的是方差/不确定度单位（`electron^2`）与面亮度单位（`surface_brightness`）本身。
- 后果：任何以方差（electron²）或面亮度为单位的产物 descriptor 无法从 JSON 恢复，`from_json` 报 `bad unit electron^2` 并返回 false；以 `i16/u8/i32` 表达的 mask/label 类产物同样报 `bad scalar`。⇒ 头对外"序列化 roundtrip"主张对这几类产物不成立。
- 定级：S2 —— 缺运行时触发路径：`from_json` 在全跟踪生产集内**零调用方**（`git grep -n "from_json\("` 命中仅本头声明、`artifact.cpp` 定义、`core/artifact_store.h:68` 的另一同名函数、第三方 `json.hpp`），写不出 `文件:行` 生产链。
- 怎么算修好：把 `from_json` 的 unit/scalar 分支改为与 `unit_name`/`scalar_type_name` **同一张表反查**（不要在两处各写一遍字面量），并让 `UnitId/ScalarType` 的枚举名↔字符串映射单一来源；**必须同批**补往返正例（对全部 8 单位 × 6 dtype 逐个 `to_json`→`from_json` 断言等值）与负例（`bad unit xyz`），否则下次再加枚举仍会漏。
- 置信：CONFIRMED（两侧字面量逐条比对）

### CR-68-07 · `ArtifactId` 规范形态 `"sha256:<hex64>"` 与 manifest 合同 `artifact_id` 的 pattern（禁冒号）互斥
- 轴：C
