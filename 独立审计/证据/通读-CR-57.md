### CR-57-5 · "验证 double 精度计算"的用例恒绿：所选取值下 double 乘与 float 乘舍入到**同一个 float32**，该断言在构造上无法判别它自称要验证的东西
- 轴：R（主，恒真断言）
- 位点：`:247` `ASSERT_FLOAT_NEAR(out, 0.1f, 1e-5f, "大动态范围: 1e6 * 1e-7 = 0.1 (double 精度)");`；配套自述 `:233-234` "大动态范围 photscal (验证 double 精度计算) … float 直接乘会损失精度"
- 上位依据：实现约束 `photometry_apply.cpp:14` "内部使用 double 精度乘法, 避免大动态范围 (例如 k=1e-7) 下的 float 精度损失" 与 `:68` `out[i] = (float)((double)light[i] * photscal);`
- 现状／复算：双精度腿 `double(1e6f)×1e-7 = 0.1`；单精度腿 `1e6f × float32(1e-7)`，其中 `1e-7f = 1.000000020040877e-7` ⇒ 积 `0.1000000020040877`。0.1 附近 float 间距 `ulp = 2^-27 = 7.4506e-9`，落在 `0.1` 之上的那个 float 是 `0.10000000149011612`，其舍入区间为 `[0.09999999776, 0.10000000522)`，**两个候选值同在该区间** ⇒ 两条腿都存成 `0.10000000149011612`，逐位相同。再叠上 `1e-5` 的绝对容差（相对期望值 0.1 即 1e-4），该判据对"实现是否真用 double"完全失敏。
- 差在哪：不是容差取松了，而是**选取的这组输入在任何容差下都无法分叉**——要分叉必须让 `float32(photscal)` 与 `photscal` 不同值且 `|out|·相对差` 超过 `ulp(out)` 数倍（例：`photscal = 1.0 + 2^-30`、`light = 1e7f` ⇒ double 腿 10000009.3、float 腿 1e7，差 9.3 而 `ulp(1e7)=0.95`）。
- 后果：实现要点 :14 的"double 中间精度"约束在本族唯一点名它的用例里没有承载；把 :68 改回 `out[i] = light[i] * (float)photscal` 后 `cal_photometry_apply` 仍绿。（已核数量级：该退化在 float 域的可见偏差 ≤ ~1.2e-7 相对，低于冻结 rtol 1e-6 ⇒ 不构成交付错值，故不升 S1。）
- 定级：S3（恒真断言成立，但可主张的产物后果仅 ulp 级；按 §3"写不出后果即降级"处理）
- 怎么算修好：换上面那组可分叉的取值并把容差收到 `ulp` 级；或按 `:297` 的"尺度相关"改成 `|out-ref| <= max(rtol*|ref|, 2*ulp(ref))` 形式并同时锁 double 腿。**同批必须改** `eng/tools/quality/check_photometry_apply.py:291`（`abs(y[0]-0.1) <= 1e-5` 复刻了同一条零判别判据），否则交叉核对门与单测一起保持恒绿。

### CR-57-26 · 两条"互为独立"的 Ω 面积法其实算的是**两个不同的几何对象**（四角测地四边形 vs 坐标线弯曲单元的 Jacobian），而条文面对面积元的几何定义零规定 ⇒ 交叉校验在概念层不闭合，误差随像元尺度线性而非随双精度改进
