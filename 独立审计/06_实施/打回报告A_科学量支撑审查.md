## 1 一句话结论

**全仓 20,595 个数值位点中，给出支撑判定的只有 85 个（0.41%）：文献值 72、公式导出 8、实验标定 5；其余 20,510 个位点的处置一律挂着"待确认"。**

## 3 六类必须打回的缺陷

### 3.1 无支撑常数（88 条在生产面）——标准 02 §4 第 4 类被普遍跳过

现状：值直接写在代码或配置里，出处列为"无"或写了一个不可解析的指针；正文里没有任何"待确认"标注，读者会把它当已定值用。
要求：逐条按 §4 走四选一。**"待确认"必须写在离值最近的地方**（代码注释＋登记面＋该量的文档条目三处同址），并给保守方向与影响范围；不许只活在台账里。
优先处理（按后果排序，取自已复核条目）：控制点层 SNR 的 `m_ref = 6.0`（四链取证面零登记）；零尺度伪方差门限 `1e−2`；坏列修复的两处入口阈值（同一语义在两处取 9.0 与 5.0，合同只登记一侧）；`min_samples` 文档 5 vs 代码 64。

**新读出来的两条（有具体运行后果，优先于纯登记问题）**：
- **内存安全系数 0.75 无推导、无标定、也不是配置项**（成稿 `独立审计/证据/通读-CR-19.md`）。它在代码里写死三处，实现**只挡 `<=0`、不设上界**；而同一个量在运行时资源清单里却是可配置项，配置目录里对它零命中。⇒ 后果可算：填一个大于 1 的值，规划器就会报出比内存上限还大的块，而本机交换分区永久禁用，触发的是**全局 OOM**（连带杀掉同单元里在跑的会话），不是本进程的一条报错。修法：给它一个推导或标定并登记；实现加"必须落在 (0,1]"的值域校验 ＋ 配一条"填 1.5 必红"的负例。
- **同一档判据只装在 CPU 通道上**：GPU 在场时执行会先进 CUDA 分支，而那条分支从不读用于判定回退的模式位 ⇒ 追溯表里那条"已验证"对这一臂不成立。修法：把守卫下移到两条通道的共同入口，或让两条通道各自显式表态。


### 3.2 阈值不是判据值而是历史读数或魔数

- 接缝判据 `1e−2` 在设计／验收／科学三层**互相指回**，全链无误差预算（谁都不生产这个数，只是互相引用）。
- 一条 fail-closed 普查门的判别力锚"单元数 > 50"：**原判"抄自某次观测"经第②层复算不成立**——脚本与归档件同批落地、当时观测量 230 与 50 不等 ⇒ 它是**无来源魔数**；不判别力结论不变（裁到 51 仍绿）。
- `9003`（因子清单乘不出该数）、`1.25` vs `1.0442` 两值并存。
要求：每个判据值要么给推导式（代码按式算），要么给标定方法与数据并落到跟踪证据件；两者都给不出的显式标"待确认"并定保守值。

### 3.3 同一个键有多个"默认值"，且**省略键时两条生产入口取相反值**

这条是本报告最硬的一条，已由第②层独立复算确认（`raw/复核-V402.md`）：

- 像素收缩因子 `pixfrac` 实测 **≥8 侧**不同值并存（代码兜底／`defaults.json`／出厂模板／CLI 生成骨架／schema 声明默认／登记册／合同／插件文档）；
- **代码兜底自己就分叉**：调度器适配路径缺键取 **1.0**，编排器路径 `json_config.cpp:712-713` 取 **0.8** ⇒ "只有一侧决定生产取值"的说法不成立，真正决定的是**这次运行走哪条路径**，而两条路径互斥；
- 合同登记册写 `declared_default="1.0"` 并注明"默认 1.0 已入 defaults.json"，而 `defaults.json:667` 的实际值是 **0.8** ⇒ **合同在断言一件与它所指向的文件相反的事**；
- 默认值一致性门**结构性看不见这些**：它读模板顶层 `config` 键，而三份出厂模板早已改成 `blocks[]` 形态、零个 `config` 键 ⇒ 模板侧贡献 0 个键仍判绿；CLI 生成的骨架里默认值嵌在字符串字面量与聚合初始化中，两条正则都吃不到；
- 同型实例：测光空间增益**阶数**——文档与算法层都是零阶，装配层缺键即取**二阶**，且该键在出厂模板、defaults、登记册、schema、合同、插件文档**六面零登记**。

要求：① 一条门做**值级等式断言**（比较数值，不是比较键名集合），扫描面必须含 CLI 生成骨架与 `blocks[]` 形态，并配"注入反值必红"的负例；② 同一键的两侧兜底值不同的，视为缺陷当场消除分叉；③ 登记册与它所指向的文件不一致时，以文件现值为准并留痕。

### 3.4 度量的验证与真值同源 ⇒ 漂亮数字没有证据资格

- **面积求和闭合**：把某片面积×2、由邻居吸收，全天求和残差仍 ≤4.4e−16（浮点最后一位），而同一批面积逐片看错到 **−9.9%…+0.6%** ⇒ 求和型闭合的资格**只到完备性与全局标度，不含逐片正确性**。凡以"闭合到 1e−15/1e−16"当面积分配正确性证据的条目，证据类型都要换。
- **Oracle 基线存在自反行**：`measured = subj/ref[...]` 而基线分支里 `subj` 就等于那一项 ⇒ 恒 1.0、恒通过，且这些恒真行被登记为"实测"并**充当冻结容差的来源**（批内称 35 行中 18 行同形态，相邻行核为真两路对算 ⇒ 该比例按部分成立处理，须逐条复算）。恒真值一旦钉成容差，之后任何真实回归都与它比不出差别。
- **worker 均衡度**每份新产物恒 `50.00`（生产侧把同一值写进两栏）。
- **io 等待**等观测字段在生产**无填充点**，默认 0.0 而 0 是合法真值 ⇒ 依赖它的判据恒不触发；同族还有"分母为 0 返回 0.0"被当成 0% 利用率（与契约写的效应方向相反）。
- **资源门整体只落记录面**：`resource_gate.h:268-269` 无条件返回 `RecordOnly` ⇒ 资源类发现全部不进判定路径。凡据此报"资源约束已核查"的条目定级要降。
- 一条为 pixfrac 修复作证的门，其奇偶断言**按构造取在被检对象自身的量化格点上** ⇒ 对量化偏差结构性失明；它现在照绿是浮点巧合（换一档必红），且两条独立 oracle 明文不注册。

要求：凡"5 位一致／恒 0.0000／逐位相同"这类读数，先做**换一组不同源输入能否报出非零**的退化自测，再进正式文档；恒真行改记 `NOT_RUN`，不得充当容差来源。

### 3.5 单位、量纲与语义混用

- 同一利用率在一处是**单核百分比**、另一处是**已分配容量百分比**（"20% 门槛"实为 0.2 核）；节拍换算被当定义常数写死，而同文件另两处已在做系统查询。
- 像素 FWHM 被代进角秒公式（错 625 倍）；ordinary kriging 实为 simple kriging。
- `ADU` 与 `integrated_flux` 的语义组合在示例件里互斥（枚举自身定义与 §31.2 双向矛盾），且 schema 分支永不触发。
- 像素面积幂次：合同把 `pixel_area_power` 锁成常量，而生产门要求另一组幂次并附加关系 ⇒ **按合同通过的产品进生产门必红**（涉冻结面，走变更流程）。
- 精度默认：合同写 `fp64`，实现缺省四处 FP32，而真实权威口径是"稠密 FP32／稀疏 FP64"——被简化成了一个全局默认。
- 某 schema 同一对象同时声明 `default=0` 与 `exclusiveMinimum=0` ⇒ **登记值落在自身值域外**：照登记值填会被拒，与"省略"语义不等价。
- 采样周期这个判据敏感参数六处各写一遍，且配置文档的默认值栏空白。
