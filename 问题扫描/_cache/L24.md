### L24-001 Gaia 模块 manifest 拼接：snprintf 返回值推进指针 + 转义无容量参数 → 栈缓冲越界写
- 类别码: H_NUMERIC（主）；次挂 C_DOC_CODE_GAP、G_GOV_GATE
- 优先级: P0（前台已逐字复验锚点）
- 位置:
  - lib/gaia_xpsd_client/src/module_entry.c::gaia_execute（char head[512]，:738；hw += snprintf(...) :741/:770/:774；json_append_escaped(&hw, c.catalog_dir) :776）
  - 同文件::gaia_inspect（char buf[512] :930；json_append_escaped(&w, inst->cfg.catalog_dir) :939）
  - 同文件::json_append_escaped（:384，签名为 (char** w, const char* s)，无剩余容量入参）
  - 站点参数来源：同文件 gaia_cfg::catalog_dir 为 char catalog_dir[1024]（:211）
- 权威依据: 宪章 §14.4（信任边界含 CLI/配置输入与用户可控数据，须 fail-fast 返回明确状态码）、§8.6（跨 DLL 边界返回稳定状态码）、
  §11（不得吞错后继续生成看似成功的产品）；同文件 :24-27 自述的输出事务合同（尺寸查询→写入，不足→PARAM+BUFFER_TOO_SMALL）
  **只覆盖出参 strbuf，未覆盖这两个内部栈缓冲**
- 问题说明: 三重缺陷叠加。①转义函数逐字节无界写入；②snprintf 返回「本应写入的字符数」而非实际写入数，代码用它直接推进 hw，
  一旦头部（module_id+op+schema+spec 三字段与键名，实测约 330-390 字节）+ catalog_dir 超过 512，hw 越过数组末尾继续写；
  ③静态算术：head 剩余约 121 字节，而 catalog_dir 容量 1024、转义后最坏 2046 → 越界写最多约 1900 字节；
  gaia_inspect 更严重——w 越过 buf+512 后 (size_t)(buf + sizeof(buf) - w) 变成负数的 size_t 巨值，
  随后 snprintf 以近无限 max 继续格式化写出。不是"截断显示"级问题，是缓冲区溢出。
- 影响: astrocs_catalog_gaia 是随产品清单发布的官方模块；execute 是每次星表查询必经路径、inspect 是 host 诊断必经路径。
  触发条件仅要求 catalog_dir 超过约 121 字符——Windows 深路径、网络盘、含空格目录都会命中。后果为栈破坏：
  随机崩溃或被构造的目录字符串操控返回地址；Phase1/Phase2 均以该模块取参考星与光谱，属发布阻断级。
- 建议处置: ①json_append_escaped 增加剩余容量入参并返回是否溢出；②所有推进点对 snprintf 返回值取 min(返回, 剩余) 夹紧，
  越界即返回 ACS_ERR_PARAM/INTERNAL 并停止产品提交（只在边界校验一次，不在 CLI/AIO/算法层重复）；
  ③head/buf 改为「先精确计算所需长度再一次性分配」，与同文件出参两阶段合同同口径；
  ④负向用例：catalog_dir 120/121/1023 字符 + 含引号反斜杠 + 控制字符，断言不越界且状态码正确（ASan 版 ctest 注册）
- 置信度: 高（前台复验）
- related: S1-001（同族堆版：lib/hips/src/module_entry.cpp::hips_execute_write_product，预算 384u+strlen+64u 且同用无容量转义函数）

### L24-002 XPSD 自报 spectrumCount 无上限即用作每星 memcpy 长度 → 堆越界读 + OOM 放大
- 类别码: H_NUMERIC（主）；次挂 G_GOV_GATE（§14.4 外部文件解析边界）、B_STD_MISMATCH（Gaia DR3 光谱 343 列固定面）
- 优先级: P0
- 位置: lib/gaia_xpsd_client/src/gaia_client.c::load_xpsd_file（:1068 xf->spectrum_count = atoi(p + 14)）；
  消费点 ::spec_collector_push（:1266 memcpy(sc->spectra + count*spectrum_count, spectrum, spectrum_count)）；
  ::spec_collector_init（按 capacity*spectrum_count 分配）；布局常量 WL_COUNT=343、STAR_STRIDE_SP=40+(343+(343&1))=384；
  唯一处置点为「等于 0 才兜底」（:2049-2050、:2089-2090、:2240-2241、:2431-2432）
- 权威依据: 宪章 §14.4（外部文件解析属真信任边界；明文要求对"会造成数据破坏、安全问题或 ABI 未定义行为"的输入校验）、
  §5.3/§7.3（科学路径数值语义不得静默漂移）；D.catalog（Gaia DR3 光谱波段数固定 343）
- 问题说明: spectrum_count 来自文件内 XML parameters 字符串的 atoi，全文件**从未校验其是否 ≤343、是否为负、
  是否超过记录可用长度**。星记录在块内可用字节由 STAR_STRIDE_SP=384 固定，块长度又受限于文件自报的 block_size，
  于是 memcpy 的源长度由撒谎字段独立决定、与源缓冲真实长度无任何约束：声明 spectrumCount=100000 时每颗星从 p+40
  起读 100000 字节，越过 scratch 末尾约 99.6KB；同时按 capacity*spectrum_count 分配（4096*100000 ≈ 410MB/文件）。
  同文件其它自报计数都有上限（tree_count<16、file_count<MAX_FILES、magnitude 判 NaN/Inf 回落），说明作者知道这道防线，唯独此处漏。
- 影响: XPSD 是从外部拉取的持久化产品（GaiaDR3/、GaiaDR3SP/），属不受信输入。后果 ①堆越界读（崩溃或把相邻堆内容当光谱字节）；
  ②数百 MB 至数 GB 分配（OOM 放大）；③若侥幸不崩，越界字节经 base64 交给 lib/photometric_calib（pc_api.cpp 调
  gaia_client_cone_search_with_spectrum），即**污染测光定标所用光谱数值且不报错**（宪章 §11 禁止的吞错继续）。
- 建议处置: ①建立"文件自报计数"统一上限策略：1 ≤ spectrum_count ≤ WL_COUNT，越界即整文件拒绝并给显式损坏状态码
  （边界之后信任 typed contract，不在查询路径重复校验）；②spectrum_start/step/bits 同样校验；
  ③spec_collector_push 的 memcpy 长度改为 min(spectrum_count, 记录剩余可读字节)，源不足返回错误；
  ④负向用例注入 spectrumCount=0/1/343/344/65535/-1 六个 XPSD，断言拒绝与不越界（ASan 注册）
- 置信度: 高
- related: L10-008（同一 load_xpsd_file 的 header_len 弃用与 root_pos/child 不设限——本条是该族第四个未校验字段）

### L24-003 七个恶意输入回归测试从不进构建：注册门只做单向闭包，孤儿测试 TU 对机器门完全隐形
- 类别码: F_TEST_GAP（主）；次挂 G_GOV_GATE（门禁形同虚设）
- 优先级: P0
- 位置: 孤儿测试 TU（真源）lib/astro_image_io/tests/{test_p0_io_hardening.cpp, hips_robust_sanitize_driver.cpp,
  gaia_sanitize_driver.c, dataflow_fuzz.cpp, hiss_writer_smoke.cpp, pipeline_frame_contract_test.cpp} 与
  modules/services/io/tests/hips_core_selftest.c；门实现 tools/quality/check_ctest_registration.py
  （C1 universe 定义 :9-17、C3 判定 :99-120/:167-174，ADD_TEST_NAME_RE 只匹配 add_test(NAME …)）；
  正面对照 tests/unit/CMakeLists.txt::p1_io_hardening_test（:761-769 add_executable+add_test）、::hips_publish_atomic_test（:566-580）
- 权威依据: 宪章 §13.1/§13.2、§12.3-4、§14.4 末段（对已观察到的故障建立最小复现与机器测试）、§17.2、§17.10；
  本仓 CI-REG-002 立规目的自述（STD-F7：新增测试目标须被 CI 显式登记）
- 问题说明: CI-REG-002 的判定 universe 是「add_test 名字集合」，因此只能发现「已 add_test 但未登记 CI」，
  **无法发现"测试源文件从不进 add_executable/add_test"**——后者对门完全不可见，是该门的结构性单向闭包缺陷。
  漏网的恰是本轴最重要的加固成果：26 个 AIO extern "C" 入口异常屏障、HISS/AHPX 恶意 fixture 四连、
  XPSD 真实解析 ASan/UBSan 驱动、HiPS MOC 与 SNR TSV 行数上限、dataflow 模糊器、HISS 写出烟测、管线帧合同、IO-002 全套自测。
  多数文件头还自述为「P0 修复的复现测试」；test_p0_io_hardening.cpp 的唯一"运行方式"是文件头的 g++ 注释行。
  grep 实证：7 个文件名在真源 CMakeLists.txt / ci/checks.json / .github/workflows 均 0 命中；
  两个 sanitize driver 仅被 lib/astro_image_io/tests/sanitize_wsl_v4.sh、v5.sh 引用。
- 影响: 影响的是"机器门可发现性"本身——约 6000 行验证代码上 §13 必备测试与 §17.2 追溯无断链不成立，且 CI 全绿不可证伪；
  直接后果是任何后续改动（含正在进行的 RESCUE-V3 批次）把边界校验改回去都不会被发现。
  同域 p1_io_hardening / hips_publish_atomic 均已注册，说明这是遗漏而非风格差异。
  另 lib/orchestrator/cpp 整树无 CMakeLists.txt（靠该目录 Makefile 手工构建），其原子写出与 checkpoint 修复同样无保护。
- 建议处置: ①给 CI-REG-002 补反向闭包 C7：扫描 tests/ 与 lib/**/tests/ 下含 main() 或自述为 test 的 C/C++/py TU，
  凡未出现在任何 add_executable/add_test/注册脚本即 FAIL（并补负例自检）；②7 个 TU 逐个定归属：能进 ctest 的进
  tests/unit/CMakeLists.txt 并入 ci/checks.json 的 UT-AIO/UT-IO（sanitize 类可单列非默认 profile 但必须在册），
  确认废弃的**删除**而不是留在树里充当证据；③lib/orchestrator/cpp 要么入构建，要么按 §14.1 明示非交付状态并停止在交付文档中引用其行为
- 置信度: 高
- related: S3-017（orchestrator 整树不注册）、F00-03（同类"门对不可见对象失灵"）、L22-005（修复未固化）、L16-001（TEST 层锚在文档）
