### L15-001 HiPS tile 目录与文件名规则与 IVOA 标准相反

- 类别: B_STD_MISMATCH
- 建议优先级: P0
- 位置: docs/standards/STANDARDS_REGISTRY.md:93；lib/astro_image_io/src/hips/aio_hips_writer.cpp:136-141；lib/astro_image_io/src/hips/aio_hips_reader.cpp:38-43；docs/interfaces/io/IO_002_HIPS_INPUT_INTERFACE.md:92-93
- 证据摘录:
  > | §3（层级索引与 NorderK/DirD/NpixN 目录结构） | 层级 tile 目录命名与 NESTED 地址编码固定 | CONFORMANT | docs/interfaces/io/IO_002_HIPS_INPUT_INTERFACE.md；lib/astro_image_io/src/hips/aio_hips_writer.cpp；tests/unit/CMakeLists.txt | 无（D=ipix/10000、N=ipix%10000 与读侧同一合同） |
  > uint64_t dir = ipix / 10000;
  >     uint64_t npix = ipix % 10000;
  >     std::snprintf(buf, sizeof(buf), "Norder%d/Dir%llu/Npix%llu%s",
  - 标准原文（web_fetch 实测，http://www.ivoa.net/documents/HiPS/20170406/PR-HIPS-1.0-20170406.pdf §4.1）:
  > Tile N in order K → Norder K/Dir D/Npix N{.ext} where D=( N/10000)*10000 (integer division) …
  > Example: the tile containing the HiPS data corresponding to the HEALPix cell index 10302 at the order 6 will be stored in the file Norder6/Dir10000/Npix10302
- 权威依据: IVOA HiPS 1.0 §4.1（HiPS directory structure）；STD-REG-001 §1.2（禁止按实现反推标准）；宪章 §12.3-10
- 问题说明: 标准里 Dir 目录名是**分组起始下标**（D=(N/10000)·10000，如 Dir0 / Dir10000 / Dir20000），文件名带**完整** tile 号
  （Npix10302）。本实现把两者互换：目录名写商（Dir1）、文件名写余数（Npix302）。N<10000 时两式巧合相同，
  N≥10000 时目录名与文件名同时错。注册表不但未登记该偏差，反而把实现算式当作「标准要求」写进清单行的偏差列，
  并以「与读侧同一合同」为符合依据——读侧同为错式，属自证闭环，不是对标准的符合性证据。
- 影响: tile_order ≥ 6（leaf nside ≥ 32768，N=12·4^K ≥ 49152）的真实 HiPS 产品中 ipix≥10000 的 tile 全部落到
  非标准路径；Aladin/CDS hipsgen 消费者按标准拼路径取不到 tile（404），产品对外不合规、不可浏览。
  Phase1/Phase3 HiPS 产品面直接受影响。
- 建议处置: ① 按标准改写 tile_rel_path/tile_path 为 `Dir=(ipix/10000)*10000`、`Npix{ipix}`；② 注册表该行「标准要求」
  订正为标准算式并引 §4.1（非 §3），偏差列在收敛前挂真实偏差 ID；③ 补一条标准示例锚用例（10302→Dir10000/Npix10302）。
- 置信度: 高
- related: L15-003、L15-008、DISP-HIPS-*

### L15-006 交付 FITS 恒带 CHECKSUM 全零占位卡，D.fits §6 行仍判 CONFORMANT

- 类别: B_STD_MISMATCH
- 建议优先级: P0
- 位置: runtime/io/fits_core.c:1151-1155、1261-1270、1449-1462、1646-1656；docs/interfaces/io/IO_001_FITS_STREAM_INTERFACE.md:139；docs/standards/STANDARDS_REGISTRY.md:223
- 证据摘录:
  > /* 首次数据写入前写 header (恒预留 DATASUM 槽; CHECKSUM 槽预留与否留到 end —
  >  * 由于布局固定性, 恒预留两个槽, end 时按需改写或保持空白/零值)。 */
  >                                     1 /*reserve_datasum*/, 1 /*reserve_checksum*/,
  >     fio_card_write(f, "CHECKSUM", "0000000000000000", "HDU checksum updated");
  >         if (sum != decoded && sum != 0xFFFFFFFFUL && sum != 0UL) {
- 权威依据: FITS 4.0 保留关键字 CHECKSUM/DATASUM（正文 §4.4.2 关键字定义 + 附录 J "CHECKSUM implementation
  guidelines"：J.1 推荐实现、J.2 ASCII 编码、J.5 累加示例 C 码）；宪章 §8.3/§17.6（禁结构合法但语义虚假的伪产品）
- 问题说明: ① 写路径**无条件**预留并写出 `CHECKSUM = '0000000000000000'`，而 IO_001:139 声称"CHECKSUM 卡由调用方选项决定
  （默认关闭）"——文档说卡默认不写，代码说卡恒写。按标准附录 J 的编码约定，全零 ASCII 解出的是确定的校验值（等价
  sum=0/0xFFFFFFFF 侧），把它留在交付文件里等于在保留关键字中声明一个与 HDU 实际内容不符的校验和，且卡注释写
  "HDU checksum updated"（并未更新）。② verify 侧的豁免设在**计算值**一侧（`sum != 0xFFFFFFFF && sum != 0` 才报错），
  而非"卡值为占位即跳过"，逻辑倒置：重算值恰为 0/0xFFFFFFFF 的任意文件都判通过（篡改不报），
  而带占位卡的正常产品在 verify_checksum=1 下必然落入 mismatch 分支。③ 在位测试仅覆盖 `checksum=1` 组合
  （tests/io/test_fits_stream_contract.py:286），"占位卡 × verify=1"零测试。
- 影响: 交付 FITS 产品对 astropy/fitsverify 类第三方校验器呈"CHECKSUM 不符"，产品合规性受损；自研 verify 在
  verify=1 时对自家默认产物给出假失败、对特定计算值给出假通过——校验门的判别力被削弱。
- 建议处置: 写路径二选一（不写卡 / 必算真值），占位只在临时文件期存在；verify 豁免改判**卡值**是否为占位并返回显式
  "未校验"状态；补 "占位卡 × verify=1" 与 "篡改 + 重算值=0" 两条负测；注册表 §6 行改判 PARTIAL 并登记偏差 ID。
- 置信度: 高（占位恒写与豁免位置为代码事实；"第三方判为不符"为按标准编码规则的推论）
- related: L15-007、L10 报（modules/services/io fits_core 同族问题）
