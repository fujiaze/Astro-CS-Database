### 1.6 对 L24-011（M9-G-4）定级的直接影响（本任务关键交付）

负责人 B-08 的原问法是「longPathAware 决定 512/PATH_MAX 系缺陷定级」。实测答案的方向与直觉相反，必须写清:

- **未声明 longPathAware 既不能减轻也不能加重 512 塌缩**: 塌缩源是定长缓冲 `ACS_FIO_PATH_MAX=512`（`modules/services/io/include/astrocs/io/fits_stream_v1.h:33`）加 `snprintf` 不查返回值，与 OS 是否允许长路径无关。**即使声明了 longPathAware，511 字节处的塌缩仍在**。
- 本地重算的塌缩阈值（`run/审计执行层/E4/collapse_recompute.py`，纯字符串算术）:
```
strlen=509  target_len=509  tmp_len=511  tmp==target? False
strlen=510  target_len=510  tmp_len=511  tmp==target? False
strlen=511  target_len=511  tmp_len=511  tmp==target? True
strlen=600  target_len=511  tmp_len=511  tmp==target? True
Linux PATH_MAX (os.pathconf on /tmp): 4096   NAME_MAX: 255
```
- ⇒ **改判（方向修正，不推翻事实）**: M9-G-4 现文「Linux 无 PATH_MAX 硬限制 → 该形态主要在 Windows 正式平台必现」（`问题扫描/findings/G_GOV_GATE/p1/M9_L24_L26.md:71`）与本实测冲突: 触发条件要求 `strlen(path_utf8) >= 511`，而未声明 longPathAware 的 Windows 进程对 >260 路径本就大概率在更早一步失败；反而是 **Linux（实测 PATH_MAX=4096）能让 511~4095 字符路径合法打开并真的走到 `tmp==target`**。即塌缩这一半**不必等 Windows 实测**，在 CI 主跑的 Linux 上就可达；Windows 那一半（>260 的确切失败点与错误码）仍待实测。
- 测试面缺口实证（静态可定）: `grep -rIn -e 511 -e 512 -e long_path -e longpath -e PATH_MAX -e deep tests/io tests/unit tests/cli tests/api` → 命中只有 HiPS tile 宽度 512（`tests/io/test_hips_input_contract.py:171,179,189-237`、`make_hips_fixture.py:145`）与无关 CRPIX `512.5` ⇒ **无任何路径长度回归用例**，条目建议处置③（511/512/508 三档）确认为零。
- 缓冲宽度不一致（静态可定）: `ACS_FIO_PATH_MAX=512`（IO-001）与 `PUBLISH_PATH_MAX=1024`（`lib/hips/src/aio_publish.cpp:39`、`:54` 两分支同值）、`ACS_HIPS_PATH_MAX=1024` 同仓并存 ⇒「唯一写出边界」实有三种路径上限口径。

### 2.4 既有真机日志已判定的一条（不改判、只补强）

MSVC STL `std::filesystem::rename` 覆盖已存在目标 = **可行**（在真 Windows 主机上通过）。三段证据:
