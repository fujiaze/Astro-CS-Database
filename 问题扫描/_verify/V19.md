## 5. 轴④ · 前序检查项产物 vs 声明顺序 / changed_paths

- **顺序是唯一机制**：`ci/run.py`:1263 `for check in selected` 按数组下标串行；`deep_ci_driver.py`:27-30 自证"build dir 由登记顺序保证（BUILD-GCC-RELEASE 或 CTEST-LINUX-FULL 先行）"。
- 唯一被机器守住的顺序契约是 `validate_registry.py` **R10**（linux-main 末位必须是 KNOWN-FAILURES-BASELINE-CHECK）。正对照很好，但它**不在该 profile 顺序校验之外覆盖任何东西**：41 道 `run/ci/` 消费者与生产者之间无顺序声明。
- **`--changed-from` 选择性失明**：`select_checks` 的该分支只经 `impact_map` 规则映射，而 `ci/impact_map.json` 24 条 rule + fallback 对生产者/消费者**双零覆盖**：
```
=== B) do CONSUMERS appear in any rule at all? ===
  consumers not reachable via impact_map at all: 42/42
  producers reachable: {'BUILD-GCC-RELEASE': False, 'CTEST-LINUX-FULL': False, 'LINUX-MAIN-BUILD-TREE': False,
                        'LINUX-MAIN-FIXTURES': False, 'WIN-BUILD-RELEASE': False, 'WIN-PACKAGE-CANDIDATE': False}
```
  （`scripts_v19_rules.py`；42 = 现值，含本轮新增的 2 道 CTEST 门）。⇒ 定向复跑面整条"构建+ctest"链不可选（与 V9-N-12 的 71/130 触达率互为表里，挂 related 不重报）。
- **`--focus` 会选消费者不选生产者**（实测 6 例，`scripts_v19_focus.py`）：
```
  path ci/checks.json                    consumers-selected=3   producers-selected=[] NONE
      e.g. ['WIN-CANDIDATE-VALIDATE','CTEST-REGISTRATION','KNOWN-FAILURES-BASELINE-CHECK']
  path tools/quality/deep_ci_driver.py   consumers-selected=3   producers-selected=[] NONE
  path include/astrocs/phase2/upm.h      consumers-selected=22  producers=[BUILD-GCC-RELEASE,WIN-BUILD-RELEASE,WIN-PACKAGE-CANDIDATE]（无 LINUX-MAIN-*）
```
  ⇒ 改 CI 注册表或改 40 门共同实现体 `deep_ci_driver.py` 时，`--focus` 只会把消费门挑出来在未构建的 build dir 上跑（红是好事，但**归因失真**：报的是"构建缺失"不是"你改坏了什么"）；且 `deep_ci_driver.py` **不在任何门的 `changed_paths` 里**（实测 `changed_paths contain it: []`），`impact_map` 的 `tools/quality/**` 规则选中的 18 门里也不含任何 CTEST 门（N-07 附带施工项）。
- **fail-closed 的正对照（勿当缺陷）**：`known_failures_baseline.py::parse_ctest_junit`（:355-382）缺文件→error、零 testcase→error；`compare_failures`（:452-457）"基线有条目但本次无该来源结果"→ error 并注明"fail-closed：不得静默跳过"；`wf_step.py` 的 `require_outputs + fail_closed`；`deep_ci_driver._run_steps` 缺可执行/坏 cwd → rc 127。⇒ 本轴建议一律"向这些既有写法对齐"，不新发明。
