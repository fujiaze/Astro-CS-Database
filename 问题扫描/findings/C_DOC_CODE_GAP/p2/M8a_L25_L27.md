## M8a-C-007 dependency-lock 声称「无 ACS_ZLIB_ROOT 则 cfitsio 降级不编译 zcompress」，与根产品构建图实路相反

- 类别: C_DOC_CODE_GAP
- 定稿优先级: P2
- 位置: `packaging/dependency-lock.json::system_dependencies[zlib].policy`（复核 48）；`cmake/cfitsio_sources.cmake::ASTROCS_CFITSIO_SOURCES`（复核 61 zcompress.c 在清单内）；`CMakeLists.txt::astrocs_cfitsio MSVC 段`（复核 275、281、287-307）；`lib/astro_image_io/third_party/cfitsio/zcompress.c::include`（复核 6）；对照 `cli/CMakeLists.txt::降级分支`（复核 121、204-215）
- 证据摘录:
  > lock:48 「MSVC: cfitsio zcompress.c 需 zlib → ACS_ZLIB_ROOT cache 变量显式指定(默认空, 不硬编码用户路径); **无 ACS_ZLIB_ROOT 时 cfitsio 降级(不编译 zcompress 路径)**」
  > cmake/cfitsio_sources.cmake:61 `lib/astro_image_io/third_party/cfitsio/zcompress.c`（无条件在 60 源清单内）；zcompress.c:6 `#include "zlib.h"`（无任何 `#ifdef` 守卫）
  > 根 CMakeLists:288 `if(ACS_ZLIB_ROOT)` 分支只做 include/link，**没有 else 剔除源**；:303 分支内 `message(FATAL_ERROR …)`
  > 真正的"warning + 降级"实现只在遗留 compat 工程：`cli/CMakeLists.txt:206-209` 「# 无 ACS_ZLIB_ROOT 时降级处理 (不编译 zcompress 路径, 见 lock policy)」+ `message(WARNING "BLD-004: ACS_ZLIB_ROOT 未指定 — MSVC zlib 路径降级…")`
- 权威依据: 宪章 §12.3-1（构建/清单/文档一致）、§14.4（fail-fast 语义要如实）
- 问题说明: 自标 `ACTIVE_NORMATIVE` 的锁，其对 MSVC 缺省路径的行为描述方向与根产品图相反 —— 根图恒把 `zcompress.c` 列入 60 源且该文件无条件 include `zlib.h`，因此未设 `ACS_ZLIB_ROOT` 时是**编译期硬失败**，不是降级；锁描述的其实是 cli 遗留 compat 工程的行为（该工程自己的注释还反向引用锁作为依据，形成互引循环）。这不是数值风险，而是 Windows 正式平台构建预案与 waiver 判断的事实依据失真。
- 影响: Windows/MSVC 构建者据锁以为"不设就自动降级"，实际会在 configure/compile 阶段失败；BLD-004 语义与实现两套口径。
- 建议处置: 二选一：①订正锁措辞为「根产品图恒编译 zcompress；MSVC 未设 ACS_ZLIB_ROOT 即编译失败（fail-fast），降级仅存在于 `cli/` 遗留 compat 工程」；②或在根图实现真实降级（剔除源 + 登记产品能力差为 DISP），并把 `cli/CMakeLists.txt` 的互引注释一并收敛。
- 置信度: 高（静态读入判断，未跑构建验证）
- 来源: L25-010
- related: M8a-C-003（同目录 vendored cfitsio 与"零外部依赖"叙述）、M8a-G-010

## M8a-C-009 test-only oracle 依赖群未入锁：astropy-healpix / scipy / rcr 三例，且 oracle 脚本内写死平台耦合

- 类别: C_DOC_CODE_GAP
- 定稿优先级: P2
- 位置: `packaging/dependency-lock.json::test_only_oracles`（复核 85-133，条目名 = astropy / numpy / pytest / astrometry.net）；`DEPENDENCIES.md::test-only oracle`（复核 75-79）；`lib/phase2/tools/satellite_gate_build.py::import`（27）、`lib/phase2/tools/controlled_rejection_truth.py::import`（21）；`lib/phase2/tools/rcr_oracle_compare.py::CLI 缺省`（17-20）；`ci/toolchain.policy.json::deep_coverage_tools.apt_packages`（27）；`lib/common/healpix/THIRD_PARTY_NOTICE.md`（28）
- 证据摘录:
  > satellite_gate_build.py:27 与 controlled_rejection_truth.py:21 「`from astropy_healpix import HEALPix, lonlat_to_healpix, healpix_to_pix`…」
  > THIRD_PARTY_NOTICE.md:28 「| astropy-healpix | 1.0.3 (测试环境) | BSD-3-Clause | 全天空 Oracle |」（版本记于 NOTICE，却不在锁）
  > rcr_oracle_compare.py:17-20 CLI 缺省 = `str(ROOT / "lib" / "phase2" / "build" / "rejection_cli.exe")`（Linux 控制节点必须靠 `ASTROCS_REJECTION_CLI` 环境变量纠正）
  > ci/toolchain.policy.json:27 apt 安装含 `"python3-scipy"`；全 `tests/` grep `^import scipy|from scipy` **0 命中**
  - 计数口径：`test_only_oracles` 实有 **4** 条（astropy/numpy/pytest/astrometry.net），`astropy-healpix`/`scipy`/`rcr` **0 条**（对 lock 单文件 grep 复核）。
- 权威依据: 宪章 §13.1（独立 Oracle 须可复验）、§12.3-1、§16.2
- 问题说明: 三件事叠在一个面上：①`astropy-healpix` 是天空域对拍工具（版本仅活在一份未标状态的 NOTICE 表里），不在自称"分离锁定"的 `test_only_oracles`；②`scipy` 被 policy 装进控制节点但仓内 `tests/` 零引用，装机清单与真实用例脱钩；③`rcr` oracle 的版本锚只有注释里的包版本 + commit 号，脚本对平台产物名写死 `.exe`（§15/§3.1 双平台职责面），无哈希、无许可采集。附带：`astropy` 记为「>=5（现值 7.x）」、`numpy`/`pytest` 记为 `system` —— "system"在依赖锁语境下即"未锁"。
- 影响: Oracle 可复现性无锚（§13.1 面）；依赖盘点面向 CI 与锁两侧各说一半。
- 建议处置: `test_only_oracles` 补 astropy-healpix / rcr（版本 + 来源 + 许可 + 安装方式），scipy 则删除安装或补登记真实用例；oracle 脚本产物名按平台解析（`rejection_cli[.exe]`）；`system`/`>=N` 两类写法制订统一口径（要么锁到版本，要么显式标"未锁+理由"）。
- 置信度: 高
- 来源: L25-012
- related: M8a-B-001（rcr 权威锚定面，两轴各计一次不重复）、L03-006（healpix 证据不可复现主落）
