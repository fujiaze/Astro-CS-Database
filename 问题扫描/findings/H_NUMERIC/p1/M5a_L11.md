### M5a-H-001 出厂 CPU provider 的 Drizzle/积分/UPM 内核以 float32 累积并用裸 1e-6f 静默归零
- 类别: H_NUMERIC
- 建议优先级: P1（原 L11-011 报 P0；因本轮未能证明该 provider 位于生产重计算路径而改判，见「影响」与 _merge 移交清单）
- 来源: L11-011（与 L04-001 为同一事实的两个视角：M5a 落 provider/内核侧，M2a 落 drizzle/元数据侧）
- 位置:

  - `providers/cpu/baseline/include/astrocs/cpu/baseline_provider_v1.h`（:48-49 NaN 语义合同、:108-109 与 :116 逐 op 公式）
  - `cmake/install_layout.cmake:63-64`（该 DSO 自述为 Linux 技术预览、legacy backend ABI）
  - 权威：宪章 §5.3、§7.3；`docs/standards/NUMERIC_STANDARD.md` L8/L15/L16/L22；`docs/architecture/ISA_BIT_MANIP_VARIANTS.md:15,19`
- 权威依据: 宪章 §5.3（「Drizzle 采用 float64 累积、按合同输出 float32/float64」）、§4.1/§7.3；`docs/standards/NUMERIC_STANDARD.md` MUST 条 L13（NaN/Inf 须显式 INVALID_*）/L15（科学累积用 FP64/stable sums）/L16（禁止裸 `1e-6` 无来源）/L22（全 0/NaN/Inf 权重 → ZERO_VALID_WEIGHT/INVALID_INPUT）与 L8（默认 science=FP64）；`docs/architecture/ISA_BIT_MANIP_VARIANTS.md:15,19`；§12.3-3
- 证据摘录:
  >     case ACS_CPU_KIDX_DRIZZLE_ACCUMULATE: {
  >             float acc = 0.0f;
  >             for (uint64_t f = 0; f < frames; ++f)      /* 固定帧序 (f32 累加) */
  >                 acc += a[f * N + i] * b[f * N + i];
  >             o[i] = (wsum > 1e-6f) ? (acc / wsum) : 0.0f;
  >  *                        out0[i]= wsum>1e-6f ? Σw*x/Σw : 0
  - 宪章 §5.3：「Drizzle 采用 float64 累积、按合同输出 float32/float64」
  - NUMERIC_STANDARD L16：「epsilon 必须说明物理/数值来源，禁止裸 `1e-6` 无来源。」；L22：「全 0 / NaN / Inf 权重 → ZERO_VALID_WEIGHT / INVALID_INPUT。」
- 问题说明: ① 累加域：drizzle-accumulate 与 integration-accumulate 两个科学内核在 `float` 中累加帧序乘积与权重和，公共头 :108/:116 还把该式写成对外合同，与 §5.3 冻结的 float64 累积直接冲突（长帧序下相对误差按 float32 eps 累积）。② 静默语义：`wsum > 1e-6f` 不满足时输出 `0.0f`，把「无有效数据」与「科学值为 0」合并；头文件 :48-49 进一步声明「NaN 权重 → 0 输出」，而 NUMERIC_STANDARD L13/L22 要求显式 INVALID_*/ZERO_VALID_WEIGHT 状态。③ 该 epsilon 无任何出处（复算：全仓检索该常数只在内核与头文件出现，`docs/architecture/cpu/` 内 `1e-6` 零命中）→ 违 L16 的裸常数禁止。④ UPM SpMV（:291）对越界列静默置 0，注释自认「应被校验」。⑤ 精度降级在 `docs/architecture/ISA_BIT_MANIP_VARIANTS.md:15,19` 被登记为「纯 float」实现事实，而非精度偏差 → 未走偏差登记。
- 影响: 凡走该 provider 的 drizzle/积分/UPM 路径，累加精度低于宪章要求，退化权重产出看似合法的 0 值产品。**可达性界定（本轮无法闭环）**：`ACS_CPU_KIDX_*` 与 provider 入口在 `lib/ cli/ runtime/ modules/` 内零调用点，仅 `tests/cpu/**` 以 dlopen 方式驱动；但 `packaging/astrocs.product.json:17` 与 install 树都把 PROV-CPU-BASELINE 列为随产品交付单元，运行期 dlopen 面静态不可判 → 故本条按「不合规的出厂合同」定 P1，若前台以 `astrocs doctor --json`/真实 run trace 证实科学节点经该 provider 执行，立即升 P0。
- 建议处置: 累加器改 float64（或按 SCI 合同显式登记容差与来源并走 §1.2）；退化权重/NaN 返回显式状态（ZERO_VALID_WEIGHT / INVALID_INPUT）而非 0；`1e-6f` 换为有来源常数并在 ALG/SCI 登记；把该 provider 的实际调用面写进 ARCH 或在产品清单中标注未接入。
- 置信度: 中（代码与合同不一致为高置信；生产可达性未证）
