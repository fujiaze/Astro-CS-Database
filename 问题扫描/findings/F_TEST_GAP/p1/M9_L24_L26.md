- **本代理数值口径（重算，不采信转述）**：以 `deg = (180/π)·√(π/3)/nside`（const 58.6323…）与 `arcsec = 3600·deg`（const 211076.285…）两式，对 nside 取 2^k 与 3·2^k 两族，解 `k = log2(const/值)` 并取最近整数后回代，判「可归约/不可归约」；再对每个并存值同时试两式：
  > 11.519173063162576 → deg 式 k=2.348、arcsec 式 k=14.161（均非整数）→ **两式皆不可归约**（叶子亦判不可归约，一致）；0.0001125 → k=18.99/30.81，且其同文件声明的 order=7 若按 deg 式应为 8.946e-4、按 arcsec 式应为 3.2208 → **与该真源自己的 hips_order=7 也不自洽**；58.6 → deg 式 k=0.0008（≈nside=1 的 deg 值 58.6323 的手填近似），而其同文件写出真实 `hips_order={leaf_order}` → **值与自身 order 脱钩**；3.220769 → **arcsec 式在 nside=65536（order=16）精确命中**（本代理回代核对）→ 该值是"与产品角秒口径自洽"的正确派生值，不是发明值（**此处细化叶子的分类**）；O4 在 nside=512 的期望串 412.2583694180887 → 与 arcsec 式一致（同口径）。

- 问题说明: ①产品与"独立 oracle"使用**同一公式、同一单位、同一格式化方式**，故该测试不可能发现单位错误——它验证的是"实现等于实现"，不是"实现符合标准"；②全仓五套 hips_pixel_scale 数值分属三种不同生成规则（两族 nside × deg/arcsec 双口径 + 手填值），经本代理归约核算后**没有任何两个站点在同一口径上互相印证**，即不存在事实源；③读端合同明文不校验该键（IO_002:78），文档反而把角秒口径规范化（HIPS_WRITER.md:186）→ 错误口径有三道"合法化"通道而无一道拦截通道；④无 disp 登记把它作为标准偏差固化（D.hips 相应行仍按 CONFORMANT 处理，见 M9-E-1）。
