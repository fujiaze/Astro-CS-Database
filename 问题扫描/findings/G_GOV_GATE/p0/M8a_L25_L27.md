## M8a-G-002 GPL 的 GSL 经 PUBLIC 链接进入交付 exe `astrocs`，依赖权威四处零登记

- 定稿优先级: P0（发布阻断）

  > packaging/dependency-lock.json 全文对 `gsl` **0 命中**（该文件自标 `doc_status: ACTIVE_NORMATIVE`）

- 权威依据: 宪章 §16.2（发布包至少含「许可证」「build provenance」）、§17.11（白名单/哈希/版本/provenance 全部通过）、§12.3-1、§15.2（Windows 正式工具链为 MSVC v143）；GSL 官方许可页 https://www.gnu.org/software/gsl/doc/html/gpl.html （GSL = GNU GPL）。
- 问题说明: 闭包可机器复核：`astrocs_p1_sdet` 为 STATIC，其 `PUBLIC` 链接需求沿 `astrocs_module_adapters → astrocs_cli_runtime → astrocs` 逐层传播（同链上还挂着 M8a-G-001 的 `astrocs_p1_ipv`），最终交付的可执行文件确以 GSL 符号为链接前提。而两处自称权威的登记面（`DEPENDENCIES.md` 自称「版本锁定权威」；`dependency-lock.json` 自标 ACTIVE_NORMATIVE）对该库**完全失明**：无版本、无哈希、无来源、`packaging/licenses/` 无许可文本、`packaging/gen_sbom_input.py` 的 SBOM 输入也不含它。矛盾的是 CI 面**知道** GSL 存在（apt 允许清单 + 头文件断言步），所以这不是遗漏一个未知依赖，而是「CI 前提登记面」与「依赖权威锁」两套账不一致。附带两点：①Linux 侧 `-lgsl` 实际解析取决于发行版（`libgsl-dev` 同时提供 .so 与 .a），因此本条不断言"静态传染"这一具体形态，只断言「GPL 组件进入产品链接闭包且无任何许可/来源/版本登记」；②Windows 正式平台上 GSL 不在锁、不在工具链锁、`ci/toolchain.policy.json` 的 MSVC 侧亦无对应条目 —— 交付图上该依赖处于未定义状态（此半属 M5b 构建图域，此处仅登记依赖面，related 指回）。
- 影响: 直接命中 §16.2 与 §17.11，发布候选在许可/provenance 门上不具备通过条件；GSL 大版本 ABI 漂移无锚可查；§17.10 连带不成立。
- 建议处置: ①在 lock 增 `gsl`（system 或 vendored 均可，需版本 floor + 哈希策略 + 许可指针），同步 DEPENDENCIES.md 与 SBOM 输入；②负责人裁决 copyleft 义务履行方式（随包 GPL 文本 + 源码提供承诺，或改用非 copyleft 求解器/动态化策略）；③补 `libgsl-dev` 之外的 Windows 侧策略说明；④加机器门：枚举 CMake `target_link_libraries` 的外部裸库名与 lock 名单做双向差集（见 M8a-G-007）。
- 置信度: 高（链接闭包、四处零登记、CI 面已知悉均为仓内字面事实；仅"静态/动态传染形态"与"Windows 可构建性"两点标注为未跑构建的推断）
- 来源: L25-002
