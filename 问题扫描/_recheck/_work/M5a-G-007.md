- 权威依据: 宪章 §3.1（正式入口含 Windows 10+ amd64 `astrocs.exe`）、§10.4（CPU-heavy 必须多线程）、§10.5（只有一个活跃计算线程即失败）、§17.6、§12.3-8
- 问题说明: 根构建的 OpenMP 探测被 `if(UNIX)` 包住，三个遗留 target 的 `-fopenmp` 亦只在 `UNIX AND OpenMP_CXX_FOUND` 下追加 → MSVC 生产构建中这些 target 的 `#pragma omp parallel for` 被编译器忽略而串行执行。同一根图内 `astrocs_p1_dpsf`/`astrocs_p1_sdet` 无条件 PUBLIC 链接 `OpenMP::OpenMP_CXX`，其 target 存在依赖 `tests/unit/CMakeLists.txt` 的额外 `find_package(OpenMP)`（生产图依赖测试子图才成立），同平台内并行性自相矛盾。文档侧 `EXECUTION_MODEL.md:9` 把 Stage1 calibrate 写成「per-tile OpenMP / 最大并发 16 / 证据 `calibrator.cpp: OpenMP 16`」，`THREADING_MODEL.md:5-7` 同口径，均未按平台区分。唯一登记处在 packaging 依赖锁的策略字段（且写「生产不依赖」），不在偏差索引、也不与 ARCH 文档互引。
- 影响: Windows（正式验证平台 / Fatduck）上 Phase1 校准与 Drizzle 重计算为单线程，直接触达 §10.4/§10.5 禁止项；§13.1 的「Windows/Linux 允许误差合同」无法在同一并发模型假设下推证；Fatduck 侧利用率数据含义与 Linux 不同，而门禁与文档均无该平台差异处理。
- 建议处置: 为 MSVC 明确并行实现（`/openmp` 或 std::thread executor），EXECUTION_MODEL/THREADING_MODEL 按平台分行登记；若暂不支持则登记偏差并在 §17.6 资源门中显式处理，不得静默串行；`OpenMP::OpenMP_CXX` 的可见来源收进根图（不依赖 tests 子图）。
