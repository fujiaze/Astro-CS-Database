### M5b-C-05 退出码在合同文档/C++ 唯一源/Runtime 映射三处互不覆盖，文档还规范化了已废弃的 orchestrator 码表
- 类别: C_DOC_CODE_GAP · 建议优先级: P1
- 位置: `docs/architecture/ERROR_MODEL.md::编排退出码`（现 :22-34）；`docs/architecture/ERROR_MODEL.md::V19R3 修正记录`（现 :41-44）；`cli/exit_codes.h::ExitCode`（现 :7-19）；`cli/runtime_client.cpp::exit_code_from_error`（现 :373 注释、:393 `case RESOURCE: return 5;`）；`ci/checks.json`（`docs_machine_consistency` 命中数 0）；`tools/docs_machine_consistency.py::main`（现 :178 `return 0 if pass else 1`）；`tools/check_api_docs.py::EXIT_NAMES`（现 :27）
- 证据摘录:
  > SUCCESS=0  GENERIC_ERROR=1  DLL_LOAD_FAILED=2  BLOCK_MISSING=3
  > CALIBRATE_FAILED=4  PLATESOLVE_FAILED=5  DRIZZLE_FAILED=6
  > CONFIG_ERROR=7  FILE_IO_ERROR=8  TIMEOUT=9  CANCELLED=10
  >   RESOURCE      = 10,  // 资源利用率或内存增长门禁失败
  >       case astrocs::core::ErrorDomain::RESOURCE: return 5;
- 权威依据: 宪章 §8.1（稳定退出码）、§11（统一状态码 + 结构化诊断传播）、§12.3-1/-9/-10
- 问题说明: ①文档规定的 `orchestrator.exe` 码表与 C++ 唯一源除 0 外全部数值同键异义（文档 2=DLL_LOAD_FAILED vs 唯一源 2=ARGS；10=CANCELLED vs RESOURCE；文档 6=DRIZZLE_FAILED vs 唯一源 6=COMPUTE），而 `orchestrator.exe` 属 ARCH-001 §7 已登记退出的 LEG-001/002 旧路径；:41-44 反而把这张表宣布为"现与 orchestrator.h 枚举 name+value 集合完全一致"，并称由 `docs_machine_consistency` 全量校验——该检查器在 `ci/checks.json` 中命中数为 0 ⇒ 无人执行的一致性声明。②实现侧 `exit_code_from_error` 把 `RESOURCE` 域映射成 5（BACKEND），而 `RESOURCE=10` 恰是为 GUI 区分资源门失败而设的冻结码；同时 `phaseN run` 的 RESOURCE 走 `cli/resource_gate.h → GateDiag` 路径，两者互不覆盖 ⇒ 同一"资源门禁失败"在不同路径返回 5 或 10。③`check_api_docs.py` 的 EXIT_NAMES 又把 6 命名为 EXEC。
- 影响: GUI 无法据退出码区分 backend 故障与资源门失败；宪章 §17 门禁退出语义不稳定。
- 建议处置: 废止 LEG 退出码表或移入 `docs/archive/`；文档码表生成自 `cli/exit_codes.h`；`exit_code_from_error` 的 RESOURCE 改 10 并补单测；把 docs_machine_consistency 挂 CI 或删除其"全量校验"表述。
- 置信度: 高 · related: M5b-E-03、M5b-G-15
