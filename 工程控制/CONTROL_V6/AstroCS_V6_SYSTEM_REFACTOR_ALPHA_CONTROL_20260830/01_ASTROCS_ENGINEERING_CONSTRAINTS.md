# AstroCS 预发布工程约束

状态：已冻结  
适用阶段：Alpha 预发布、首次正式发布及其架构收敛工作  
日期：2026-08-29  
适用分支：`main`

## 1. 文档效力

本文汇总项目近期已经确认的工程方向和硬约束。后续控制包、Agent 任务、代码修改、测试和审核不得与本文冲突。

若历史控制包、旧文档或 Agent 自行提出的方案与本文冲突，以本文为准。本文只由项目负责人确认后修改；Agent 不得自行放宽、删除或重新解释硬约束。

根目录 `AGENTS.md` 应保持简短，只负责要求 Agent 阅读本文及当前任务相关的模块合同，不重复全文。

## 2. 当前阶段与核心目标

AstroCS 当前处于 Alpha 预发布和架构收敛阶段。近期工作重点不是继续增加大量新功能，而是：

1. 恢复并统一原有模块化架构；
2. 确保科学定义、算法、数据语义、接口、代码和测试相互吻合；
3. 建立可复用的模块级数值验证，降低未来迭代的全链路验证成本；
4. 完成可靠、可维护、可检查的纯 CPU 正式发布基础；
5. 消除长时间重计算中的单线程和低资源利用问题；
6. 形成 Linux/Windows 双平台 CLI 发布链路。

本阶段禁止借架构整理之名改变科学公式、扩大功能范围或进行无关重写。科学缺陷必须单独立项、单独提交、单独验证。

## 3. 产品与发布形态

1. AstroCS 以统一 CLI 为正式产品入口，提供 Linux amd64 和 Windows amd64 两个版本。
2. Phase1、Phase2 由同一 CLI 和 Pipeline Runtime 编排，不再各自形成独立调度体系。
3. 未来 Windows GUI 通过稳定的 CLI 命令、配置和进程协议调用核心能力，不直接绑定科学模块内部实现。
4. Linux 版本面向命令行和自动化用户，不要求同步开发 GUI。
5. Phase3 定义为“HiPS 球面产品到平面 FITS 的映射”。当前尚未开发，任何文档和发布报告不得把它标记为已实现。
6. 预发布版本使用 Alpha 命名；首次正式发布范围必须明确列出已实现和未实现阶段。

## 4. ACR 与计算后端决策

### 4.1 当前冻结范围

ACR 是未来的 CPU/GPU 异构计算底层。由于开发和科学等价验证成本较高，ACR 不进入当前 Alpha 和首次正式发布的生产依赖。

当前要求：

- 保留 ACR 源码、接口、文档和独立测试；
- 不删除 ACR，也不继续扩大业务接入；
- Phase1/Phase2 生产链不得依赖 ACR 才能运行；
- ACR 不作为当前预发布或首次正式发布的阻塞门禁；
- 正式发布后的独立性能更新再接入 CPU/GPU 动态异构计算；
- 未来接入必须通过统一计算后端接口完成，不得重新侵入科学算法和 Pipeline 调度器。

### 4.2 首发 CPU 后端

首次发布先完成科学可靠、资源利用充分的纯 CPU 实现。支持的实现路径可包括：

- amd64 保守标量路径；
- AVX2 路径；
- AVX-512 路径；
- OpenMP 或统一线程池并行路径。

不得硬编码 CPU 核心数量、线程数量或假定某指令集一定更快。不同 ISA 后端必须通过同一数值合同和等价测试。

CLI 必须提供 benchmark 子命令，测量至少包括：

- 可用逻辑核心与有效线程扩展；
- 标量、AVX2、AVX-512 的实际吞吐与精度；
- 内存带宽及典型数据规模下的瓶颈；
- 推荐线程数、分块大小和计算后端。

benchmark 生成机器配置文件，运行时据此选择已验证的最优 CPU 路径。未执行 benchmark、配置损坏或硬件不匹配时，必须回退到保守兼容路径并产生清晰诊断，禁止盲目启用高级 ISA。

发布包可以包含多个 CPU 计算 DLL/共享库，由 CLI 统一选择；对外不得暴露多套不一致的科学接口。

## 5. 并行和资源利用硬约束

1. 长时间、计算密集的生产任务不得以单线程实现或运行。
2. 短时 I/O、元数据解析、初始化、极小稀疏任务允许串行。
3. 确实无法有效并行的计算必须有量化证据、明确原因和负责人批准，不能由 Agent 自行豁免。
4. 重计算任务运行时必须同步采集 CPU、线程、内存、磁盘 I/O、等待、峰值、均值和时间序列。
5. 对明确为 CPU 计算受限的阶段，应持续使用接近全部已分配 CPU；若长期低于目标利用率，任务不得静默通过，必须定位锁等待、串行区、负载不均、重复 I/O、内存带宽或算法复杂度问题。
6. 不以“程序最终完成”代替性能验收，也不以单个瞬时峰值证明资源已被充分利用。
7. 线程预算由统一运行时管理，模块不得各自硬编码线程数或相互过度订阅。
8. 性能优化必须先采样和定位，再修改；禁止无意义反复运行完整历史基准。

## 6. 目标架构

工程收敛为以下职责边界：

1. **CLI**：命令入口、配置加载、benchmark、运行控制和稳定机器输出。
2. **Pipeline Runtime**：解析 Pipeline、建立依赖图、调度模块、传播取消和错误、管理 checkpoint。
3. **数据管道**：承载具有明确 schema、单位、坐标系、精度、所有权和 provenance 的数据对象。
4. **I/O 与 Artifact Store**：唯一负责 FITS/HiPS/缓存/原子写入/产物索引，不负责编排科学步骤。
5. **资源调度器**：统一管理线程、内存预算、任务并发和运行指标。
6. **模块注册表**：加载模块描述，校验输入输出和配置，向 Pipeline Runtime 提供执行入口。
7. **科学模块**：只实现本模块科学算法、CPU 内核和独立验证。
8. **计算后端**：当前为纯 CPU；未来可在不改变科学模块合同的前提下接入 ACR。
9. **统一日志系统**：通过运行上下文集中接收日志、指标、警告、错误和阶段事件。

Pipeline 调度器负责“执行什么以及先后依赖”，计算后端负责“具体内核如何计算”。二者不得混为一体。

现有 `PipelineFrame`、I/O 唯一入口、DLL/共享库隔离、科学合同、模块测试和 ACR 内核注册等有效设计应尽量保留，通过适配器逐模块迁移，禁止大爆炸式重写。

## 7. 模块化与注册协议

每个生产模块必须能够独立理解、构建、测试和替换，并提供统一的模块描述，至少声明：

- 唯一模块 ID、版本和 ABI；
- 输入输出端口；
- 数据 schema、单位、坐标系、精度和无效值语义；
- 配置 schema 和默认值；
- 前置条件、后置条件和失败语义；
- 串行/并行模型、线程预算和内存需求；
- 执行入口和 CPU 后端；
- 日志、指标、取消和 checkpoint 接口；
- 对应的 SCI、ALG、DATA、API 和 TEST 标识；
- 独立数值验证入口。

新增功能原则上通过“实现模块 + 声明合同 + 注册模块 + 组合 Pipeline”完成。不得要求在 CLI、I/O、调度器和多个无关模块中同时硬编码新阶段。

调试应能根据静态 Pipeline 图和真实运行 trace 定位到具体模块、端口、数据对象和提交版本。

## 8. 科学与数值验证

### 8.1 追溯关系

所有核心实现必须形成以下可检查链路：

`SCI 科学定义 → ALG 算法推导 → DATA/API 合同 → 模块与源码符号 → TEST 数值验证 → 发布证据`

科学文档说明计算对象、物理意义、数学定义、单位、假设和适用边界。算法文档从科学定义推导离散实现、近似、误差和复杂度。架构与接口文档说明这些算法如何被软件承载，不得反向篡改科学定义。

### 8.2 模块级验证

每个科学模块至少维护：

- 确定性的合成数据生成器；
- 独立 Oracle 或解析解；
- 科学不变量和性质测试；
- 边界、NaN/Inf、空输入和极端参数测试；
- 串并行结果一致性测试；
- 标量/AVX2/AVX-512 后端等价测试；
- 确定性、精度和允许误差说明；
- 性能及资源利用测试；
- 标准化机器报告。

正常内部重构优先运行模块测试和自动计算出的受影响链测试，不反复对比大量历史版本，也不反复跑完整真实数据。

### 8.3 全链路验证触发条件

以下情况才要求扩大到完整链路或真实数据：

- 发布候选版本；
- 科学定义或离散算法改变；
- 数据合同、单位或坐标语义改变；
- Pipeline 拓扑改变；
- 编译器、平台、ISA 或计算后端改变；
- 模块测试发现跨阶段异常；
- 接缝、黑洞、条纹、排异或其他图像级问题需要真实场景确认。

真实数据不是模块单元测试的替代品。历史版本也不是唯一科学 Oracle；应以科学文档、解析解、合成数据和不变量为主要判据。

## 9. Linux 与 Windows 分工

### 9.1 Linux 常在线控制节点

腾讯云 Linux amd64 服务器资源较低，主要承担：

- 文档与代码一致性检查；
- 静态分析、语法检查和 API 提取；
- 轻量编译和单元测试；
- 小规模合成数据验证；
- Pipeline 和注册表检查；
- 任务控制、证据汇总和长时间低资源任务。

可从 Fatduck 获取少量冻结并哈希的真实数据辅助验证，但应避免在低资源 Linux 节点反复执行大规模重计算。

### 9.2 Windows Fatduck 计算与发布节点

Fatduck 远程 Windows 节点主要承担：

- Windows amd64 正式构建；
- MSVC/Windows CLI 兼容验证；
- benchmark 和多 ISA 路径验证；
- 批量真实数据及银心三板块验证；
- CPU、内存和 I/O 利用率采样；
- HiPS 浏览器人工图像审核；
- 最终发布产物生成。

Windows 离线时，Agent 必须继续完成 Linux 上可以完成的工作，不得因非必要远程依赖整体停止。只有缺少必需数据、权限、科学决策或最终 Windows 发布证据时才允许标记真实阻塞。

## 10. 文档体系

### 10.1 L0 项目负责人审查层

项目负责人只需阅读根目录 `REVIEW.md` 及其链接的少量顶层文档：

- `SCIENCE_OVERVIEW.md`：核心科学定义、假设和结论；
- `PIPELINE_OVERVIEW.md`：Phase1/2/3 数据流和模块关系；
- `ARCHITECTURE_OVERVIEW.md`：CLI、I/O、调度器、模块和计算后端；
- `RELEASE_STATUS.md`：通过项、失败项、未验证项和发布限制；
- `CHANGE_REVIEW.md`：本轮变化、科学影响、测试证据和需负责人决策事项。

顶层文档必须简洁、可审查、包含必要公式、流程图、风险和证据链接。不得要求项目负责人维护或逐份阅读底层实现文档。

### 10.2 L1 规范层

面向开发 Agent，统一使用稳定标识：

- `SCI-xxx`：科学定义；
- `ALG-xxx`：算法推导；
- `DATA-xxx`：数据语义；
- `ARCH-xxx`：架构约束；
- `API-xxx`：接口定义；
- `MOD-xxx`：模块注册；
- `TEST-xxx`：验证要求。

规范层由人工编写和审核，机器检查结构、引用和覆盖关系。数学语义和科学正确性不能仅由关键词检查代替。

### 10.3 L2 实现层

每个模块维护自己的 README、接口解释、实现约束、并发模型、内存所有权和测试说明。稳定定义进入模块文档，临时调试过程进入日志，不得把历史审计记录和任务编号长期堆积在生产代码注释中。

代码注释重点解释数学原因、单位、所有权、线程约束、边界条件和非显然设计，不复述代码。

### 10.4 L3 机器证据层

从源码、构建和运行结果自动生成：

- API/ABI 清单；
- 模块注册表；
- 静态调用图和 Pipeline 图；
- 实际运行 trace；
- 文档—代码—测试追溯矩阵；
- 静态分析和语法检查结果；
- 数值测试报告；
- 性能与资源利用报告。

机器生成证据不得手工修改，也不得直接成为顶层科学结论。

### 10.5 单一权威来源

- 科学公式以 SCI 为权威；
- 离散算法以 ALG 为权威；
- 数据含义以 DATA 为权威；
- 真实接口签名以源码和 AST 提取结果为权威，API 文档负责解释；
- Pipeline 拓扑以机器可读 Pipeline IR 为权威；
- 模块集合以注册表为权威；
- 测试结论以现场生成证据为权威；
- 顶层文档只汇总权威来源，不重复维护另一套底层定义。

## 11. 机器一致性检查

应逐步建立自动检查，至少覆盖：

1. 每个生产模块都有唯一注册描述；
2. 每个端口引用有效 DATA 合同；
3. 每个算法实现引用有效 ALG/SCI 标识；
4. 每个核心合同至少有一个独立测试；
5. 使用 Clang AST 等工具提取真实函数名、参数、类型和可见性；
6. 代码导出符号与 API/ABI 合同一致；
7. 注册表、Pipeline 配置、链接产物和实际模块集合一致；
8. 文档声明的阶段顺序与静态 Pipeline 图一致；
9. 静态 Pipeline 图与真实运行 trace 的模块和端口一致；
10. 文档声明的串并行模型与代码线程入口一致；
11. 重命名或删除后不存在悬空文档、配置和测试引用；
12. 根据提交差异生成受影响合同和测试集合；
13. 顶层 PASS/FAIL/NOT VERIFIED 状态可追溯到不可修改的现场证据。

机器检查可以证明结构和追溯关系，不得声称仅靠 AST、关键词或文档链接就证明科学正确。科学正确性仍需推导、独立 Oracle、性质测试和抽查。

## 12. Git 与执行流程

1. 只在 `main` 开发，不创建功能分支作为常规流程。
2. 每个 commit 只包含一个可独立解释和验证的目的。
3. 架构迁移、科学修改、性能修改和文档修复不得混在同一个 commit。
4. 每个原子任务通过对应检查后 commit，并及时 push。
5. 提交信息、证据和 `CHANGE_REVIEW.md` 必须能说明修改、影响范围、测试和限制。
6. 禁止 force push、删除历史和未经授权的破坏性 Git 操作。
7. 不设置大量必须人工回复才能继续的停止点。Agent 应连续完成 Linux 可执行工作，并在 Windows 在线时继续远程验证。
8. 只有以下情况允许停止并请求决定：权限或数据缺失、不可恢复失败、科学定义冲突、需要负责人选择、将执行破坏性操作、无法满足发布硬门禁。
9. 所有外部进程、网络、远程硬件和可能阻塞的脚本必须设置明确超时，并持续输出或保存日志。

## 13. 控制包与审核包

控制包必须包含详细任务、依赖、输入、验收标准、检查点和逐项 checklist，使执行 Agent 无需自由猜测任务含义。检查点用于记录和自动判定，不应被滥用为频繁人工停工点。

审核包必须采用白名单打包，只包含本轮审核必要内容，例如：

- 当前 commit、仓库身份和环境摘要；
- 当前相关源码或可验证的源码快照；
- 本轮更新的 L0/L1/L2 文档；
- 机器一致性报告；
- 测试、性能和资源利用摘要；
- 失败日志和最小复现；
- 文件清单和 SHA-256。

审核包禁止包含：

- Git 历史对象和无关旧版本；
- 原始大规模 testdata；
- 可重新生成的完整构建目录；
- 大型缓存、临时文件、崩溃转储；
- 其他项目或其他对话内容；
- 未在白名单和大文件清单中声明的文件。

大型数据和产物只记录路径、来源、大小、哈希和生成命令。确需提交图像结果时，仅包含审核所需的代表性预览和小型差异证据。

## 14. 每轮负责人审查摘要

每轮工作结束，`CHANGE_REVIEW.md` 至少回答：

1. 本轮修改了什么；
2. 是否改变科学定义或算法；
3. 是否改变数据语义、接口或 Pipeline；
4. 自动判定的影响范围；
5. 执行了哪些模块测试和链路测试；
6. 文档—代码一致性是否通过；
7. CPU、内存和 I/O 是否退化；
8. 哪些结论由机器验证，哪些由人工抽查；
9. 对应的原子 commit；
10. 当前是否达到发布门禁，以及尚未验证什么。

项目负责人只审核顶层科学结论、架构边界、重大风险和发布状态。底层实现、函数级文档和测试维护由 Agent 负责，但必须可追溯并接受抽查。

## 15. 当前明确的非目标

当前阶段不做：

- ACR 生产接入和 CPU/GPU 混合路由；
- Windows GUI；
- 未经单独设计的 Phase3 实现；
- 与预发布无关的大规模新功能；
- 为追求形式统一而进行全仓无关格式化；
- 反复以历史版本全量运行代替模块级科学验证；
- 用文档自报 PASS 代替现场编译、测试和运行证据。

## 16. 最终判定原则

首次正式发布必须同时满足：

- 科学定义与算法推导可靠；
- 数据语义、接口、代码和测试可追溯；
- Phase1/Phase2 通过统一 CLI 和 Pipeline Runtime 工作；
- 纯 CPU 后端在支持的平台上正确选择 ISA 并充分利用资源；
- Linux 和 Windows 构建与验证证据完整；
- 模块能够独立测试，未来修改可按影响范围验证；
- 顶层文档足以让项目负责人判断科学、架构和发布风险；
- 未实现能力和已知限制被明确披露。

最终目标不是一次性“把当前代码跑通”，而是建立一种长期可持续的工程机制：新增、替换或调试模块主要通过标准合同、注册和独立测试完成，不再要求每次全局修改和重新证明全部数值链路。
