# 冻结需求

## 1. 产品定位

ACR 是 AstroCS 的独立底层异构计算黑箱。它面向未来少量密集计算模块，提供 CPU 多线程、CPU ISA、GPU、多 GPU 和 CPU+GPU 联合执行。本支线只开发底层，不改造任何真实算法。

## 2. 核心路由原则

ACR 采用：

> 离线通用硬件画像 Benchmark + 任务特征成本推算 + 运行时工作保持动态派发。

明确禁止：

- 用户配置 CPU/GPU 任务百分比；
- 在正式 API 中传入 `cpu_share`、`gpu_share`；
- 把某个经典实验的切分比例直接固化为所有任务路由；
- 为每个 AstroCS 业务算法做完整比例穷举；
- 运行时在线训练或修改硬件画像。

允许：

- Benchmark 对不同设备、尺寸、精度、ISA和线程规模分别测量；
- 运行时读取当前队列、设备健康、数据驻留和内存预算；
- 空闲设备从共享工作池继续领取适合的未开始工作块；
- 根据画像模型和剩余工作量动态调整下一批块大小。

## 3. 本支线必须完成

- 公共 API、任务特征、Buffer、事件和错误语义；
- oneTBB CPU runtime；
- CPU ISA发现、安全门禁和多版本实现；
- 可选 GPU portable backend及至少一个真实 GPU后端；
- 主存、显存、PCIe/互连、算术、归约、卷积、稀疏和启动开销 Benchmark；
- 固定、只读的多维硬件性能画像；
- 基于画像的成本估算器；
- 工作保持的 CPU/GPU动态调度器；
- 默认约95%资源占用控制；
- 经典实验、故障注入和持续测试；
- CPU-only构建、文档、CI、交付和主线合并。

## 4. 本支线禁止

- 修改或接入现有任何业务算法；
- 删除、替换或注释现有 OpenMP；
- 改变 PipelineFrame、Orchestrator 或正常 CLI；
- 使用 Drizzle、积分等真实业务代码作为底层 POC；
- 正常 AstroCS 启动时初始化 ACR；
- 新建版本分支、第二套 ACR 或新仓库。

## 5. 未标定行为

当 ACR 被独立工具或未来算法调用但没有有效硬件画像时：

- 正常运行；
- 使用保守纯 CPU 多线程路径；
- 输出非阻断警告，建议用户在空载时运行 benchmark；
- 不强制标定；
- 不自动判断用户是否空载；
- 不启用 GPU 自动路由。

普通 AstroCS 未调用 ACR 时不得输出该警告。

## 6. Benchmark行为

- 开始前只提示用户停止其他任务并保持空载；
- 不扫描、关闭或阻止其他程序；
- 使用有限、经典、可复现的测试矩阵；
- 测量实际支持的 Scalar/SSE/AVX/AVX2/AVX-512；
- 默认重点 FP32，同时覆盖 FP64 和 FP32+FP64累加；
- 分离 kernel、内存、传输、队列、分配和同步开销；
- 生成带硬件、驱动、编译器、依赖和内核实现指纹的只读画像；
- 正式运行不写回画像。

## 7. 资源控制

默认：

- CPU利用率目标约95%；
- 每张GPU利用率目标约95%；
- RAM/VRAM容量上限默认95%；
- I/O预算可配置。

95%是资源占用目标，不是任务切分比例，也不是永久停用线程。所有CPU线程均可参与。

## 8. 数值策略

- 默认 IEEE 754 FP32；
- CPU/GPU正常末位差异可接受；
- 不要求逐位一致；
- 默认关闭破坏语义的 fast-math；
- 特殊任务可声明 FP64、FP64 accumulator 或确定性合并；
- Benchmark和经典实验只做必要正确性验证，不建立沉重的设备精度认证体系。

## 9. 合并和备用

全部验收通过后合并到 `main`。合并后：

- ACR源码存在但不被现有算法调用；
- 普通运行无副作用；
- GPU SDK不是CPU-only构建强制依赖；
- 后续算法接入另开分支；
- 失败、不完整或证据不一致不得合并。
